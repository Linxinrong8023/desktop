# 智能体切换：换一个执行者，怎样继续同一件事

> 连续追问教材 · 样章二 · 待验收。核对日期：2026-09-10，依据 `project_learn` 当前实现。先读[对话历史保存](../对话历史保存/模块说明.md)，本章接着使用同一个虚构案例。
>
> 阅读目标：能够解释切换中的每个确认点，并在历史过长、目标能力不足、发送失败或执行中断时继续推理。文中的压缩、检索和交接事务设计属于可能方案，不是现有功能。

## 从用户眼中的“换一个 Agent”开始

上一章，用户在商城项目中要求：

> 修复重复重试，最多重试两次，不改变公开接口。

Agent A 已读取文件并定位问题，回复“下一步补充回归验证”。这不证明修复和测试已经完成。现在用户想让 Agent B 继续，希望不用重新介绍全部背景，也不想丢掉前面讨论的约束。

界面上是一次选择，设计上至少有四个问题：

1. 用户仍在原来的对话里，系统怎样保持这段对话的身份？
2. Agent B 有自己的会话，怎样把它接到同一个工作环境？
3. Agent B 原本不知道历史，需要交给它哪些信息？
4. 从“选择了 B”到“B 能继续工作”之间失败了，系统怎样识别并恢复？

**可以这样口头介绍当前设计：** Ora 的会话和历史由自己保存，执行者是可更换的绑定。用户点选新 Agent 后先保存待切换意图，实际发送时再创建目标 Agent 会话。目标准备成功后才停止旧的运行绑定，更新会话指向，并记下切换事实。下一条请求带上从历史整理出的交接文本；发送层接纳请求后再记下交接已发送的事实。这个设计保持了对话身份，但当前还缺少目标容量感知的压缩策略，也不是跨数据库、文件和 Agent 的统一事务。

下面逐个检查这段介绍中最容易被追问的地方。

## 决策一：为什么同一段对话需要多个编号？

### 直接使用 Agent 的会话编号有什么问题

如果用户眼中的对话直接等于 Agent A 的内部会话 A1，换到 B 就遇到困难：B 不认识 A1。把界面编号也换成 B1，又会让原来的标题、历史、归属和打开入口需要跟着换身份。

当前把稳定的“对话”与可更换的“执行关系”分开。上一章的身份继续使用：

| 对象 | 切换前 | 切换后 | 原因 |
| --- | --- | --- | --- |
| Ora 会话 S | `a1b2c3d4-1111-4111-8111-123456789abc` | 不变 | 用户继续同一段对话 |
| 工作区 W | `b1c2d3e4-2222-4222-8222-123456789abc` | 不变 | 执行的是同一个工作区中的任务 |
| 当前 Agent | `demo/agent-a` | `demo/agent-b` | 更换执行能力提供者 |
| Agent 内部会话 | `provider-a-001`，简称 A1 | `provider-b-001`，简称 B1 | B 为自己建立新的会话 |
| Ora 历史文件 | `sessions/a1/b2/<S完整编号>.jsonl` | 不变 | 文件由稳定的 Ora 会话编号定位 |

`agent_cli` 保存的是 Agent 身份，不是角色模板表 `agents` 的主键。新建一个角色模板不能完成运行 Agent 的切换。

### 既然都在同一工作区，B 直接读代码不就知道发生了什么？

代码可以帮助 B 了解当前文件状态，却不一定包含“最多重试两次”“不能改变公开接口”“哪些方案已讨论后被否决”。反过来，历史里说“已经修改”也不能代替检查当前文件，因为用户或其他工具后来可能再次修改了它。

因此继续任务至少需要两种信息：**当前工作区的实际状态**和**此前形成的目标、约束及决定**。共享目录不能替代上下文交接，交接文本也不能替代读取实际工作区。

### 为什么不能直接把 A 的私有会话文件交给 B

私有格式、索引、状态和恢复方式由各个 Agent 决定，B 不一定认识 A 的文件。即使格式相似，里面还可能包含只对 A 有意义的工具状态或内部信息。

当前采用共同可接收的文字作为交接载体。它降低了对某个 Agent 私有格式的依赖，但表达能力变弱：B 收到的是“被告知的历史”，不是自己真实参与过的历轮交互，也不自动继承 A 的内部状态。

**继续追问：如果未来两个 Agent 支持统一的历史导入呢？**

可以增加更丰富的导入路径，但仍需明确内容类型、模型容量、工具状态能否恢复以及失败语义。统一格式能改善互通，不能直接保证导入后行为一致，也不能替代当前文件状态检查。

## 决策二：切换应该先停止旧 Agent，还是先准备新 Agent？

### 用户点选为什么不立即拆掉原来的执行关系

Agent A 可能正在回复。点一下 B 只是表达“接下来希望换人”，不应立即破坏本轮执行。当前前端先在内存里记录待切换选择，下一次发送才进行实际换绑。

这也带来一个容易误解的状态：选择器已经显示 B，但数据库可能仍指向 A。前者是意图，后者是已经提交的执行关系。待切换意图未持久化，页面重载后不保证保留。

这层前端延后安排不等于后端允许任何时机都不打断：后端真正换绑时会停止旧会话的运行对象。介绍“不打断”必须讲清它依赖的交互流程，不能无限扩大承诺。

### 当前顺序为什么先创建 B1

假设先停 A，再发现 B 没安装、配置不完整或模型不支持。用户失去了原来可用的执行关系，却没有得到新执行者。

当前先检查目标是否与原 Agent 相同、历史是否已降级，再用同一工作区准备 B1，并应用所选模型意图。新会话准备成功后，才进入停止旧绑定和更新记录的阶段。准备中的新会话若未交接给正式运行对象，会由清理机制尝试释放。

这里的“准备成功”仅表明 B1 已经建立、必要配置阶段通过。此时 B 还没收到历史，更不能说已经完成用户任务。

### 用数据库变化展示中间过程

`sessions` 始终只有 S 这一行。下面只展示变化相关字段；标题、创建时间、工作区和可见性保留，完整字段见上一章。

| 时点 | `agent_cli` | `agent_session_id` | `status` | `updated_at` | 其他事实 |
| --- | --- | --- | --- | --- | --- |
| 开始前 | `demo/agent-a` | A1 | `0`（Running） | `1789005600000` | 历史记录到位置 6 |
| 页面选择 B | 仍为 A | 仍为 A1 | 不因点选而更新 | 不因点选而更新 | 前端内存多一个待切换选择 |
| B1 准备成功 | 仍为 A | 仍为 A1 | 仍以当前旧运行状态为准 | 尚未因改绑更新 | B1 已存在，但尚未成为数据库权威绑定 |
| 停止旧运行绑定 | 仍为 A | 仍为 A1 | 停止流程可能已置为 `1` | 取停止处理时间 | 不能再说 A 的原活动状态完整保留 |
| 更新当前绑定 | `demo/agent-b` | B1 | 绑定写入保留此刻 status；若已停止则仍为 `1` | 例如 `1789006200000` | 两个绑定字段一起更新，但尚未完成全部切换步骤 |
| 更新为 Running | B | B1 | `0` | `1789006200000` | 第二次数据库操作 |
| 追加切换事实并建立新运行对象 | B | B1 | `0` | 不必再变化 | JSONL 增加位置 7 的切换记录 |

示例改绑时间为北京时间 10:10。这里故意展示“数据库暂时指向 B，却尚未回到 Running”的中间状态；如果直接给一张最终行，很容易漏掉这个故障窗口。

**边界与缺口：** 先准备 B 可以保护“新会话创建失败”之前的旧绑定；它没有保障整次切换失败都能恢复原样。旧运行对象停止之后，再发生数据库或文件错误，已经不是毫无影响的失败。

### 反例：只要返回失败，我就认为还在 A 上，可以吗

不可以。需要问失败发生在哪一步。目标创建失败时尚未替换旧绑定；绑定更新后追加历史失败时，数据库可能已经指向 B。一个统一的“切换失败”提示不足以解释所有状态。

可能的改进是给一次切换独立的操作身份和可查询阶段，让调用者遇到不确定结果时重新查询，而不是直接发起另一场切换。后面会讨论需要保存哪些证据。

## 决策三：历史交接应该在什么时候发生，怎样判断已经交接？

### 当前为什么等下一条消息再带历史

切换时建立 B1，但不立即为注入历史额外发起一轮任务。如果用户又改选其他 Agent，就避免了一次无意义的对话请求。B1 的创建仍有成本，后面的历史输入也有成本，所以不能将其描述为“切换零成本”。

下一次发送时，系统先读截至本轮之前的历史，整理成一个交接文本块，再加上用户的新消息：

| 发给 B1 的内容顺序 | 本案例中的内容 | 为什么这样组织 |
| --- | --- | --- |
| 第一块：交接说明和历史 | 原要求、A 的回复、工具名称与结果状态、切换说明 | 让 B 知道前面发生过什么，避免把旧要求当成完全未处理的新任务 |
| 第二块：用户新消息 | “继续补充回归验证，保留前面的约束。” | 明确这一轮现在要做什么 |

构造交接时，还没有把本轮新用户消息追加到历史。随后才保存用户新消息。这样交接文本不会先包含一次新消息，紧接着请求正文又包含一次。

展示给 B 的历史也不等于文件内容原样复制：

| 原记录中的信息 | 当前交接方式 | 造成的边界 |
| --- | --- | --- |
| 用户和助手文字 | 保留并按轮次整理 | 长对话仍可能很长 |
| 工具调用 | 保留名称与结果状态 | B 不会因此得到工具的完整输入输出 |
| 推理、计划等 | 不携带 | 不能声称迁移了原 Agent 全部内部过程 |
| 图片、音频等 | 变成类型说明或资源提示 | B 不会从一个 `[image]` 标记恢复图片内容 |
| 历史缺口或坏行 | 提醒记录不完整 | 提醒不能恢复丢失事实 |

因此当前过程更准确叫**筛选并整理历史**。没有调用摘要模型，也没有根据目标上下文上限生成指定长度摘要。

### 必须拆开的四个确认点

| 确认点 | 当前可观察的证据 | 不能据此推断 |
| --- | --- | --- |
| 新绑定提交 | `sessions` 指向 B1，切换流程完成相关步骤 | B 已经知道原来发生的事 |
| 请求发送被接纳 | 发送层接受携带历史的请求，取得等待响应的标识 | B 已验证输入合法、容量足够 |
| 目标响应 | 后续收到该请求的结果或错误 | 仅凭正常返回就保证所有约束被保留 |
| 任务质量达标 | 对新结果进行约束检查、测试或用户验收 | 当前系统已有通用的交接语义质量评分 |

当前 `HandoffDelivered` 记录在**第二个确认点**。发送层开始请求并不等待本轮最终响应；后续处理结果通过另一条事件过程到达。文档和口述都不能把这个记录解释为“模型成功吸收上下文”。

### 交接事实具体怎样保存

上一章的历史最后位置为 6。接下来依次增加：

| 位置 | 实际记录类型 | 主要字段／内容 | 证明什么 |
| --- | --- | --- | --- |
| 7 | `agentSwitched` | from=A，to=B，`agentSessionId=B1` | 执行关系已经发生切换，新的执行者还需要上下文 |
| 8 | `update` | 用户新消息 | 用户请求已记录；不证明请求已经发出 |
| 9 | `handoffDelivered` | `agent_session_id=B1` | 携带交接内容的请求已通过当前发送确认点 |

下面是实际序列化形状。字段命名存在 camelCase 与 snake_case 的区别，数据示例按当前结构保留，讲解不要求背诵拼写。

```jsonl
{"at":"2026-09-10T10:00:00+08:00","seq":7,"type":"agentSwitched","from":"demo/agent-a","to":"demo/agent-b","agentSessionId":"provider-b-001"}
{"at":"2026-09-10T10:00:00+08:00","seq":8,"type":"update","update":{"sessionUpdate":"user_message_chunk","content":{"type":"text","text":"继续补充回归验证，保留前面的约束。"}}}
{"at":"2026-09-10T10:00:00+08:00","seq":9,"type":"handoffDelivered","agent_session_id":"provider-b-001"}
```

没有独立的“切换记录表”或“摘要表”。当前绑定在 `sessions`，切换和交接确认在 JSONL，运行时另外记着“还欠一次交接”。进程重启后，可以依据最后相关历史记录重新判断这个状态。

### 连续追问：为什么不能把“新用户消息已保存”当作交接成功

用户记录是发送之前写入的。假设位置 8 保存完，连接立即断开，请求没有发出去。此时文件里有用户消息，却没有位置 9 的送达记录。重建运行对象时仍应认为欠交接。

如果仅因看见用户消息就清除这个状态，B 下一轮可能在不知道旧约束的情况下工作。两个记录描述的是两个不同的事实，不能为了少存一行合并成一个。

**继续追问：那为什么不等 B 完整回答后，再写送达记录？**

等待最终回答能得到更强的处理结果，但也出现另一种不确定：B 已接收并执行了一部分任务，连接却在最终响应前丢失。重试时再次塞入整段交接和任务，可能重复输入甚至重复工作。

当前选择发送确认点，是一种有限证据下的取舍。更强保障需要区分“已准备、已发送、目标接收、任务完成”，最好配合目标侧可查询的请求身份或去重能力。单纯把本地标记写得更晚，并不能解决两边状态不一致。

## 决策四：历史有几十万 token，新 Agent 装不下怎么办？

### 先诚实回答当前实现保障到哪里

**当前实现：** 读取 Ora 历史，保留历轮用户与助手文本，筛掉部分内容后拼成一个交接文本块。没有按目标模型容量进行 token 预算、分层摘要或原文检索的专门机制。

公共请求入口有 16 MiB 大小检查，但它发生在交接历史被加入之前。它检查用户请求的序列化字节大小，不是加入历史后的完整上下文，更不是目标模型 token 容量。因此不能拿这项检查回答“长历史已经有保护”。后续传输或 Agent 自身即使有限制，也不等于 Ora 做过预算规划。

**边界与缺口：** 交接请求可能已经通过本地发送确认点，随后目标才拒绝过长输入。此时送达记录可能已存在，当前没有专门围绕“上下文超限”重新压缩并建立新交接版本的完整恢复流程。不能假定下一次重试会自动变小。

### 先算预算，再选择压缩方式

以下是**假设场景的演算**，32,000 是示例容量，不是任何具体模型的规格。token 是模型输入输出的计量单位，不能简单与字符数或字节数等同。

如果目标总上下文可用容量是 32,000，我们保守分配如下：

| 用途 | 示例预算 |
| --- | ---: |
| 系统指令及执行者预设 | 3,000 |
| 工具／MCP 能力说明 | 5,000 |
| 当前用户消息及其附带内容 | 1,000 |
| 为本轮输出预留 | 4,000 |
| 估算误差和额外开销余量 | 3,000 |
| 剩余可用于交接历史 | **16,000** |
| 合计 | 32,000 |

这里预留输出是示意策略；实际目标如何计算总上下文、独立输出上限和隐藏开销，需要按 Agent／模型合同确认。Ora 可能看不到目标内部全部指令和工具开销，因此即便做出估算，也不应声称拥有绝对精确的剩余空间。

假设原历史 180,000 token，第一轮摘要仍有 22,000。它虽比原文短很多，还是超过 16,000，所以“已经压缩”不是成功标准。

一个可能的重新分配是：早期结构化摘要 10,000，近期原文 4,000，来源索引和关键原文摘录 1,500，共 15,500，小于历史预算。但数字合格只是第一道检查；还要确认关键约束是否保留，以及实际加入请求后是否仍然符合限制。

### 四种可选方案，各自会在哪里被考倒

以下为设计比较。除第一行的有损文字整理路径外，其余不是当前已实现功能。

| 方案 | 怎样工作 | 好处 | 主要失败方式 |
| --- | --- | --- | --- |
| 尽量直接传递文字历史 | 按轮次附带保留的原文，当前采用类似方式 | 容量足够时少引入摘要改写；容易追溯措辞 | 历史过长；旧噪声挤占新任务空间；当前也丢弃了部分非文字细节 |
| 只截取近期内容 | 保留最近若干轮或预算内的尾部 | 简单、快速、成本可控 | 早期“不改接口”等关键约束可能消失 |
| 分层摘要 | 较早内容整理成结构化摘要，近期保留原文，随长度继续合并 | 可以覆盖更长过程 | 摘要可能漏信息，反复摘要还可能积累歧义 |
| 摘要加原文检索 | 常驻摘要与索引，需要细节时回查原始记录 | 把常驻上下文和全量存储分开 | Agent 不知道自己漏了什么时不会主动查；检索也可能没找对 |

不能只说“用 RAG 就能解决”。检索需要提问，而遗失的早期约束恰好可能使新 Agent 不知道应该提问。关键约束应主动进入交接包，检索主要补充细节，两者承担不同职责。

### 可能方案：把交接当作一个有来源、可验证的产物

**要解决的问题：** 在有限上下文中保留任务连续性，并能解释遗漏或失败，而不是输出一个无法审计的大段总结。

可以把交接包分成以下内容：

| 部分 | 本案例应交接什么 | 为什么不能只交一段泛化总结 |
| --- | --- | --- |
| 当前目标 | 修复重复重试 | 防止只复述历史却忘记接下来要做的事 |
| 必须遵守的约束 | 最多重试两次；不改变公开接口 | 这是后续工作不可静默丢掉的条件 |
| 已经观察到的结果 | 读取了相关文件；A 表示已定位重复调用 | 区分可见证据与推断 |
| 尚未证实／未完成 | 本例没有证据证明修复已保存或回归已通过 | 避免摘要把“下一步要做”改写成“已经完成” |
| 重要决定及被否决方案 | 若有则说明原因；本例没有就不补写 | 新执行者需要知道哪些方向不该无故重走 |
| 近期原文 | 新问题和紧邻的具体讨论 | 减少细节被过早概括 |
| 来源与回查方式 | 对应 Ora 会话和历史位置／内容版本 | 发现疑问时可以检查原始证据 |

每条关键信息要能指向来源，且区分用户要求、Agent 判断和已经验证的结果。同一约束有更新时保留最新有效决定及变更关系，而不是机械保留互相矛盾的两句原话。例如后来用户明确允许改变接口，旧约束就不能继续被当作永恒规则。

这种结构化处理同样会出错。抽取到“最多两次”还要理解它是“重试两次”还是“总共尝试两次”；遇到原始表达本身含糊，应保留不确定性，而不是摘要替用户作决定。

### 如果这个交接包仍然太大

一个可讨论的处理顺序是：先去除重复和过程性噪声，再压缩较早的叙述，把大块工具细节改成带来源的摘要，保留核心约束与近期上下文。每轮调整后重新计算完整请求的预算。

如果连必要约束、当前任务和最低回答空间都放不下，应明确失败或要求缩小任务、选择更合适的目标。不能无限递归摘要，也不能为了返回“切换成功”悄悄删掉必须遵守的要求。

**预算未知时怎么办？** 先尝试取得可信能力信息；无法取得则使用明确标注的保守预算策略，并告知不确定性。目标返回超限后可以按更小预算生成新版本重试，但需要有限次数、停止条件和费用约束；如果连安全下界都无法判断，应让用户作出选择。未知不能当作无限大。

### 摘要需要保存什么，才能避免失败后从头乱来

以下是一份**尚不存在的交接准备记录示意**。它可以由未来专门的表和产物文件承载，不是当前 `sessions` 已有字段。

| 逻辑字段 | 示例 | 用途 |
| --- | --- | --- |
| 交接编号 | H1 | 同一次交接重试可关联 |
| Ora 会话 | S | 对应哪段原始对话 |
| 来源快照 | 截止某字节边界、位置范围 0～6、内容指纹 d1 | 确定摘要基于什么内容 |
| 目标约束 | Agent B、已确认的模型与工具配置版本 | 避免换目标后复用不合适的预算 |
| 预算与策略 | 历史预算 16,000；策略版本 P1 | 解释为什么选择这些内容 |
| 产物版本 | H1-v2；摘要位置及内容指纹 h2 | 同一版本重试复用，重新生成则另记版本 |
| 准备状态 | prepared／sent／rejected 等明确阶段 | 把准备成功和发送、目标结果分开 |
| 失败原因 | 例如 context_overflow | 决定缩小预算还是停止重试 |

原始 JSONL 保留，压缩的是给 B 的交接副本，不修改原历史来假装它一直很短。来源不能只存“最大 seq=6”：原先较小位置也可能被更正，需要文件边界和内容版本证据，判断旧摘要是否已过期。

**成本：** 增加摘要生成延迟、模型调用费用、产物存储和失效处理；保留原文及衍生产物还需要相应的删除／保留规则。

**失败：** 来源和目标配置未变时，发送失败可重用已校验产物；内容变化则重新准备。摘要服务失败不覆盖原历史，保留可重试的失败阶段。是否在释放旧绑定前完成这些准备，需要和切换事务设计一起决定，不能只在最后一个发送步骤塞进摘要调用。

### 连续切换十次，会不会越压缩越忘事

如果 B 只拿 A 的摘要继续生成新摘要，再把它交给 C，信息可能逐代损失。一个改进原则是：持续保留原始历史和带来源的决定记录，周期性从可验证来源重新整理，而不是始终摘要上一份摘要。

这不等于每次都重读全部历史。可以维护分段摘要及来源指纹，原段未变化时复用，发生更正时使对应摘要失效。索引、失效判断和回查能力必须一起设计，否则只是把错误缓存得更久。

### 怎样验证交接质量，而不只证明字数变少

先建立包含明确约束和后续任务的样例集合，至少包含早期约束、后期修改约束、已否决方案、未完成事项、长工具输出和多次切换。

比较直接交接、截取近期、分层摘要、摘要加检索在同一批任务上的表现。考察：关键约束有没有进入交接包、后续结果是否违反约束、是否把未完成误说成已完成、来源能否追溯、输入超限率、准备延迟和费用。模型结果可能波动，应重复执行，不用一个成功例子证明整体质量。

本案例可以检查 B 是否仍按“最多重试两次”设计验证、是否擅自改变接口、是否把 A 的“已定位”误认成“已经修复并通过测试”。这些比摘要措辞是否流畅更有意义。

不应只让负责生成摘要的同一个过程自己评价“没有遗漏”。能机械核对的约束和实际测试结果应单独检查；语义部分结合人工标注或独立评估，仍说明评估的局限。

## 决策五：切换到一半退出，怎样知道应该继续哪一步？

### 当前有哪些持久证据，哪些只是内存状态

数据库回答“当前绑定是谁”，JSONL 回答“记录到哪些切换和发送事实”。临时运行对象知道自己还欠不欠交接，但进程退出后这份内存知识消失，只能根据已保存证据重建。

不要把一个正常路径中的最终状态当作所有失败路径的结果。按中断位置逐个看：

| 失败位置 | 可能已经留下的事实 | 当前结果／保障边界 |
| --- | --- | --- |
| 创建 B1 失败 | 数据库仍指向 A | 此次换绑尚未停止旧绑定；目标准备失败被返回 |
| B1 准备完成，但尚未替换旧绑定时请求取消 | B1 是未正式接管的新会话 | 释放保护尝试清理未暴露会话；不把它当成已提交绑定 |
| 停止 A 后，绑定更新失败 | 旧运行对象可能已停止，数据库仍指向 A | 不保证恢复原活动状态；后续操作需要按保存绑定重新建立运行关系 |
| 绑定已写 B1，但状态更新失败 | 数据库可能已经 B1／Stopped | 两次更新不是一次完整切换事务，调用失败不能解释成“仍在 A” |
| 绑定和状态成功，但位置 7 未记录就退出 | 数据库已指向 B1，历史未必有切换证据 | **阅读推断的风险：** 重建时可能缺少“B1 还欠历史”的证据，本章未做该窗口的故障注入 |
| 位置 7、8 已写，发送失败 | 切换与用户意图存在，没有位置 9 | 交接仍未结清；发送失败路径记录取消边界，后续重建可再次交接 |
| 发送成功，但位置 9 写失败 | B 可能已收到，本地没有持久送达记录 | 历史降级；恢复后可能再次交接，优先避免静默漏交接，但存在重复输入成本 |
| 位置 9 已写，目标之后报告上下文超限 | 本地已记录发送事实 | 不能视为模型成功吸收；当前缺少专门的压缩重试闭环 |
| 交接时读取文件失败 | 内存仍记着欠交接 | 当前仍可以发送本轮新内容，并保留债务；B 这轮可能没有旧背景 |

最后一行值得单独说明：当前“历史读不到时先发送新消息”的选择优先保持一定可用性。对于必须依赖先前约束的任务，可能更希望直接阻止发送。这是可讨论的产品取舍，不能用“之后会重试”掩盖本轮上下文缺失的影响。

### 可能方案：让切换有独立的准备记录和阶段

要改善“数据库已经换人，历史却没有切换证据”的窗口，可以考虑在释放旧绑定前，先保存一次切换意图，记录原绑定、目标绑定、来源快照、产物版本和操作阶段。它与上一节的交接产物属于同一操作的不同证据，不必各自发明互不关联的编号。

举例：`交接H1，原绑定A1，目标B1，预期原绑定版本v1，历史快照d1，阶段prepared`。完成本地绑定更新时，在同一个数据库事务里推进该记录；JSONL 的切换说明可以从这份持久操作记录恢复或重试写入，而不再独自承担“是否需要交接”的全部判断。

**这仍不能形成跨 Agent 的全局事务。** 数据库最多原子地保存本地绑定和操作阶段。目标收到请求后是否执行、外部文件是否改变，需要目标提供可查询／去重的请求能力，或由业务设计补偿和人工确认。

### 准备期间旧 Agent 又产生了新内容怎么办

如果长摘要生成花了十几秒，而 A 还在输出，刚生成的摘要可能已经落后。不能只说“先准备再切换”而不定义快照边界。

可能先在 A 运行时预生成，再在实际切换前短暂阻止这段会话接受新任务，等待当前轮次结束或明确取消，取得最终稳定边界。确认来源未变化则直接使用；变化了就追加整理差量或重建产物。准备失败时尽量保持旧绑定可用，再决定是否允许用户重试。

这增加等待、快照校验和产物失效成本，但避免把过时摘要当作最后一刻的会话事实。需要明确哪些动作属于预准备，哪些动作才真正停止旧执行关系。

### 同时发来两次切换请求怎么办

仅仅让数据库更新排队，不等于请求里引用的旧状态仍然有效。若两个请求都认为原来是 A，一个先切到 B，另一个随后仍以“从 A 切换”为前提，就需要重新校验。

当前路径先读取原会话、准备目标，再进入串行换绑阶段。这里应针对并发请求补充验证，不能把前端通常串行操作当作整个后端的一致性证明。本样章没有复现这组并发竞态。

可能的做法是在提交前核对预期原绑定或版本，发现已变化则拒绝过期请求并返回当前状态；配合操作编号让同一次请求重试不重复创建目标会话。代价是调用方要处理冲突与重新确认，不能直接覆盖最近一次选择。

## 决策六：切回 A，为什么不能继续用 A1？

在 B 工作之后，A1 的内部上下文停留在离开时。直接恢复 A1 会漏掉 B 的讨论、决定和操作。当前切回 A 会建立新的内部会话，例如 A2，再按同一个 Ora 历史交接。

| 阶段 | Ora 会话 | 当前绑定 | 历史文件 |
| --- | --- | --- | --- |
| 最初 | S | Agent A／A1 | S 的文件 |
| 切到 B | S | Agent B／B1 | 同一文件继续增长 |
| B 完成若干工作后切回 A | S | Agent A／新的 A2 | 继续同一文件，交接包括 B 留下的记录 |

这里“不继续使用旧绑定”不意味着 Ora 删除了 A 的私有历史。当前停止和卸载路由与删除 Agent 私有记录是不同的权限边界。

**替代方案：** 保留 A1，以后仅把 B 新增的信息补给它。这能减少重复输入，但需要精确知道 A1 已经知道哪些位置、它内部有没有压缩或修改、差量是否被处理、是否与当前文件状态冲突。每个 Agent 都需要可验证的上下文进度。缺少这些能力时，全新会话加交接更容易推理，代价是重复的准备和输入成本。

还有一种相似但不同的情况：并没有切换 Agent，只是 A1 无法恢复，需要重建 A2。当前会先在内存准备 A2，等携带历史的请求通过发送确认点后才保存替代绑定；此前数据库仍留 A1。它没有跨 Agent 的切换记录，不能机械套用 A→B 的写入顺序。

## 把一次完整切换串起来

下面是正常路径的检查单，按“已知事实”阅读，而不是把每一步都叫成功：

1. **原始状态。** 会话 S 在 W 工作，绑定 A1，历史已记录到位置 6；用户原约束仍在位置 1。
2. **表达意图。** 页面选择 B，只在内存暂存；当前工作尚未因点选被替换。
3. **实际发送。** 用户提交“继续补充回归验证，保留前面的约束”。系统先处理待切换目标，建立 B1 并完成必要设置。
4. **本地换绑。** 停止旧运行关系，更新数据库绑定和状态，追加位置 7 的切换事实，建立 B 的运行对象。这里有跨操作、跨存储窗口。
5. **准备交接。** 从位置 7 及其之前的历史生成给 B 的文本，保留筛选后的旧内容；此时不包含本轮新消息。
6. **记录本轮请求。** 位置 8 保存原用户消息；请求中另外带交接块，不把这份交接再次写成用户原话。
7. **通过发送确认点。** 请求被发送层接受，位置 9 记录交接已发送。当前绑定和待交接状态已推进，但目标的后续响应尚未得到。
8. **接收结果与验收。** B 可能继续回复，也可能返回错误。后续输出继续使用同一份历史；当前设计没有自动证明 B 保留了全部约束，需要结合任务结果检查。

发送给目标的配置、模型选项还要符合新会话实际报告的能力。`sessions` 当前没有模型列，不能仅从这张会话行还原 B 本轮实际使用的全部模型配置。这也是未来按目标预算缓存交接包时需要补充的证据。

## 综合自测：沿着自己的回答继续追问

### 追问链一：为什么不直接传全部历史

你回答“太长，所以摘要”。面试官继续问：新模型更小怎么办？摘要仍然超限怎么办？必要约束本身就超过预算怎么办？

<summary>展开分析提示与参考思路</summary>

先明确目标的总上下文、输出限制以及宿主无法看到的开销，按实际完整请求计算历史预算。摘要长度必须服从预算，不能仅依据压缩率。再区分可降级的过程细节和必须保留的任务约束。

如果最低必要信息加当前请求与回答空间都放不下，需要改变任务范围、目标模型或交互方式，明确告知用户。不能把删到能发送当作语义正确。验证要同时检查输入能否被接收和后续工作是否遵守约束。

</details>

### 追问链二：你说“摘要加检索”，为什么就不会忘事

B 不知道早期曾讨论过接口不能改，它会主动去检索吗？如果检索找到旧决定，却漏了后来的撤销怎么办？

<details>
<summary>展开分析提示与参考思路</summary>

检索解决“知道需要某类信息时如何找回来”，不能完全解决“不知道自己漏了什么”。关键目标与当前有效约束应主动随交接进入上下文，原文检索补充依据和细节。

摘要和索引需要带来源及变更关系，处理后来的修订或撤销。评测应专门放入“早期约束、很晚才会触发的任务”和“后来修改过的约束”。否则在最近几轮都能找到答案的样例上得到高分，没有证明长历史连续性。

</details>

### 追问链三：切换成功后，为什么 B 还能说上下文太长

数据库已经指向 B，文件里还有送达记录。这是不是说明数据库记录错了？要不要立即删掉送达记录并重发？

<details>
<summary>展开分析提示与参考思路</summary>

先说明各记录的语义。绑定记录描述执行关系，送达记录描述当前发送确认点；它们都不等于模型处理成功。所以问题可能是记录所承诺的能力有限，而不是某列必然写错。

未来应增加明确的目标拒绝状态和交接产物版本。是否重发要先判断目标有没有开始产生副作用、错误是否明确表示未接纳处理；不能见到任何失败就删除证据并重做。上下文超限的专门降级流程目前未实现，应这样如实说明。

</details>

### 追问链四：先准备 B，是否就能保证失败回到 A

B1 已准备好，旧运行对象也已停止，结果数据库第二次写入失败。你准备恢复什么？A 的原会话还能立即继续吗？

<details>
<summary>展开分析提示与参考思路</summary>

先确定第一步绑定写入是否提交，再检查状态和历史。旧对象已停止，不能承诺恢复进程内原状；最多根据可用的 provider 会话及持久历史重新建立运行关系。

更完整方案需要操作阶段、原绑定版本和目标身份，使恢复可以明确继续、补偿或等待人工确认。数据库能原子更新本地证据，不能回滚目标已经执行的工作。故障测试应覆盖每个阶段，而不是只让 B 创建失败一次。

</details>

### 追问链五：模型摘要给出一个漂亮总结，怎样证明有用

摘要保留了“修复重试问题”，却没有保留“不改变公开接口”。语言评分很高，后续任务也完成了。算成功吗？

<details>
<summary>展开分析提示与参考思路</summary>

先定义任务成功包含哪些约束。只完成主要功能但违反接口约束，应被判为交接失败或任务未达标。摘要质量不能只靠语言流畅度或覆盖主题来衡量。

建立带标注的约束、决定、未完成事项集合，检查它们是否进入交接；再安排会触发这些条件的后续任务，观察真实行为。比较多种策略的质量、超限率、耗时与成本，重复评估波动，并保留人工检查。

</details>

### 追问链六：历史里的命令都应该被新 Agent 照做吗

原工具输出里出现“忽略以前的约束”，或者历史中有已经完成的危险操作要求。拼成一个用户消息后，B 会不会重新执行？

<details>
<summary>展开分析提示与参考思路</summary>

交接必须区分“过去发生的内容”“当前有效的用户要求”和“不可信的外部输出”。当前文字包装与前言帮助表达历史语义，但不是一种形式化的安全隔离，也不证明新 Agent 永远不会误读。

可能改进包括保留来源类别、把已完成和待执行分开、仅在需要时提供外部原文，并在 Agent 的执行权限边界继续进行校验。评测要包含历史指令被重新执行、外部文本冒充新指令等反例。上下文管理与工具执行安全相关，但不能只靠摘要把二者一次性解决。

</details>
