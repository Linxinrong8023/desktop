## 从一次“好像卡住了”的回答开始

用户让 Agent A 修复重复重试，另一个窗口正在让同一个 Agent 分析测试。第一个窗口几十秒没有输出：是模型慢、工具仍在运行、连接损坏，还是界面消费太慢？如果答案只有“设置超时后重连”，很可能把第二个正常会话也杀掉，甚至让第一个任务重复改文件。

可以这样口述整体设计：Ora 按 Agent 身份管理共享连接，按会话管理串行状态和事件队列。一轮请求有明确的拥有者；运行时依据有意义的活动判断停滞，先划清旧请求的输出边界，再决定是否重试。业务会话与 provider 私有会话分开保存，连接和进程则由各自的生命周期所有者回收。这个结构实现的是分层故障处理，不能直接推导出所有执行恰好一次。

## 为什么既共享连接，又给每个会话独立的状态？

### 问题与直观方案

为每个窗口启动一个 CLI，隔离直观，但相同会话的多个窗口可能发起相互冲突的请求，也增加进程数量。反过来，所有窗口共用一个全局队列，某个慢会话会拖住其他会话。真正需要隔离的是“谁能改变这个业务会话”，不只是窗口。

### 当前实现与完整演算

**当前实现**：完整 AgentRef（如 `demo/agent-a`）定位独立 Supervisor。多个 Ora Session 可以共享该 Agent 的 ACP 进程连接，但每个 Session 有串行命令处理者与自己的路由。provider session ID 用于投递，连接 generation 表示属于哪次连接；路由 token 还防止旧处理者删除新路由。

| 时刻 | 共享连接 | 会话 S 的路由 | 会话 T 的路由 | 可观察结果 |
| --- | --- | --- | --- | --- |
| t0 | A，generation=4 | provider-a-001 / token=12 | provider-a-002 / token=13 | 两个会话可分别执行 |
| t1 | 同上 | 普通队列满 | 正常消费 | S 收到独立控制故障，T 无须等待 S |
| t2 | A 的连接断开 | 该代次失效 | 该代次失效 | 同一 Agent 的两会话都受影响 |
| t3 | A，generation=5 | 新注册 token=14 | 按需恢复 | 旧 token=12 的清理不能删掉新路由 |

队列容量是 256，setup 期间尚未拿到 provider ID 的通知也有有界缓冲。队列满时不用阻塞共享 reader 来等待某个会话；故障走独立控制通道，使“队列满了”仍能被告知。连接级有序流本身仍无界，因此单会话有界不等于整条链路内存有界。

SQLite 只保存业务绑定。例如 `sessions(S, agent_cli=demo/agent-a, agent_session_id=provider-a-001, status=0)`；token=12、generation=4、队列长度、正在执行哪条命令是内存状态。重启后不能根据 `status=0` 认定旧连接活着，启动会把残留 Running 校正为 Stopped。

### 连续追问：队列满为什么不把消息丢掉继续？

先回答丢消息的影响：丢掉文字可能只是残缺，丢掉工具完成或响应边界会改变后续状态判断。再追问为何只停 S：因为路由能定位受影响会话，而共享连接仍可能健康。再追问连接流仍无界怎么办：需要总字节预算、按会话公平调度和明确过载策略，不能只把 256 改成 512。

**可能方案**：为连接增加字节预算与每会话配额，记录流量和溢出原因；控制消息预留预算。代价是需要定义大消息拆分及公平性，失败时让责任会话明确失败并保留降级证据，不能悄悄丢弃会影响状态的事件。它解决内存上界，不能解决 provider 本身的无界生成。

## 多久没输出才算停滞？为什么重试之前要确认取消？

### 问题与直观方案

“45 秒没有文字就重试”会误杀一次耗时两分钟的测试。把任何通知都当心跳，又会让不断上报用量、实际上不做事的 Agent 永远不超时。更危险的是发出 cancel 就立即重发：ACP 的流更新没有请求 ID，旧响应可能混入新请求。

### 当前实现与完整演算

**当前实现**：四次尝试的无有效活动窗口依次为 45、60、90、120 秒，也就是最多三次自动重试。正文、思考、计划等推进会重置窗口；用量、模式等会话附属通知不算进展。工具进入 InProgress 时暂停该会话的普通停滞计时，全部运行工具结束后重新计时。重复 Pending 不会无限续命。

| 时刻 | 事件 | 本轮判断 |
| --- | --- | --- |
| 0s | 第一次发送 P | 45s 无活动窗口开始 |
| 20s | 收到正文 | 截止点变为 65s |
| 40s | 工具 read-1 InProgress | 普通停滞窗口暂停 |
| 140s | read-1 Completed | 从此重新给 45s |
| 185s | 仍无有意义活动 | 发送 cancel，等待响应边界 |
| 187s | 在 5s 宽限内得到 Cancelled 响应 | 才允许在同一 provider session 重发 P，窗口 60s |

如果返回正常结束而不是 Cancelled，或宽限内没有完整响应边界，不进入这次自动重发。重试通知先发给 prompt owner；跟随视图看到同一轮的连续内容。用户输入已经记录过，重试不会再追加一条相同用户记录；已有助手输出也不会被自动抹掉。重发使用相同请求块，因此若首次请求携带交接文本，这次请求仍带同样文本，但不会再制造一次新的历史交付债务。

### 连续追问：取消被确认，为什么还可能重复改文件？

确认取消证明旧请求在协议上结束，不证明它没有执行过工具。假设第 180 秒已经向外部服务提交任务，回执还没进入对话；第 187 秒重发可能再次提交。串行、取消 fence、有限重试分别解决乱序、串轮、无限放大，均不提供业务幂等。

**边界与缺口（已确认行为）**：工具 InProgress 可以让普通停滞计时暂停很久；该机制不是工具最长运行时限。重试不是断点续算，也不会回滚已发生的副作用。

**可能方案**：对会产生外部副作用的工具，保存稳定 operation ID、输入摘要、接受状态与结果凭据，让工具端按同一 ID 返回原结果。成本是工具接入合同更复杂；失败时保留 Unknown 并对账，不能用新 ID 绕过去重。对于不能幂等的第三方 API，改为人工确认重试或查询既有业务对象。这和工作流的副作用问题相同，见执行与恢复模块。

## 进程崩了，为什么不能一直自动拉起来？

### 问题、当前选择与反例

直观做法是断线立即重启。若安装包损坏，每次启动都失败，会形成 CPU、日志和子进程风暴；若旧进程还没退出，启动替代品还可能同时占用目录和端口。

**当前实现**：插件生命周期拥有插件进程，插件负责 Agent CLI；运行时只借用 ACP 连接。连接结束时请求停止并回收旧代次，再考虑替代代次；Supervisor 做退避和短时间失败熔断。一分钟内超过三次异常会打开熔断。升级/卸载时另有 suspend 标记阻止 Supervisor 抢先重启，操作结束再恢复协调。

演算：A generation=4 崩溃 → 路由失效 → 停止插件/CLI → 等待退避 → generation=5。若用户同时开始替换包，先标记 A suspended，Supervisor 不再循环拉起旧目录中的进程。磁盘已安装的版本、运行的进程代次与会话已采用的配置必须分别检查。

**边界与缺口**：熔断是进程内状态，不是持久事故数据库；应用重启会重建管理状态。当前权限请求按可用允许项自动响应，不能把会话隔离解释成逐工具人工审批或强沙箱。

**可能方案**：增加持久故障摘要（Agent、版本、最后失败类别、人工解除记录），让坏版本升级后有条件解除熔断。它解决诊断与恢复操作性，代价是迁移和清理；读取失败时保持保守的不可用状态，不能绕过安装完整性校验。

## 完整业务推演：两个会话中一个停滞

1. S、T 的 `sessions` 行已存在，指向同一 Agent 的不同 provider ID；各自 JSONL 保存自己的对话。连接代次与路由只在内存。
2. S 写入用户输入后发请求，T 同时独立执行。S 的工具结束后没有更多进展，触发停滞处理。
3. S 等到旧请求 Cancelled fence 后重发，T 不因此重发。SQLite 绑定不变，S 的历史仍只有一个原始用户输入，但可能出现多段尝试输出。
4. 若整个连接随后损坏，S、T 都失去该代次。历史中已有稳定条目可读；尚未稳定的片段可能没有落盘。
5. 再次发送时按需恢复 provider；恢复不了则重建并交接 Ora 历史。重启并不自动继续上次未完成 prompt。

跨 SQLite、JSONL、provider 的步骤不存在统一事务。判断事故时分别问：业务绑定是什么、哪些内容已保存、外部执行是否已发生、响应边界是否完整。
