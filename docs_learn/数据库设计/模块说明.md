## 面试官问“你设计了哪些表”，应该从哪个业务承诺回答？

如果回答只有 54 张表和字段名，仍解释不了为什么删除任务后清理不能丢、为什么 Agent 换绑和历史写入会不一致、为什么节点成功必须连结果一起提交。本章从这些承诺倒推存储边界，字段全集放在文末查证。

整体设计：Desktop 的 SQLite 保存结构化身份、状态和需要跨重启承担的责任；长对话、技能包、Git 与安装产物保留各自介质。事务只保护同一数据库内的变化，跨介质用 journal、清理任务、冻结操作与回执处理。约束分数据库硬约束和业务规则，不能混为一谈。

## 为什么不把所有内容都塞进 sessions 一张表？

### 当前实现与存储决策

把所有消息、模型、工具、文件和进程状态都塞一个 JSON，最初写得快，但身份、可变性、访问模式与恢复责任不同。**当前实现**：

| 事实 | 位置 | 原因及更新时点 |
| --- | --- | --- |
| Session 身份、Workspace、绑定、MCP 选择、降级原因 | sessions | 创建/换绑/状态修改时小范围更新 |
| 对话消息、工具快照、结束/交接记录 | sessions 下 JSONL | 流式合并后追加，按 seq 回放 |
| Workflow 身份/定义/执行 | workflows、workflow_snapshots、workflow_runs、workflow_node_runs、scope 表 | 编辑、发布、运行分生命周期 |
| 技能目录与角色正文 | skills、agents | 技能正文另在包中，角色正文在 content |
| Git 工作树与回收责任 | worktrees、leases、cleanup_jobs | 固定基线、创建前预留、删除时保存清理 |
| 技能交付期望/操作/回执 | effect_* | 每次外部变更前后保存责任 |
| MCP 凭据、插件值 | store.json | 不进入业务 SQLite |
| 已装插件/更新包/代码 | 验证后的磁盘与 Git | 表不伪装完整文件库存 |

**可能方案**：消息迁到关系表可获得索引和更强事务组合，但需设计稳定消息身份、修正版本、分块大对象和保留政策。成本是迁移/写放大/索引维护；写失败仍需停止无记录执行，不能只是换介质就忽略恢复。是否值得，取决于分页、检索、跨设备需求，而非“数据库一定更高级”。

## 哪些更新必须同事务，哪些做不到？

### 当前实现与三组演算

**例一：任务删除与清理责任。** 同事务把 T/W 软删并插入 J pending。事务前都没有发生，提交后都发生。Git 物理删除在事务外；数据库成功不代表磁盘已释放。

**例二：节点完成与结果变量。** 完成 NB、保存输出/分支决定一起提交。下游不会读到本事务产生的“成功但没结果”。但 NB 调外部 API 的成功不在此事务内，重试仍需业务幂等。

**例三：Agent 换绑与 JSONL。** `sessions` 变为 B/B1，随后历史追加 switch 记录不是同一事务。崩溃可能只留下新绑定，重启不能凭空补出确认。未来若需要更强恢复，要持久切换操作或 outbox，并明确接收端去重。

| 失败窗口 | 能保住什么 | 仍需处理什么 |
| --- | --- | --- |
| SQLite 事务未提交 | 相关行不部分可见 | 外部已经发生的操作 |
| 已提交，响应丢失 | 库内事实存在 | 客户端查询/请求去重 |
| 文件已变，操作 phase 未更新 | Prepared 意图与 artifact | 对账，不能猜没发生 |
| 业务软删，清理失败 | pending job | 后台重试/人工处理 |

**可能方案**：需要可靠通知时使用同事务 outbox，保存事件 ID、对象版本和负载，提交后投递；代价是额外表/清理和消费者去重。投递失败重放原事件，不换 ID；它解决不丢责任，不把所有外部调用变成 exactly-once。

## 外键、唯一索引和业务校验各自保证什么？

### 当前实现与反例

`workspace_id` 外键保证目标行存在，不保证目标未软删；部分唯一索引保证一个项目只有一个可见 main，不说明目录已准备好。`workflow_snapshots.graph` 是 JSON 文本，SQL 不理解画布每条边；发布指针也有业务维护而无同等物理外键的情况。

| 约束 | 当前例子 | 不能扩大的结论 |
| --- | --- | --- |
| 外键 | sessions.workspace_id→workspaces.id | 工作区此刻可执行 |
| 部分唯一索引 | active project main；active namespace/name | 任意软删记录不再影响任何业务 |
| CHECK | Effect ready≤applied≤observed≤desired | 文件已真实修改或消费者真实采用 |
| 触发器 | Loop 当前根/活跃轮归属检查 | 所有未知 JSON 合同都已验证 |
| 仓储校验 | 发布/激活归属，状态转移 | 手工 SQL 同样安全 |

Session 标题、状态、绑定、历史健康分别更新拥有的列，避免过期整行快照覆盖别人刚改的标题。时间戳不是并发版本：两次操作可同毫秒，时钟也会回退；Effect 的 generation/fence 与时间分开。

### 连续追问：为什么不全交给数据库触发器？

触发器适合稳定局部约束，图可执行性、provider 能力和文件归属不能只靠 SQL。全部塞触发器会让业务错误与跨介质操作难解释。**可能方案**：加强缺失的局部关系约束，同时保留领域校验；新增外键前先扫描历史数据，迁移遇到坏引用拒绝或隔离，不能默默删数据“修复”。成本是迁移复杂和性能，收益要对应真实风险。

## WAL、连接池与迁移能保证什么？

### 当前实现

Desktop repository 连接统一开启外键、WAL、5 秒 busy timeout、NORMAL 同步。WAL 让读写协作更好，不意味着多个 writer 可同时随意修改；慢 Git/复制不应占住写事务。NORMAL 不保证物理断电后最后一次提交一定保留。

迁移版本为 0001–0014，`migrations(version,up_sql,down_sql,executed_at)` 保存实际执行 SQL 快照，每步 DDL 与版本记账同事务。启动按版本序列对齐；开发显式 reconciliation 才比较 SQL 漂移并重建变化后缀。不能修改旧迁移后期待普通启动自动重做，也不能任意使用今天的 down SQL 回退昨天的结构。

| 版本 | 关键变化 |
| --- | --- |
| 0001–0004 | 项目/工作区/会话，Skill/角色，工作流，Git lease/job |
| 0005–0009 | 市场来源、Effect、来源 namespace、enabled、artifact_retrieval |
| 0010 | Effect 恢复发现时间、移除自动建 Scope 触发器 |
| 0011 | sessions.mcp_selection，历史行默认显式空集合 |
| 0012 | NodeRun.iteration（foreach 从 0 开始） |
| 0013 | Loop scopes、当前根指针、降级归档及归属约束 |
| 0014 | 扩展包安装与成员 ownership |

已有特定旧 Loop 编号接纳逻辑按精确快照识别，不是任意旧数据库自动兼容。0013 降级时保留 scope 归档并处理旧版本无法执行的运行，回退不等于让新特性继续可运行。

### 连续追问：换 FULL 就可以保证产品恢复吗？

更强同步只影响提交耐久，不补全缺失的业务证据，也不统一文件/Git/provider 事务。**可能方案**：按数据重要性选择同步配置并做真实故障验收，记录被确认接受的操作与恢复结果。成本是写延迟；平台/文件系统不满足要求应明确拒绝或降低宣称，不用性能测试冒充断电测试。

## 同一仓库里的 Node 数据库为什么不计入这 54 张表？

54 张表指 `ora-db` 的 Desktop `ora.sqlite3`，不是整个仓库所有 SQLite 文件。Node、Controller、Host、Guardian 有独立持久权威与 schema；不能将它们的 FULL 配置反套 Desktop NORMAL，也不能将 Desktop schema 迁移写进 Host journal。

当前 Node `ora-node.sqlite3` 保存 node_metadata、executions、resources、outbox、managed_executions、process_attempts、execution_identities、clone_executions、clone_outbox、process_outcomes、controller_binding、execution_controllers 等。精确字段/版本由 Node 数据所有者定义，见本章来源链接；本章附录不把这些表伪装成 Desktop 主库。Controller 结果接管与 receipt、Host 的 Scope/Run 意图、Guardian 的进程证据分别承担不同责任，详见系统架构。

## 完整业务推演：一个跨表约束失败

新 Run R 插入后，触发器建立根 scope ROOT1 及当前根指针。创建 NodeRun N 时 scope 必须属于同一 Run 的合法执行区域；另一个 Run 的 scope 不能混入。复合执行的新轮另建 scope，历史 scope 保留。续跑更换当前执行依据后，旧回调不能只拿 node_id 命中新尝试。

如果事务失败，节点与对应库内事实不部分提交；若 Agent 在事务前后已经产生外部行为，恢复仍查 Session/操作证据。不要把一个强外键案例扩大成整个系统强一致。
