## 从一件具体的事开始

你让 Agent A 检查一个商城项目：

> 修复重复重试，最多重试两次，不改变公开接口。

Agent 一边分段回复，一边读取文件。你能看到文字不断增长，工具从“正在执行”变成“完成”。此时如果关掉页面，再次打开应该看到什么？如果 Agent A 被卸载，你是否还应该能读到这段对话？如果接下来换 Agent B，它又应该知道哪些事情？

这些问题要求我们先把三件事分开：

| 对象 | 它回答的问题 | 存在多久 |
| --- | --- | --- |
| 页面上正在变化的内容 | 此刻用户看到了什么？ | 页面或运行时可以消失 |
| Ora 保存的对话记录 | 这段对话留下了哪些可读取的事实？ | 保存到磁盘，独立于某个 Agent 存活 |
| Agent 自己的上下文 | 这个执行者下一次回答时能使用什么？ | 由对应 Agent 管理，Ora 不能当作自己的完整记录 |

**可以这样口头介绍整体设计：** Ora 自己保存会话身份和对话内容。身份、归属、当前 Agent 等结构化信息放在数据库；对话内容按条目追加到会话文件。实时片段先整理成消息或工具状态，再写入。每条内容还带着它在对话中的位置，因此即使完成顺序不同，重新打开时也能恢复合理顺序。保存失败会显式标记缺口；这套记录能脱离原 Agent 阅读，也能作为换 Agent 时的交接来源。

这段介绍只是地图。下面逐个检查：为什么需要这些决定，它们有什么代价。

## 决策一：为什么对话不能完全交给 Agent 自己保存？

### 最直观的做法为什么有吸引力

Agent 通常已经有自己的会话。Ora 如果只记住它的会话编号，下次再找它要历史，似乎可以少存一份数据，也不用维护消息格式。

这相当于用户把所有档案放在某个执行者手里。只要它始终在线、始终支持同样的读取方式，方案可能成立。但产品允许卸载、升级和切换 Agent：用户的对话就不能因此一起失去访问入口。

此外，Agent 返回的历史不一定包含 Ora 需要表达的全部事实。例如，“这一轮被用户取消了”“这段对话曾切换到另一个 Agent”“某次写入失败导致部分内容缺失”，属于 Ora 自己必须记录的事情。

### 当前实现：把“对话属于谁”和“谁正在执行”分开

Ora 给这段对话一个稳定编号。用户换执行者时，这个编号继续存在；Agent 的内部会话编号只表示当前执行关系。打开历史时读 Ora 文件，不要求 Agent 先恢复运行。

本章固定使用以下身份，后文用 S、W、A1 作为简称：

| 简称 | 实际示例值 | 含义 |
| --- | --- | --- |
| S | `a1b2c3d4-1111-4111-8111-123456789abc` | Ora 对话编号 |
| W | `b1c2d3e4-2222-4222-8222-123456789abc` | 这段对话工作的工作区 |
| Agent A | `demo/agent-a` | 当前提供执行能力的 Agent 身份 |
| A1 | `provider-a-001` | Agent A 内部的这一次会话 |

这里的工作区表示实际执行环境；它不是对话编号，也不是 Agent 的内部编号。用户可以在同一个工作区建立多段对话。

### 数据到底放在哪里

`sessions` 表中有这样一行。下表使用“字段—值”展开，便于逐项阅读；它表示一行记录，不是多行数据库数据。

| 实际字段 | 示例值 | 为什么需要保存 |
| --- | --- | --- |
| `id` | S 的完整编号 | 重新打开、重命名和切换时仍能找到同一段对话 |
| `workspace_id` | W 的完整编号 | 知道任务在哪个执行环境中进行 |
| `title` | 修复重复重试 | 用户可见名称，不能拿它当唯一身份 |
| `agent_cli` | `demo/agent-a` | 当前由哪个 Agent 执行；字段名沿用实现命名 |
| `agent_session_id` | `provider-a-001` | 找到该 Agent 内部的会话 |
| `history_degraded_reason` | NULL | 当前没有记录到历史写入降级原因 |
| `status` | `0` | 当前为 Running，表示运行绑定，不等于每时每刻都在回复 |
| `created_at` | `1789005600000` | 创建时间，epoch 毫秒 |
| `updated_at` | `1789005600000` | 最近数据库更新的时间，epoch 毫秒 |
| `is_deleted` | `0` | 普通列表中仍可见 |

示例时间对应北京时间 2026-09-10 10:00。表里**没有消息正文列**，也没有单独的 `messages` 表。

正文保存在：

`<应用数据目录>/sessions/a1/b2/a1b2c3d4-1111-4111-8111-123456789abc.jsonl`

`a1`、`b2` 取自会话编号开头，用来分散目录中的文件数量。路径可以从编号确定，所以表里不再存一个独立路径，避免编号和路径各说各话。JSONL 表示每一行都是一条完整的 JSON 记录，新增记录通常追加在末尾。

**边界与缺口：** 双存储带来新的责任。数据库中的会话行和文件内容不在一个共同事务中，也就是没有一次提交能让两者同时成功或同时回退。备份一份数据库拿不到正文；删除行成功也不保证文件一定删除成功。这是换取独立历史所有权后的维护成本。

### 这一决定会怎样被追问

**问：那为什么不把正文也放进 SQLite，顺便解决双存储问题？**

这是合理的替代方案。正文落表更容易按消息查询，也能把某些元数据和消息修改放进一个数据库事务。不能回答“对话天生就不能存数据库”。

当前选择文件，采用按会话追加、再整段回读的访问方式，保存了协议里的结构化内容。但如果未来需要跨会话全文搜索、逐条编辑、长期审计，应重新比较两种存储方式。把正文迁到表里也不会自动让 Agent 的外部执行与数据库原子提交。

**继续问：既然自己存了，能不能称为拥有 Agent 的全部记忆？**

不能。Ora 保存的是自己观察并选择记录的对话信息。Agent 的内部状态、未发出来的信息、已经丢失的片段，不会因为有 JSONL 就自动出现。完整文件也不保证新 Agent 接收到同样完整的上下文，下一章会说明交接时又做了哪些取舍。

## 决策二：实时文字应该每来一个片段就存，还是等整轮结束再存？

### 两个简单方案各有什么问题

假设 Agent 想显示“我先检查重试逻辑。”，实际分两次送来“我先检查”和“重试逻辑。”。

每个片段都原样写入，可以较早留下证据，但读取时必须再次理解并合并这些片段。工具状态可能还经历“等待—执行—完成—补充结果”，一个逻辑条目会出现很多网络更新。原始事件档案是可行方案，但它需要明确的回放规则与格式演进策略。

全部等到整轮结束再保存，则把过多信息留在内存。即使 Agent 已经输出了很多内容，最后一秒进程退出，也可能丢掉整轮尚未写出的信息。

### 当前实现：保存已经能够整理出来的条目

系统维护一份暂存区：某条回复目前累积了哪些文字，某个工具目前是什么状态。它不把每个网络片段都当作一条独立聊天消息。

判断依据来自事件的身份和边界，而不是“等两秒没文字就算完成”：

| 收到的情况 | 如何理解 | 保存动作 |
| --- | --- | --- |
| 同一种文字流、相同消息编号又来一个文字片段 | 原消息还在增长 | 合并到暂存文字 |
| 同一种文字流出现新的消息编号 | 前一条有编号消息的边界已经出现 | 保存前一条，暂存新一条 |
| 没有消息编号的连续文字中插入一个独立工具等条目 | 连续文字被打断，不能把后续回复都接到前面 | 整理被打断的无编号文字 |
| 有明确消息编号的文字中穿插工具事件 | 相同编号仍可表明文字属于同一条 | 工具事件不会仅因穿插就强制拆开这条文字 |
| 工具报告完成或失败 | 已有可保存的结果状态 | 保存工具当前快照 |
| 一轮结束 | 剩余暂存内容也需要留下记录 | 保存剩余条目，再保存本轮结束原因 |

这里的“快照”指条目在某一时点的完整状态，不只是这次改变了哪个字段。“已经能够整理”也不等于未来绝不会收到更正。工具完成后仍可能补充信息；系统允许再保存一个新版本，后面会展开。

用户自己的消息也有一个特别处理：使用 Ora 接到的用户内容记录一次，不再把 Agent 回显的用户消息重复记一次。否则下一章加入的交接文本可能被回显后再次存入历史，越交接越膨胀。

### 本案例的前半段

先把顺序编号称为 `seq`：它是**条目第一次进入对话时得到的位置**，不是消息编号、工具编号或文件行号。整段会话持续编号，下一轮不会重新从零开始。

| 步骤 | 收到的事情 | 暂存区变化 | 本步追加到文件 |
| --- | --- | --- | --- |
| T0 | 建立 Ora 历史 | 为会话说明保留位置 0 | `seq=0` 的 Meta，记录初始身份 |
| T1 | 用户提交修复要求 | 用户内容取得位置 1 | `seq=1` 的用户消息 |
| T2 | 回复 m1：“我先检查” | m1 在位置 2，正文暂为“我先检查” | 无 |
| T3 | 回复 m1：“重试逻辑。” | 同一条位置 2，正文合成完整句子 | 无 |
| T4 | 工具 read-1 开始读取文件 | 工具取得位置 3，尚在执行 | 无；m1 有明确编号，仍暂存 |
| T5 | 回复 m2：“我会保持公开接口不变。” | m1 结束；m2 取得位置 4 | `seq=2` 的完整 m1 |

注意 T3 和 T5 的区别：一句话在自然语言上似乎完整了，不等于协议已经宣布消息边界。保存依据是可观察的结构，不能靠标点猜 Agent 是否还会接着说。

**连续追问：同样的文字接连出现两次，要不要去重？**

不能只比较文字。用户可能真的提出了两次同样要求；工具也可能执行了两次同样的命令。消息编号和条目位置用于判断“这是旧条目的继续”还是“新发生的事情”。内容相同并不足以说明身份相同。

**继续追问：Agent 没提供消息编号，你是不是就无法工作？**

当前用连续性和中间事件作为较弱的边界证据。有明确身份时使用明确身份，没有时采用有限的推断。这种降级支持不同 Agent，但也提醒我们：输入协议提供的信息越少，宿主能作出的精确判断就越有限。

## 决策三：为什么先发生的内容，会比后发生的内容更晚写入？

### 先把三种顺序分开

**出现顺序**决定一条内容在对话中的位置；**完成顺序**决定何时有可保存的状态；**物理写入顺序**是文件末尾实际增加行的顺序。它们并不天然相同。

读取文件的工具可能持续很久，但 Agent 在等待时已发出下一条说明。如果强迫所有条目严格按出现顺序写入，就必须让已完成的后续消息继续等工具。进程在等待期间退出，那些本来可以保存的消息也会一起丢失。

当前实现允许先保存后完成的消息，再用先前分配的位置恢复逻辑顺序。`seq` 正是把“何时写”与“应该出现在哪儿”分开的证据。

### 接着走完刚才的案例

| 步骤 | 收到的事情 | 暂存区变化 | 本步追加到文件 |
| --- | --- | --- | --- |
| T6 | 新回复 m3：“读取结束后，” | m2 整理完毕；m3 取得位置 5；工具仍在位置 3 | `seq=4` 的 m2 |
| T7 | read-1 报告读取完成 | 工具位置仍为 3，状态更新为 completed | `seq=3` 的工具快照 |
| T8 | read-1 补充标题“读取 src/retry.ts（确认版本）” | 仍是同一次工具调用，没有新分配位置 | 再追加一条 `seq=3`，带补充后的完整快照 |
| T9 | m3 继续：“已定位重复调用，下一步补充回归验证。” | 合并到位置 5；本轮正常结束 | `seq=5` 的完整 m3，然后 `seq=6` 的本轮结束记录 |

整个文件此时按物理行序排列如下：

| 文件中的行序 | 实际 `seq` | 类型 | 主要内容 |
| --- | --- | --- | --- |
| 1 | 0 | `meta` | S、W、Agent A 和 A1 的初始关系 |
| 2 | 1 | `update` | 用户要求：修复重复重试，最多重试两次，不改变公开接口 |
| 3 | 2 | `update` | m1：我先检查重试逻辑。 |
| 4 | 4 | `update` | m2：我会保持公开接口不变。 |
| 5 | 3 | `update` | read-1：读取 src/retry.ts，completed |
| 6 | 3 | `update` | read-1：读取 src/retry.ts（确认版本），completed |
| 7 | 5 | `update` | m3：读取结束后，已定位重复调用，下一步补充回归验证。 |
| 8 | 6 | `turnEnded` | 本轮由 Agent 正常结束 |

这张表中的内容是文件记录的阅读投影。下面两行展示实际 JSONL 数据形状；它们是数据样本，不需要记住字段拼写。示例时钟固定，所以时间相同，不表示所有实际事件同时发生。

```jsonl
{"at":"2026-09-10T10:00:00+08:00","seq":2,"type":"update","update":{"sessionUpdate":"agent_message_chunk","content":{"type":"text","text":"我先检查重试逻辑。"},"messageId":"m1"}}
{"at":"2026-09-10T10:00:00+08:00","seq":3,"type":"update","update":{"sessionUpdate":"tool_call","toolCallId":"read-1","title":"读取 src/retry.ts（确认版本）","status":"completed"}}
```

外层 `type=update` 表示一条对话内容；里面 `sessionUpdate=agent_message_chunk` 是协议的内容类型名称。**即使名称带 chunk，这里已经存的是合并后的文字**，不能仅凭类型名称误以为文件仍是原始网络碎片。

### 同一位置写了两次，为什么不会显示两次工具？

读取时先确定每个位置最后保存的版本，再按位置排序。例子中两条 `seq=3` 是一个条目的两个快照，最后那条替换前一条用于回放。于是逻辑内容顺序为 `1 → 2 → 3 → 4 → 5`，另有位置 0 的身份记录和位置 6 的结束边界。

身份记录不显示成聊天气泡。重复快照也不会变成两次工具调用。物理文件仍保留两条记录，但普通回放只展示最终版本；如果要做所有中间变更的审计，就需要另一种读取方式，不能把普通回放当完整事件审计。

**问：直接回头修改原来的工具行，不就没有重复了？**

可以设计成可更新的存储。问题是一个较长的新快照未必能塞进原行的位置，原地修改还要处理半写覆盖和读写冲突。追加更正让日常写入保持简单，代价是文件增长和读取时去重。两者是取舍，不能说追加方案完全没有成本。

**继续问：出现 completed 就能保证工具真的成功了吗？**

历史只能保存系统观察到的结果。Agent 明确报告失败时不会被改成成功；但当前还存在一个值得说明的推断：正常结束一轮时，如果某个工具仍未报告终态，整理逻辑会把未结束工具记为 completed。取消或其他提前结束则保留未完成状态，用本轮结束原因补充说明。

这意味着部分 completed 来自“正常结束一轮”的推断，而不是独立工具成功回执。后续若要严格审计外部副作用，应额外区分“观察到成功”和“根据会话结束推定完成”。这是改进方向，不是当前已有的证明能力。

## 决策四：正在生成时重新打开，怎样既不漏内容又不重复？

### 只读文件为什么还不够

在 T6 后重新打开，文件里有位置 0、1、2、4。工具位置 3 仍在内存，位置 5 的文字也只出现了一部分。如果只读文件，新打开的页面就会缺少这些正在进行的内容。

但如果文件还在增长，读取历史后再随便接实时事件，也会产生另一个问题：某条消息可能被历史读到，又从实时通道收到；也可能恰好落在两个步骤之间，哪边都没拿到。

### 当前实现：选择一个明确的衔接点

有活跃会话时，由拥有这段会话处理权的运行对象安排加载。可以把它理解成这段对话的唯一值班员：它知道哪些内容已写进文件，哪些尚在整理，也负责后续实时变化。

它在加载衔接点提供三部分信息：

1. 已经写入的文件截止位置。这里按字节数划边界，不是“读到最大的 seq”；因为较小 seq 可能晚写。
2. 这个时点仍在内存的条目快照，带原来的位置。
3. 衔接点之后继续发生的实时变化和本轮结束边界。

以 T6 为截面，回放先合并文件中的 0、1、2、4 与内存中的 3、5，按位置恢复，再继续接 T7 之后的更新。工具已经写入过后不会再被当作尚未落盘条目重复加入前缀。

没有活跃运行对象时，读取就是一次有限的文件回放，不访问 Agent，也不会为看一眼历史创建新的 Agent 会话。

### 连续追问：两个页面都打开，谁拥有正在进行的任务？

一个页面发起执行，其他页面可以跟随。关闭跟随页面只取消它自己的阅读，不应取消原来的任务。跟随页面消费太慢时也不能拖住执行者；当前会在超出缓冲能力后给该视图显式错误，而不是无限堆积。

如果改成“所有页面都必须确认收到每条事件才能继续执行”，就会让一个卡住的页面阻塞 Agent。更可靠的观察通常依赖可重读的事实，加上明确的实时衔接，而不是要求所有观察者一直在线。

**边界与缺口：** 内存条目快照能帮助活跃期间重新打开，不能抵抗整个进程退出。T6 时退出，尚未写入的工具状态和 m3 片段仍可能丢失。应该把“页面关闭后可恢复”与“进程或机器故障后全部恢复”分开回答。

## 决策五：保存失败之后，还应该继续让 Agent 工作吗？

### 必须分清失败发生在哪个时点

如果用户这一轮尚未发给 Agent，先保存用户内容就失败了，系统可以拒绝开始，避免一开始就产生没有记录的任务。

如果 Agent 已经在执行，期间记录失败，不能假装已经发生的外部工作没发生。当前允许进行中的轮次收尾，同时停止继续记录，标记历史降级，拒绝后续新轮次；修复后再显式恢复历史保存。

这不是“保存失败就重新请求 Agent 一次”。重发可能让文件修改、命令执行等副作用重复发生。

### 数据怎样表达“这段记录不完整”

| 阶段 | `sessions.history_degraded_reason` | 历史文件 | 后续发送 |
| --- | --- | --- | --- |
| 正常 | NULL | 持续追加 | 可以 |
| 写入失败 | 例如 `no space left on device` | 留下失败前成功写入的内容，失败写入还可能留下尾部碎片 | 拒绝新的 prompt |
| 修复存储后申请恢复 | 只有恢复处理成功后才回到可写状态 | 先尝试追加 `gap`，说明此前未记录内容的原因 | 成功恢复后才继续 |

`gap` 不能把丢掉的文字补回来。它的价值是让用户和后续 Agent 知道记录有缺口，避免把残缺记录误当作连续完整的经过。

还有第二层失败：保存降级原因到 SQLite 本身也可能失败。当前会保留内存降级状态并告警；不能宣称“数据库一定已知道本次文件写失败”。这是双存储都出问题时的边界。

### 不同故障需要不同判断

| 故障 | 当前如何看待 | 能保留什么／不能保证什么 |
| --- | --- | --- |
| 最后一行没写完，且无法解码 | 读取时忽略未完成尾部，不按完整坏行计数 | 保留此前完整记录；被截断内容无法恢复 |
| 中间有一条完整行无法解码 | 标记历史损坏，向读者提示不可读取的记录数量 | 可以展示其他记录，但不知道损坏内容原来具体占什么位置 |
| 文件整体无法读取 | 无法安全知道已有编号，记录器降级 | 不能盲目从零继续编号，以免把新内容当旧位置的更正 |
| 文件完全不存在 | 当前读取视为空历史 | 兼容尚无文件的会话，也意味着不能单靠缺文件区分“从未记录”与“被意外删掉” |
| 磁盘写失败 | 停止记录并进入降级流程 | 已经执行的外部动作不会自动回滚 |
| 机器断电 | 最近写入可能丢失 | 当前写入完成后，没有逐批等待存储介质持久化确认的保障 |
| 删除数据库记录后，文件删除失败 | 记录警告，删除文件是尽力处理 | 文件可能残留；普通列表不再可见不等于物理数据已彻底清除 |

**继续追问：能忽略半截尾行，就代表下次追加一定安全吗？**

不能这样推导。容错读取和修复文件尾部是两件事。当前 writer 追加时没有先截掉未完成尾部的独立步骤；如果旧尾部没有换行，新的记录可能接在碎片后面，使这一整行无法解析。这里是根据读写顺序识别的风险，本样章没有做这条崩溃恢复故障注入。

可能的修复是：在唯一写入者恢复时定位最后一个有效记录边界，先隔离坏尾部，再决定截断或补救并记录缺口。这要在新写入开始前完成，并确保不能与另一个写入者并发修复。只给 reader 加“忽略错误”无法替代这个过程。

## 把完整业务再走一遍

下面串联正常路径，不把已保存内容误当作业务工作已完成：

1. **会话建立。** 在 `sessions` 保存 S→W、Agent A→A1 等元数据；历史文件写 Meta。数据库和文件不是同一个事务。
2. **用户发送。** 用户要求作为位置 1 保存，再进入 Agent 执行过程。记录的是原用户内容，交接等宿主附加内容不会重复混成一轮用户原话。
3. **流式输出。** 页面可以不断收到变化；合并器按消息和工具身份整理，位置 2、3、4、5 分别代表不同条目。
4. **条目追加。** 出现位置不决定谁先落盘；本例实际写入位置顺序为 `0,1,2,4,3,3,5,6`。
5. **一轮结束。** 位置 6 保存结束原因；它说明这一轮结束，不证明用户要求的整个修复工作已经验收。示例回复只说“已定位，下一步补验证”。
6. **重新打开。** 每个位置保留最后版本再排序；显示回复和工具，身份及交接记账记录不显示成消息气泡。
7. **继续或换 Agent。** 历史下一位置是 7。下一章从这里追加切换事实；原文件不会因换 Agent 而改名。

此过程中，不会为每个文字片段新建一行 `sessions`，也不会每收到一个 chunk 就更新会话表。对话正文变化与会话元数据更新具有不同频率。

## 可能方案：历史更大、要求更严时，哪些设计要重新考虑？

以下均为未实现的设计推演，不能在面试里说成已经上线。

### 方案一：保留追加记录，增加可重建的索引

**问题：** 当前 reader 整体读取文件，历史越长，读取、解码、排序的时间与内存成本越大。

**做法：** 给完整文件建立分段和位置索引，记录某一代文件中哪些字节段覆盖哪些条目。这里“文件代次”是整份文件被重新整理后使用的版本标识，防止拿旧文件的位置索引读取新文件。普通打开可以先读取近期部分，向前翻阅时再加载。因为旧位置可能在末尾更新，索引还需要知道每个位置的最新记录在哪儿，不能只记“某个范围第一次出现在哪儿”。

**新信息示意，不是当前表：** `会话=S，文件代次=2，已索引到字节=某边界，位置3最新记录偏移=某位置`。这个索引是派生缓存，原记录仍是依据。

**代价与失败：** 增加维护和校验成本。索引没及时写完时，先验证它匹配文件代次，再从已确认边界补扫；发现不一致则重新建立。不能让损坏的索引把正文永久藏起来。

### 方案二：给耐久性设置明确档位

**问题：** 用户对“进程退出”和“机器断电”的可接受损失可能不同。

**做法：** 可考虑在轮次结束或关键交接边界强制同步，而普通片段合并后批量同步。要先定义承诺，例如“已确认结束的轮次”需要达到哪一级耐久性。

**新信息与代价：** 若界面要展示“已保存”与“已强制同步”的差别，需要独立确认位置，不能把当前写入字节边界直接当作断电安全边界。更强同步增加等待与存储开销，仍需结合操作系统与介质能力，不声称解决所有硬件故障。

**失败处理：** 强制同步失败不能继续展示超出实际保障的成功状态；保留最后确认位置，明确告知尚未达到承诺的范围。

### 方案三：把正文与绑定放入同一数据库

**问题：** 降低元数据和正文之间的跨存储窗口，并支持更细的查询。

**做法：** 可以设计消息版本表，把会话、位置、版本及内容关联；例如“会话 S，位置 3，版本 2，读取工具最新快照”。这不是当前已有表，也不意味着必须采用。

**代价与失败：** 需要迁移历史、设计索引、评估写竞争与容量，还要决定保留所有版本还是只留最终版本。数据库事务能改善本地状态一致性，依旧无法包住 Agent 的外部工作。迁移中断时需要可恢复的进度和校验，不能在尚未验证导入完整前删原文件。

### 追问链一：你说“用户看到了，所以肯定保存了”

页面已经显示完整回复，此时进程退出。重新打开少了一段。是不是一定是数据库丢数据？如果加上每条记录强制同步就全部解决了吗？

<details>
<summary>展开分析提示与参考思路</summary>

先确定“看到”的内容在哪一层：可能仍是暂存消息，也可能已经追加到文件。会话表不存正文，所以不能一上来归因于数据库。再区分页面退出、进程退出、机器断电，三者对内存和磁盘的影响不同。

强制同步只对已经提交给文件写入的内容有意义，不能保存仍未交给 writer 的片段。需要沿“收到事件—合并暂存—追加成功—同步确认—页面展示”检查实际顺序和承诺。可以在每个阶段制造中断，观察能恢复的范围，而不是只测试正常关闭后重开。

</details>

### 追问链二：你说“按 seq 排序就行”

两个工具内容相同要不要合并？同一个工具有两条相同 seq 的记录怎么办？如果后来要统计中间失败过几次，普通回放结果够不够？

<details>
<summary>展开分析提示与参考思路</summary>

先区分身份与内容：不同工具调用可以内容一样；同一次调用才沿用原位置。重复位置先选最后版本，再排序。这个读取结果服务于最终对话展示，较早快照已被折叠，不能用它准确统计全部中间变更。

如果需要审计，必须明确统计口径，并保留／读取原始版本变化。验证案例至少包含不同身份的同内容工具、同身份的多次更新、乱序追加，以及重复位置更新后的最终回放。

</details>

### 追问链三：保存失败，要不要自动重试整轮？

用户消息记录成功了，Agent 已修改文件，后面的回复记录失败。重试原 prompt 能否把历史“补全”？

<details>
<summary>展开分析提示与参考思路</summary>

不能把重做业务当成补写记录。外部文件可能已经被修改，再执行可能重复产生副作用。先保留可证明的记录，标出缺口，恢复存储；需要了解实际工作结果时，检查当前工作区并与已知基线比较，但不要伪造丢失的原话。

更强方案可以把业务操作设计成可识别、可查询、可幂等重试，但那需要执行对象提供相应证据。JSONL 本身不是外部操作的事务管理器。

</details>

### 追问链四：准备换 Agent，文件“完整”就够了吗？

文件所有行都能解析、顺序也正确。能否说明新 Agent 能继续原任务？

<details>
<summary>展开分析提示与参考思路</summary>

还需要检查交接选择保留了什么、目标模型是否容纳得下、关键约束是否进入请求、目标是否接受处理。文件存在与可解析，只解决历史存储的一部分问题。当前交接还会省略工具输入输出、推理和计划，图片等也只留下文字标记。
