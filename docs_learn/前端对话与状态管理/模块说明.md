## 界面出现了一条消息，它是否已经被保存？

用户切换会话、流式回答仍在到达；首次发送后草稿需要变为真实会话；网络恢复后又收到标题更新。这些状态不能简单塞进一个“messages 数组”。

整体设计：后端业务事实由前端数据所有者查询/采用，未发送输入由草稿管理，进行中的消息由流状态维护。每一份状态有明确身份和生命周期；失效事件通知重查，不能充当持久数据库。

## 草稿为什么需要结构化内容和独立身份？

### 当前实现与完整演算

只存输入框纯文本，会丢失文件、Skill、Command 引用的结构；把草稿直接当 Session，又提前创建后端资源。**当前实现**：草稿按 conversation key 隔离，编辑器 JSON 与文本一起保存，首次发送后 rekey 到真实会话。localStorage 写入防抖、跳过相同内容、生命周期 flush，失败保留待写；损坏缓存按 cache miss 恢复。图片字节只在内存。

| 阶段 | 客户端 | 后端 |
| --- | --- | --- |
| 输入中 | 草稿 key=D1，文本+引用结构 | 无 S1 行/无 provider |
| 发送准备 | pending Agent/模型意图 | 创建实际 Session |
| 创建成功 | 采用后端 S1，草稿关联转 S1 | sessions(S1) 已保存 |
| prompt 接纳 | 展示用户轮次/响应流 | JSONL 保存输入与稳定更新 |
| 刷新页面 | localStorage 恢复未发草稿 | 已发内容从 history 回放 |

**边界与缺口**：关闭/崩溃前尚未 flush 的防抖写入可能丢失；图片不能因文本草稿恢复就自动恢复。localStorage 不跨客户端，也不能用作已发送正文唯一记录。

连续追问“为什么先清草稿再发送不行”：失败会丢用户意图；成功响应/明确接纳边界后再处理更可解释。**可能方案**：为发送意图保存本地 outbox、稳定 request ID 和附件引用，后端配合去重；成本是附件持久化与过期清理。缺后端去重时不要自动重发“可能已成功”的输入，否则可能执行两遍。

## 为什么广播只通知失效，而不直接覆盖缓存？

### 场景与当前实现

S 标题先改 A，再改 B；两个响应乱序回来，旧 A 若无条件写进 UI，会覆盖 B。另一个窗口还可能漏掉事件。

**当前实现**：`state/data` 的领域所有者管理查询身份、权威响应采用和失效规则，UI 调其接口而不手拼 key。应用事件消费与重连分开，重连主动 refetch 必要会话补漏；工作流通知携带 run_id，让前端读取持久状态，并有轮询补偿。

```text
后端：title B 已提交
事件：S invalidated（可能丢失或重复）
客户端：按 S 的查询身份重取 -> 得到 B
切到 T 后：S 的迟到响应只能更新 S 所属缓存，不能当 T 的内容
```

pending-agent 的 B 选择也不是 `sessions.agent_cli` 已变；发送成功后的权威绑定才应反映为已完成切换。不能在 UI 点选时改出一条假的业务事实。

**边界与缺口（读取推断）**：失效与重取提供最终修正，不是跨窗口实时强一致；是否防止每条旧响应覆盖必须按具体 owner 核查，不能从用了查询库推导全局成立。**可能方案**：实体 revision 和请求 generation 双重检查，新增后端 revision/客户端水位，成本是接口变更；旧响应可丢弃，但错误不能抹掉仍未保存的本地编辑。

## 长对话为什么既要虚拟化，又要保护原文本？

### 当前实现与例子

几千条消息全部挂载会使 DOM 与 Markdown 解析昂贵。**当前实现**：达到门槛的消息列表虚拟化，稳定 row key、动态高度；短会话直接挂载。用户上滚阅读时不被每个新 token 抢回底部，定位历史前先挂载目标行。

流式 Markdown 的临时不完整语法只在派生展示快照中修复，不修改原消息。例：收到 JSON 代码块的开始标记但尚无闭合 fence，展示层可以临时补闭合；如果写回消息原文，下一块真实闭合到达就可能重复，历史也被 UI 改造污染。

虚拟化只减少视图节点，不自动减少后端 JSONL 扫描、内存消息集合或 Agent 交接 token。要区分渲染容量、历史读取容量、模型上下文容量。

**可能方案**：按稳定历史游标分段加载，加锚点及高度占位；需要持久历史索引/游标版本，成本是重复 seq 修正与定位复杂度；索引过期重建或回退扫描，不错序展示。不能用切掉 UI 前 1000 条消息当成安全上下文压缩。

## 工作流自动保存如何避免旧响应把新编辑标成已保存？

**当前实现**：编辑器图形状态与后端 draft 分开；自动保存防抖、重叠写入串行化，用 generation 识别过期响应，失败保留 dirty，切换文档前 flush。mock 工作流内存执行与真实 Run 缓存分开。

演算：编辑 G1 发保存，用户继续得到 G2；G1 成功只能证明 G1 保存，不能把 G2 dirty 清掉。切换 F2 时 F1 的结果归 F1。正在执行的 R 仍引用发布快照，不随草稿保存变化。

**可能方案**：跨客户端再加后端 expected_revision 并返回冲突。这解决两个浏览器同时写 draft 的问题，需保存版本号；代价是合并，失败保留本地图并提示冲突。前端本地串行不能替代后端并发协议。

## 完整业务推演：断线后切换会话再回来

S 正在输出，用户打开 T，S 的跟随订阅按生命周期释放，但关闭视图不意味着取消 prompt owner。后端继续记录稳定历史。再打开 S 通过历史截止点、pending 和实时流衔接；事件连接恢复刷新 Session 元数据。输入草稿按 S/T 分别恢复，模型 pending 与实际绑定分开。任何原型设置或 mock 图的显示都不能用来证明后台已执行相应安全策略。
