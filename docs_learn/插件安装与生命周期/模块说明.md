## 安装成功以后，Agent 为什么还可能不能工作？

用户安装 A 的插件包，设置页显示已安装，但开始聊天时缺少 CLI；升级时又有旧会话正在使用旧版本目录。这里至少有三件事：包是否可信且完整、进程是否运行、执行协议是否准备好。

整体设计：来源决定身份，包管理验证磁盘内容，Lifecycle 独占进程生命周期，Runtime 使用已注册的能力。安装、运行、配置完整和会话 ready 分别判断；卸载按照所有权收回资源，不根据“名字相同”认领用户已有内容。

## 为什么来源身份不能由包自己声明？

### 直观方案、当前设计与演算

只用 `name=agent-a` 做主键，两个市场的同名包就可能共享配置、进程和技能目录。接受包自报 namespace，又允许不可信来源冒充另一个来源。

**当前实现**：宿主为规范来源 URL 分配稳定 namespace，`plugin_source_namespace` 保留这个绑定；完整 PluginId 是 namespace/name。安装路径、配置路径、运行者身份都使用它。删除来源配置不删除身份分配，也不卸载已安装包。

| 存储 | 示例投影 | 回答什么 |
| --- | --- | --- |
| plugin_marketplace_source | url=来源 U，enabled=1，artifact_retrieval=带 type 的配置 | 去哪里发现/获取包 |
| plugin_source_namespace | canonical_url=U，namespace=demo | 该来源的稳定身份 |
| 版本目录 | plugins/installed/demo/agent-a/1.0.0 | 现在安装的代码 |
| 私有配置目录 | plugins/data/demo/agent-a/store.json | 跨版本用户配置 |
| Lifecycle 内存 | demo/agent-a, generation=4, Running | 本进程中运行的实例 |

当前没有 `installed_plugins`、`plugin_processes` 表；安装事实来自验证后的磁盘扫描。不要把来源表当安装库存。

连续追问：删除 U 后再添加为什么不能随机换 namespace？因为会切断旧配置、技能来源和消费者身份关联。**可能方案**是显式身份迁移协议：记录旧新来源、受影响资源清单和迁移阶段，原子切换可事务部分，文件部分保留 journal。代价是处理碰撞及回滚；遇到未知旧资源必须停下，不能直接合并同名目录。

## 升级包时，为什么要同时处理进程和会话？

### 问题与最直观方案

把新版本解压覆盖旧目录很方便，但进程可能仍在读旧文件；Windows 的目录句柄还可能直接阻止替换。只停进程又不够，Supervisor 可能立刻把旧进程拉起来。

### 当前实现与操作推演

**当前实现**：包先校验摘要、归档边界、manifest 与入口；Agent/Workbench 按需启动通用插件进程，Skill/MCP/Hook/Webview 不因此运行 `main.js`。Lifecycle 是插件进程的唯一所有者，Agent Runtime 借用某一 generation 的连接。包替换外围会 suspend Agent Supervisor，阻止替换期间复活。

```text
原状态：磁盘 A@1.0，进程 generation=4，S/T 绑定该 Agent
准备替换：阻止 Supervisor 再拉起 A
停止/回收：由 Lifecycle 和插件拥有者收尾，旧连接路由失效
包操作：安装验证后的版本，或按卸载协议暂存原目录后提交移除
协调：重新发现安装事实、技能投影和相关能力
恢复：解除 suspend；后续连接/会话按新事实建立
```

这是有中断边界的版本替换，不是“旧会话零中断继续使用旧代码”的多版本运行。Running 只证明进程运行；Agent 还要注册合同、启动 CLI、ACP 初始化等准备。静态贡献显示 Stopped 也不等于不可用。

**边界与缺口**：包验证不是恶意 Agent 的强沙箱，当前 Agent 仍有较宽运行能力。安装、文件投影、配置和连接也不是一个跨介质事务。卸载提交后的暂存清理失败不应反向宣布插件仍安装；当前部分清理重试责任在进程内，不能泛化为全部持久自动恢复。

### 连续追问与替代方案

先问“旧会话是否必须继续用旧能力”。若必须，**可能方案**是按包版本运行并存、Session 固定版本引用、旧版本引用计数归零再回收。需保存版本绑定与退役状态，成本是多进程、数据格式兼容和安全补丁不能立即覆盖旧版本；旧版本启动失败时阻塞或显式迁移，不能静默切新。当前 suspend/替换选择更简单，但要接受受影响会话恢复成本。

## 扩展包卸载为什么不能删除它列出的所有成员？

### 当前实现与完整数据演算

用户先自行安装 M@1.0，然后安装扩展包 P，其中包含 M 与 N。P 只真正新装了 N。现在卸载 P，删掉 M 就误删用户资产。

迁移 0014 新增了两张真实表：

| 表 | 记录投影 |
| --- | --- |
| pack_installation | pack_id=P, source_url=U |
| pack_installation_member | pack_id=P, member_id=M, version_at_install=1.0, ownership=pre_existing |
| pack_installation_member | pack_id=P, member_id=N, version_at_install=1.0, ownership=managed_by_pack |

如果 N 后来被用户独立升级为 2.0，卸载 P 时 N 也保留，理由是 VersionChanged。所有权来自安装 journal，不能用今天市场里 P 的成员列表重建。重新扫描只识别 ExpectedAndPresent、VersionChanged、Missing，不自动修复或重写历史。

卸载计划先分类，再逐个复用单插件卸载链路。成功处理一个成员才释放对应关系；某成员失败保留其行并停止，重试从剩余关系重算。全部关系释放后才删除 P 根记录。M/N 保留时只是解除与 P 的关系，并未删除它们的包。

### 连续追问：版本号没变，但用户手工改了文件呢？

**边界与缺口（阅读推断）**：这里的 VersionChanged 判断依据安装版本，不是一份逐文件用户修改账本。若要求识别同版本内容漂移，要额外核对包摘要和文件归属，不能从这个 journal 推导已覆盖。**可能方案**是在成员记录保存安装摘要与受管身份，卸载前检测漂移；成本是哈希与人工处理，无法证明归属时保留并报告冲突。

## Hook 声明合法，为什么还不能自动执行？

**当前实现**：Hook 配置声明包内 `assets/` 下的 executable、可选 supportedAgents 展示列表，以及 lifecycle 的必需 init 和可选 deinit。当前不是旧材料所描述的固定 `rtk-rewrite-v1` 协议。settings-only、MCP transport、Hook hook 三种配置形状互斥；声明编译只证明格式合法，是否执行由后端授权路径决定。包校验和每次执行前都要重新确认 executable 是包内普通非链接文件；参数直接交给操作系统，不经过 shell 拼接。

演算：安装 H 包并通过声明校验 → 用户授权相关生命周期执行 → 宿主再次核查包内 executable → 执行声明的固定参数。supportedAgents 只是展示声明，不是 Host 已探测全部 Agent 并保证适配的结果；工具自身知道如何检查目标环境。也没有一张 Hook 表保存“所有 Agent 已采用”。

**连续追问：init 已修改第三方配置但返回失败，能否直接重试？** 需要先检查该 Hook 自身的幂等与恢复合同。静态声明、参数校验和执行授权不自动回滚它修改的外部文件。**可能方案**是 Hook 操作回执/journal：保存版本、动作 ID、目标身份、修改前后摘要与补偿资料；成本是工具合作与敏感资料保护；结果未知时对账或人工处理，不能用反复 init 保证一致。卸载 deinit 也不能把用户后来改过的配置无条件恢复成旧备份。

## 完整业务推演：卸载中断以后重试

P 管理 N、K，M 原本已有。先删除 N 的包，释放 N 关系；删除 K 失败，则 K 关系和 P 根仍保留。重启以后按 journal 与当前目录对账，N 不会被当成还需要重新安装，M 不会因为仍在 P 的市场清单里被删除。重试处理 K，再释放 M 的关系，最后清 P 根。

若 N 已删除但释放行失败，下一次发现 Missing，可释放关系；这体现“可安全重复处理已缺失资源”，而不是一个包级原子事务。配置是否同时删除由明确的数据处置选择决定，不应该默认清除所有私有数据。
