# 百度一面问题集合

> 整理日期：2026-09-11。
> 本文汇总本次会话的最终共识，围绕产品优势、对话历史存储、跨 Agent 上下文交接展开，并补充相关面试追问。
> **当前实现**依据本轮读取的代码；**拟议方案**是讨论后认可的设计，不代表已经上线。竞品能力以本次查阅的官方资料为准。

## 一、Ora 的核心卖点与优势

### 1. 面试时如何回答“为什么用 Ora，而不是直接用 Codex、Claude Code？”

Ora 是面向多种编码 Agent 的工作环境。它的价值在于管理跨 Agent 的任务连续性、能力配置和重复工作流程。

可以这样回答：

> 当一个 Agent 反复尝试仍然解决不了问题时，开发者本来就会考虑换一个。Ora 希望让这次切换直接在当前任务里完成：继续使用原工作区，把需求、进度、修改原因和失败尝试交给接手者，减少寻找目录、整理背景和重复试错的成本。
>
> 对于经常重复的研发流程，Ora 可以把流程、节点使用的 Agent、skill 和工具配置组织起来，发布为快照。每次输入新需求后，按选定流程执行，用户在需要判断的地方确认。

这里没有承诺底层 Agent 的推理能力更强，也没有承诺切换后一定解决问题。产品价值需要通过接手成功率、减少的人工操作和流程执行体验来验证。

### 2. 四个卖点如何排序

| 卖点 | 用户获得的价值 | 本次讨论的定位 |
| --- | --- | --- |
| Agent 切换与上下文交接 | 当前 Agent 卡住时，减少换工具重新开始的成本 | 个人开发者最容易理解的主卖点；增强交接机制仍属拟议方案 |
| 自定义工作流与发布快照 | 把反复执行的流程及节点配置保存下来，重复运行 | 另一主卖点，尤其适合重复任务和团队流程 |
| Skill、MCP 统一管理 | 按任务、工作区或节点配置能力，减少跨 Agent 重复配置 | 辅助卖点；实际隔离范围取决于实现 |
| 统一 worktree 管理 | 不必寻找各个 Agent 创建的目录，切换时继续使用原工作区 | 体验加分项，与 Agent 交接联动更有价值 |

### 3. Skill、MCP 管理：从“安装方便”转向“能力按任务生效”

用户通过 npm、npx 等工具已经可以安装到多个 Agent，所以“统一安装”本身说服力有限。

更有意义的场景是：用户可能有 1000 个 skill，但不同任务需要不同的能力集合。Ora 的管理方向是维护能力来源、期望配置和实际生效状态，并通过已有 effect 协调思路落实配置。

对外表达可以是：

> **能力统一管理，按任务和工作流节点装配，换 Agent 不用重新配一遍。**

需要区分两个问题：

- **存在哪个目录**：只物化在 worktree A 的项目级文件，不会因为 A、B 使用同一种 Agent 就自动出现在 worktree B。
- **Agent 最终加载什么**：还可能受全局目录、父目录、仓库已跟踪配置等影响。若要保证“只启用用户选中的能力”，Ora 必须处理底层 Agent 的实际加载规则。

也不能把“安装很多 skill”直接说成“每次把全部 skill 正文塞进上下文”。按需加载机制通常会区分名称、描述与完整正文。这个卖点重点是配置范围、选择成本和跨 Agent 一致性，而不是一个未经测量的 token 节省数字。

### 4. Agent 切换：最有吸引力的是“卡住了，换一个继续”

本次讨论最认可的场景：当前 Agent 陷入反复修改、反复失败，用户决定换另一个 Agent 尝试。

手动操作当然可行，但通常要完成以下衔接：

1. 找到当前 worktree，确认工作目录和代码状态。
2. 在该目录启动另一个 Agent。
3. 重新整理目标、用户约束、开发进度和失败尝试。
4. 必要时重新配置 skill、MCP。

Ora 可以把这些操作收成当前任务中的一次切换。

交接记录的价值不只是让接手者看见代码：代码展示“现在是什么样”，历史还能解释“为什么这样改”“什么方案试过了”“哪些结论还没有验证”。

> **Agent 卡住了，直接换一个继续。工作目录不用找，已有改动不用搬，任务背景不用重新整理。**

这句话描述的是产品目标；实际交接仍有摘要损失，需要原始历史检索补足。

“根据任务选择不同 Agent”和“一个入口使用多个 Agent”也有价值，但不必宣称多 Agent 总比单 Agent 效果更好。对用户已有的高效单 Agent 流程，强行增加协作节点可能反而增加成本。

### 5. 工作流为什么不等于一个 SOP skill

Skill 可以包含指令、参考材料和脚本，也可以指导 Agent 使用 MCP。不能简单说“skill 只能提示，不能执行或连接系统”。

两者真正的区别在于流程由谁推进：

| 维度 | 通过 skill 描述 SOP | 由 Ora 工作流运行时管理 |
| --- | --- | --- |
| 步骤推进 | Agent 读取并解释步骤；也可调用配套脚本 | 程序根据节点依赖、状态和条件推进 |
| Agent 与工具配置 | 在指令或辅助程序中安排 | 在节点配置中明确指定 |
| 版本 | skill 文件可以版本化 | 发布快照固定本次运行采用的流程与配置 |
| 人工确认 | Agent 按约定发问 | 可作为明确的暂停、继续边界 |
| 中断后处理 | 依赖 Agent 或自行编写的辅助程序 | 工作流运行时记录执行状态并据此恢复 |

例如，可以把以下 SOP 映射为相应节点和控制逻辑：

```text
输入新需求 → grilling 澄清 → 用户确认 → 开发 → 审查
                                           ↓
                                 按审查结果修复、复核 → 输出 PR
```

这是业务流程示意，不代表现有工作流引擎已经支持图中所有循环和集成。

用户仍然需要输入新需求，也仍然需要判断需求与方案是否正确。工作流省掉的是反复组织节点、交接产物、配置工具和处理流程状态的操作。

**快照固定流程配置，不保证模型每次生成相同结果。**

对接公司内部系统可以加强价值，例如接收工单、等待审批、回写产物。但需要实际连接器和节点能力才能兑现，Skill + MCP 也可以完成系统调用；Ora 的优势应落在流程组织与管理上。[Claude Code 官方能力组合说明](https://code.claude.com/docs/en/features-overview)

### 6. Worktree 的价值如何准确表达

已经核实的竞品事实：

- Codex 的图形界面支持直接选择 Worktree 与起始分支，并管理 Local、Worktree 之间的迁移。[官方文档](https://learn.chatgpt.com/docs/environments/git-worktrees)
- Claude Code Desktop 支持使用 Git worktree 隔离并行会话。[官方文档](https://code.claude.com/docs/en/desktop)
- Claude Code 可以进入已有 worktree。Git worktree 没有绑定某种 Agent，在 Codex 创建的目录中启动 Claude Code，不需要先搬运未提交的修改。[官方文档](https://code.claude.com/docs/en/worktrees)

因此，Ora 的加分项是统一体验：用户不必记住各个 Agent 把 worktree 创建在哪里。

- **不同任务并行**：放在不同 worktree，隔离文件修改。
- **同一任务换 Agent**：继续使用原 worktree，同时交接上下文。

技术上能够手动完成，不意味着没有产品价值。减少寻找路径、启动工具、确认环境的步骤，就是可演示的体验收益。

表述边界：worktree 隔离不保证最终合并没有冲突；“直聊”更准确地说是当前工作区模式，不必默认绑定 `main` 分支。

## 二、对话历史的具体存储形式

### 1. 当前不是“所有对话正文存在数据库表”

**当前实现：会话元数据与生命周期由数据库管理，对话记录正文由 `ora-history` 写入按 Ora session 划分的 JSONL 文件。**

文件路径由 session ID 推导：

```text
<history_root>/<id 的前 2 个字符>/<id 的第 3、4 个字符>/<ora-session-id>.jsonl
```

例如，ID 为 `abcd1234-1234-4234-8234-123456789abc`，路径结构是：

```text
<history_root>/ab/cd/abcd1234-1234-4234-8234-123456789abc.jsonl
```

`history_root` 由运行时提供，不应把这个占位符误认为固定安装路径。

依据：[history README](/Users/silon/ora/desktop/crates/history/README.md)、[路径计算](/Users/silon/ora/desktop/crates/history/src/path.rs)。

### 2. 一行是什么：不是一整个 turn，也不是每个 ACP notification

每一行是一个序列化的 `HistoryLine`：

| 字段 | 含义 |
| --- | --- |
| `at` | 写入时的本地时间，RFC 3339，包含时区偏移 |
| `seq` | 记录在会话中的逻辑位置 |
| `type` 与对应字段 | 展平后的 `HistoryRecord` 内容 |

这里要区分三个单位：用户的一次 prompt、Agent 发来的流式更新、最终落盘的一条记录。

| 输入 | 当前组装与存储方式 |
| --- | --- |
| 一次用户 prompt | 每个 `ContentBlock` 分别形成一条用户记录 |
| Agent 文字流 | 按消息身份与连续性合并，形成完整文字记录 |
| Agent 对用户 prompt 的回显 | 忽略，避免重复保存及混入注入内容 |
| `agent_thought_chunk` | 如果 provider 发送，则合并为思考记录保存 |
| `tool_call`、`tool_call_update` | 按工具调用 ID 合成快照，包含 provider 实际报告的字段 |
| Plan | 每个 turn 保留最新计划快照 |
| 图片、资源等非文字内容 | 作为独立内容记录保存 |
| 模式、命令列表、配置项、usage 等更新 | 当前组装器不写入对话历史 |
| Turn 结束 | 写入独立 `TurnEnded` 记录，保留结束原因 |

例如，用户一次发送“一段文字 + 两张图片”，会生成三条用户内容记录。随后 Agent 回复、调用工具、再回复，可能生成多条 Agent 和工具记录，最后另有 turn 结束记录。

虽然持久化类型沿用了 ACP 的 `agent_message_chunk` 等名称，里面的文字已由 Ora 合并，并不代表每个流式 chunk 都单独写盘。

依据：[记录类型](/Users/silon/ora/desktop/crates/history/src/record.rs)、[组装器](/Users/silon/ora/desktop/crates/history/src/assembler.rs)。

### 3. JSONL 示例

以下使用虚构内容，展示文字消息和结束记录的字段结构；实际文件还会包含开头元数据、工具记录等。

```jsonl
{"at":"2026-09-11T10:00:00+08:00","seq":1,"type":"update","update":{"sessionUpdate":"user_message_chunk","content":{"type":"text","text":"修复登录失败的问题"}}}
{"at":"2026-09-11T10:00:02+08:00","seq":2,"type":"update","update":{"sessionUpdate":"agent_message_chunk","content":{"type":"text","text":"我先检查登录逻辑和错误日志。"}}}
{"at":"2026-09-11T10:01:00+08:00","seq":3,"type":"turnEnded","stop_reason":"end_turn"}
```

当前 `HistoryRecord` 包括：

| Rust 类型 / JSON `type` | 用途 |
| --- | --- |
| `Meta` / `meta` | schema 版本、Ora session、workspace、Agent 身份、provider session、cwd |
| `Update` / `update` | 组装后的会话内容 |
| `TurnEnded` / `turnEnded` | 正常结束、取消等 turn 结束原因 |
| `AgentSwitched` / `agentSwitched` | 从哪个 Agent 切到哪个 Agent，以及目标 provider session |
| `HandoffDelivered` / `handoffDelivered` | 当前交接发送状态的记账标记 |
| `Gap` / `gap` | 写入失败产生的历史缺口标记 |

`HandoffDelivered` 是当前实现中的发送记账，不等于能够观测 Agent 内部已经理解或执行完交接请求。

### 4. 为什么不能按文件行号直接回放

记录第一次出现时分配 `seq`，达到可保存状态时才追加到文件。工具调用可能很早开始、很晚结束，因此写入顺序不一定等于会话顺序。

此外，**同一个 `seq` 可以再次追加，表示修订旧记录**，例如工具结果晚到。

读取时会恢复逻辑顺序，并对相同 `seq` 保留最后一次记录。正常读取会加载整个文件；也已有按写入字节截止位置读取历史前缀的接口。

这对增量摘要很重要：只查 `seq > 上次最大 seq`，可能漏掉后来追加的旧记录修订。新的摘要方案需要识别追加位置或记录版本，而不只是逻辑序号。

依据：[读取与修订处理](/Users/silon/ora/desktop/crates/history/src/reader.rs)、[写入与字节位置](/Users/silon/ora/desktop/crates/history/src/writer.rs)。

### 5. 图片与附件存什么

当前历史写入层直接序列化 ACP 内容块，没有在这里统一把二进制内容抽取成独立附件文件。

| 内容类型 | 当前保存内容 |
| --- | --- |
| 图片 | `data` 中的 base64、`mimeType` 等字段，可能还有 URI |
| 音频 | base64 数据及对应类型信息 |
| 嵌入文本资源 | URI、文本、可选 MIME 类型 |
| 嵌入二进制资源 | URI、base64 blob、可选 MIME 类型 |
| Resource link | URI 与资源元数据，不代表文件字节已被归档 |

所以不能把全部附件概括成“只存路径”，也不能把所有附件都说成 base64。

压缩时应先解析内容块：图片与二进制附件转成稳定引用，避免把 base64 当普通文本送给摘要模型。引用应能定位原始记录及其中的内容块；不要求一开始就把媒体迁出 JSONL。

### 6. Ora 历史是否等于 Agent 的内部上下文

**不等于，即使还没有发生内部压缩也不等于。**

Ora 能保存的是它记录的用户输入和 provider 经 ACP 暴露的内容。Agent 内部还可能有 system prompt、工具定义、配置、内部状态、未暴露的工具信息及模型推理表示。

`agent_thought_chunk` 只代表 provider 愿意输出的思考内容，不能当作完整私有思维链。工具记录同样以实际返回字段为边界，Ora 不能保存从未收到的信息。

Agent 内部压缩只改变它自己的工作上下文，并不意味着 Ora 必须删除原始历史。保留历史的作用正是让会话不依赖某一个 provider 的内部状态。

### 7. 当前持久化与恢复的边界

- 每份历史文件由单一 writer 顺序追加；多个 Ora 进程共用同一数据根不在当前支持范围内。
- 写入会 flush，但不逐次 sync 到磁盘；不能承诺突然断电后最后几条也绝对不丢。
- 崩溃留下的末尾不完整行会被忽略；其他无法解析的行会导致历史被标记为损坏。
- 写入失败会进入相应退化处理，不能继续把缺失记录的历史当作完整历史。

这些是历史系统已有的耐久性边界，不是引入摘要才出现的问题。

## 三、切换 Agent 时的问题与解决方案

### 1. 当前实现与拟议方案的差别

**当前实现**：切换后，在需要交接的 prompt 前注入由历史生成的文本。它保留用户和 Agent 文字，将工具调用简化为标题与状态，省略思考、工具输入输出和计划，图片使用 `[image]` 等占位。当前渲染器没有模型上下文预算控制。

因此存在两类主要问题：

1. 工具证据、修改原因等信息可能未进入交接文本，接手者理解不足。
2. 历史很长时，直接拼接的交接内容可能超过目标 Agent 的上下文窗口。

依据：[历史交接渲染](/Users/silon/ora/desktop/crates/history/src/handoff.rs)、[运行时注入](/Users/silon/ora/desktop/crates/backend/src/agent_runtime/handoff.rs)。

**拟议方案**：短交接文本 + 保留原始历史 + session 范围内的 MCP 补读 + 可用的摘要后端。

### 2. 默认让当前 Agent 总结，保留独立压缩服务兜底

默认路径：当前 turn 结束后，向原 Agent 发一条专门的总结 prompt，让它利用已有上下文生成交接文本。

不需要把 Ora 的全量历史重新塞入它已有的长会话，也不应在这个长会话里连续发送所谓“独立分块”。

独立压缩服务作为备用路径：

- 当前 Agent 额度不足、进程退出、无法响应时使用。
- 服务使用单独的上下文，由 Ora 提供待摘要材料。
- 新 session 只能隔离上下文；若仍使用同一个额度耗尽的账号，不会自动解决额度问题。
- 没有可用服务时提示失败和配置入口，保留现场，允许重试。

产品形态倾向于先作为设置中的内置能力，允许配置用户自己的模型连接或 API key；未来可扩展插件或 Ora 托管服务。具体供应商、费用与默认策略尚未确定。

### 3. 摘要阶段只做总结

总结 prompt 应要求区分：

- 用户明确要求与 Agent 自己提出的建议。
- 已实施、已验证与仅计划实施的内容。
- 有证据的结论与待验证假设。
- 当前有效约束与已经被用户修改或否定的旧决定。

同时在实际运行能力上限制写文件、执行修改命令等工具，只开放必要的只读能力。仅在 prompt 中写“不要改代码”不足以作为工具权限控制。

总结质量可能受原 Agent 的错误判断影响，但这是手动总结、原生压缩也会遇到的常规限制。本次接受通过结构化提示、证据引用和后续补读降低风险，不要求每次交接再增加一个独立审查 Agent。

### 4. 交接文本应该包含什么

```text
任务目标与完成标准
当前有效的用户约束、偏好和明确否定项
已经确认的设计决定及必要理由
已修改内容与当前进度
已执行的验证及结果
已尝试但失败的方案、错误现象和证据引用
尚未解决的问题与下一步建议
图片、附件、关键工具结果的检索引用
信息不明确时如何调用历史 MCP
```

不追求重建原 Agent 的全部内部思维。关键是让接手者知道从哪里继续、哪些限制必须遵守、缺失证据去哪里查。

### 5. 是否保存摘要：保存实际交接正文即可

本次倾向：把实际可复用的交接正文存入独立数据库表，与 Ora session 关联。

第一版不必同时保存内容重复的“摘要”和“最终交接文本”。固定提示外壳、当前用户新请求可以发送时拼装，避免下次摘要时反复包含。

建议记录的信息如下；这是逻辑字段设计，不是现有表结构：

| 信息 | 用途 |
| --- | --- |
| 交接记录 ID、Ora session ID | 标识归属 |
| 交接正文 | 重用、重试、再次切换时作为输入 |
| 历史覆盖截止位置或版本 | 判断哪些内容已纳入，哪些是新增或修订 |
| 来源 Agent / 摘要服务信息 | 排查摘要来源 |
| 生成状态与完成时间 | 未完成结果不能替换最后一次有效结果 |
| 目标 provider session 与交付状态 | 支撑发送重试和原会话恢复 |

选择单独表是为了分离普通聊天记录与内部交接产物。并非放进历史就必然显示：现有回放已能过滤内部记账记录。也可以在历史里保留轻量标记，由标记关联独立交接记录。

**必须有可定位的覆盖边界，但不一定非要往普通聊天消息中插一条可见消息。**

### 6. 多次切换如何增量总结

记：

- `S`：最近一次成功的交接文本。
- `H`：其覆盖位置之后新增或修订的历史内容，不包含内部总结包装文本。
- `S′`：新交接文本。

规则：

```text
没有历史变化：直接复用 S
有历史变化且输入放得下：summarize(S + H) → S′
没有已有 S：从本次选定历史快照生成第一份交接文本
```

上述是独立服务组装输入时的逻辑。默认由当前 Agent 总结时，它已经持有自己的运行上下文，Ora 不需要机械地再追加一遍 `S + H`。

新摘要生成成功后，再保存正文和对应覆盖边界。失败时保留旧摘要，不把尚未成功总结的内容记为已覆盖。

**修订处理**：当前 JSONL 允许旧 `seq` 在文件后面被更新，因此增量范围要考虑追加字节位置或版本。可利用已有的历史前缀读取机制选择稳定快照，再将新增的修订解释为对旧事实的更新。

### 7. 待摘要内容超过压缩服务窗口怎么办

本次明确不接受直接丢掉很久以前、尚未总结的对话来换取一次调用。

采用按需分块：内容能放下时一次处理，超过时才拆分。

```text
新增历史 H
  ├─ A → 独立上下文总结 → a
  ├─ B → 独立上下文总结 → b
  └─ C → 独立上下文总结 → c

旧摘要 S + a + b + c → 整合 → 新摘要 S′
```

每块请求都是独立、受限的上下文，不是在原 Agent 已经很长的 session 中不断追加。

这样避免对每一块都反复重写旧摘要 `S`。如果块摘要的总和仍过长，继续按预算分组整合；单条巨大文本或工具结果也需要在内容内部切分，并保留来源引用。

分块确实增加模型调用与摘要损失。原文保存和 MCP 检索用来补足细节，但不能证明摘要保留了全部语义。可以缓存已成功的块摘要，失败重试时减少重复计算。

### 8. 如何控制预算而不过度复杂化

需要分别控制：摘要请求输入、摘要输出、最终交接正文，以及 MCP 单次返回内容。

本次接受给交接文本设较小预算，不追求填满目标 Agent 的整个窗口。目标 Agent 内部剩余预算不一定可见，因此不能只靠猜测它的完整上下文大小。

实施时可使用摘要服务提供的计数接口、匹配的 tokenizer，或保守估算加服务端超限反馈。具体计数方案待实现时选定，不要求给所有 Agent 分别维护一套复杂 tokenizer 系统。

需要保留的工程约束：

- 摘要输入要为指令、工具定义和输出预留空间；超长则缩小分块。
- prompt 中提出长度要求，程序也检查实际产物；输出被截断视为未完成。
- MCP 支持分页、返回大小限制和继续读取游标，不能一次把全部历史重新塞回上下文。
- 对于上下文超限拒绝，缩小输入或交接正文后重试，不推进成功标记。

“防止超限”的落实依赖这些边界，不应把“模型答应简短”当作唯一保证。

### 9. 历史 MCP 如何保证不串 session

Ora session ID 与 provider 自己的 session ID 不是同一回事。Agent 不会因为创建了 ACP session 就自动知道 Ora 内部的 ID。

推荐由 Ora 在运行时把 MCP 连接、授权凭据或服务实例绑定到对应 Ora session。Agent 决定查什么，服务端决定它被允许查哪个会话。

即使工具参数包含 `session_id`，服务端仍必须核验它与绑定范围一致。按记录 ID 或附件 ID 查找时也要校验归属，不能仅靠 prompt 告诉模型“别查其他 session”。

独立摘要 Agent 与接手 Agent 的历史访问都应绑定到原始 Ora session；不能误用它们新建的 provider session ID 查历史。

可提供的操作包括搜索、分页读取、读取指定记录与附件。接口形式尚未确定，核心要求是服务端作用域限制。

当前正文是 JSONL，所谓“数据库 MCP”可以是历史访问门面：后端通过元数据或索引定位 JSONL，不必为了工具名称把所有正文迁入数据库。

### 10. 图片与附件如何交接

交接文本保留可定位的引用，例如“用户第某条消息中的 UI 截图，见某记录的第某内容块”。若已有可靠文字说明，也可以一并保留，并标明是已有描述。

接手 Agent 需要时通过 MCP 读取原图、文本资源或文件。服务必须返回目标 Agent 能实际使用的媒体或资源内容，单给一个不可访问的数据库位置不算完成补读。

图片不作为 base64 文本反复摘要。只有外部链接的资源，也不能声称 Ora 已永久保存了原文件。

### 11. 切换、中断与恢复

本次认可的顺序：

1. 当前工作 turn 结束，运行时确认允许切换。
2. 选择历史截止快照，进入限制工具的总结阶段。
3. 成功生成并保存交接文本。
4. 创建或恢复目标 Agent session，继续使用原工作区，发送交接。
5. 保存目标绑定和交付状态；中断时按普通会话恢复规则处理。

只有成功生成后才继续正式交接。仅靠前端延迟切换不能代替后端状态检查；这是实现时需要落实的约束。

摘要生成失败、连接中断、发送后响应丢失，都可以通过工程措施处理，不应单独包装成推翻整个设计的大漏洞。

**生成成功与交付成功是两个状态；恢复连接与恢复会话也不等于重新发送上一个请求。** 中断后应优先恢复已经创建的目标 session，避免直接新建会话并盲目重放可能已经执行的任务。

不需要另造一整套交接恢复系统，但切换流程必须保留普通恢复所需的身份和状态。

### 12. 方案的最终判断

这套方案可以作为第一版实现基础。没有必要追求跨厂商完整复制内部上下文，也不要求摘要完全无损。

第一版最值得验证的是接手质量：

- 新 Agent 是否保留关键用户约束，并识别用户后来的纠正。
- 是否理解当前进度、验证结果和失败尝试。
- 是否在证据不足时通过 MCP 找到正确原文。
- 连续多次切换后是否出现事实漂移。
- 超长文本、图片、额度耗尽、进程中断时是否保留可恢复状态。

Git 可以帮助核对和恢复代码，但不会自动恢复未记录的需求，也不代表所有未提交文件都已有备份。这里接受正常工程边界，不要求额外冻结整个工作环境。

## 四、其他讨论过的相关问题

### 1. ACP 会不会通知 Agent 内部发生压缩

本次先前核查到 ACP schema 1.7 引入了实验性的压缩相关更新，包括 `compaction_update` 与 `compaction_summary_chunk`。压缩摘要可能作为可选内容返回，但要看客户端能力声明和 provider 适配器实现。

不能把“schema 有这个类型”直接说成所有 Agent 都会上报，也不能把返回摘要理解为完整内部上下文。当前 Ora 使用的 schema 版本与处理分支仍需在实际接入时检查；本轮读取的历史组装器尚未实现这些压缩通知的专门处理。

来源：[ACP 更新记录](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/CHANGELOG.md)、[CompactionUpdate](https://agentclientprotocol.github.io/typescript-sdk/types/CompactionUpdate.html)、[CompactionSummaryChunk](https://agentclientprotocol.github.io/typescript-sdk/types/CompactionSummaryChunk.html)。

### 2. 能不能直接使用 Agent 自带的压缩摘要

能获得可读摘要时，可以作为交接材料，但它只覆盖对应压缩范围。其后新增内容仍可能很长，所以不能单靠“内部摘要 + 后续全文”解决任意长输入。

还需要区分 CLI 的 `/compact` 与供应商 API compaction。OpenAI Responses 的 compaction 可能包含不透明的加密条目，不能把它当作 Claude 等其他 Agent 可直接解释的普通文本。[OpenAI compaction 文档](https://developers.openai.com/api/docs/guides/compaction)

关于“是否压缩思维链”，只能按具体实现判断：可见的思考文本、供应商内部保留的状态、未公开的推理过程是不同概念。不能从某个 API 的行为推断所有 CLI 都如何处理。

### 3. 其他开源项目是否解决了摘要输入本身过长

本次已做过社区源码调研，主要结论是：有提前压缩、裁剪工具输出、裁掉部分历史、外置检索、分块摘要与层级合并等做法；没有找到能够支持“任意长积压、不跳过未总结内容、只做一次生成式调用”的通用方案。

| 项目 / 方向 | 本次核查的启发 |
| --- | --- |
| OpenCode、Pi | 提前触发、工具输出限长、特定长 turn 处理；摘要请求仍可能失败 |
| Aider、LangMem、LangChain | 部分路径通过裁剪摘要输入控制体积，不符合本次“不直接丢弃未总结历史”的要求 |
| context-mode | 外置原文并检索，减少全部工具输出进入上下文的需要 |
| LLMLingua-2 | 通过小型分类模型做抽取式压缩，减少远程生成调用；仍有信息选择和部署成本 |
| lossless-claw | 保存原文和摘要关系，分块及多级压缩；名称中的 lossless 不代表摘要语义完全无损 |

上述结论对应调研时的具体版本，不概括所有后续实现。固定源码链接、细节与限制见：[开源压缩机制调研](/Users/silon/ora/desktop/docs/agent-compaction-community-research.md)。

### 4. 面试时要避免的几种说法

| 容易被反驳的说法 | 更准确的表达 |
| --- | --- |
| Codex、Claude Code 没有 worktree 模式 | Ora 统一各 Agent 的工作区入口，减少寻找和切换目录的操作 |
| Claude Code 不能接手 Codex 的 worktree | 可以手动接手，Ora 自动衔接工作区、上下文和配置 |
| Skill 做不到对接内部系统 | Skill 可以配合 MCP；Ora 的价值在流程运行、状态管理和节点配置 |
| 多 Agent 一定比单 Agent 好 | 卡住时更换 Agent 是具体需求，交接机制降低更换成本 |
| Ora 保存了完整内部思维链 | Ora 保存 provider 暴露并被历史组装器记录的内容 |
| 摘要有字数提示就绝不会超窗 | 还需要输入分块、输出检查、工具返回限额与超限处理 |
| MCP 能查原文，所以摘要无损 | 原文可追溯，但接手者仍可能没有意识到遗漏 |
| 底层都能手动完成，所以没有价值 | 少找目录、少配工具、少整理背景、少组织重复流程，就是可验证的产品价值 |

## 五、落地前尚待确定的事项

1. 各 Agent 如何真正限制总结阶段的工具能力，哪些适配器支持默认总结路径。
2. 独立压缩服务的连接配置、输入与输出预算、分块缓存及失败重试方式。
3. 交接表的最终 schema，以及如何结合追加位置和记录修订表示覆盖范围。
4. 历史 MCP 的会话绑定方式、搜索索引、分页与多模态返回能力。
5. 用真实长会话验证接手质量，明确第一版的验收标准。

这些属于实现细化，不改变已经认可的主方案。本文件未修改任何产品代码、数据库结构或运行配置。
