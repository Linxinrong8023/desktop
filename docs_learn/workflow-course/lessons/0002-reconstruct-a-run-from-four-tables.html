从四张表重建
一次失败运行

你拿到一个 run_id，不需要先读完整引擎。按固定顺序查询，就能回答：跑的是哪版图、在哪个 Workspace、哪些节点真正启动、失败发生在哪里。

本课胜利条件：能从 run_id 画出完整的持久化证据链

先从事故现场出发

Incident

用户说：“PR 审查工作流失败了。”你看到编辑器里的 Draft 一切正常，但这句话还不能帮助排故。第一件事不是重跑，而是拿到失败的 run_id。

为什么？因为 run_id 同时连接了执行状态、冻结 snapshot、Workspace 和所有已经开始过的 NodeRun。

核心三步，再按需深入

01 · Run确定执行实例

读取 snapshot_id、workspace_id、整体状态、输入和错误。

02 · Snapshot确定冻结计划

读取 version 与 graph，证明当时准备执行什么。

03 · NodeRuns确定实际进度

按 run_id 展开状态、错误、时间和 session_id。

04 · Session还原 Agent 过程

仅对已经绑定 Session 的 Agent 节点继续深挖。

05 · Logs补基础设施证据

Session 前失败或数据库信息不足时再查后端日志。

四张表为什么不能合并

表 它稳定回答的问题 为什么独立
workflows “这个流程是谁？” 名称和激活指针可变化，但稳定身份不能随版本或运行复制。
workflow_snapshots “某一版图是什么？” 一个 Workflow 有唯一 Draft 和多个发布版本；Run 必须钉住其中一个。
workflow_runs “哪一次执行怎么样？” 同一 Snapshot 可执行多次，每次状态、输入、Workspace 和结果独立。
workflow_node_runs “哪些节点实际执行过？” 并行、失败、取消和 HITL 都需要节点级状态；未开始节点不应制造假记录。

直接可用的 SQLite 排故路径

第一步：从 Run 找冻结版本和执行位置。

SELECT id, workflow_id, snapshot_id, workspace_id, run_status, input, output, error, started_at, finished_at FROM workflow_runs WHERE id = ?1 AND is_deleted = 0;

第二步：读取该 Run 真正钉住的图，不查询当前 Draft。

SELECT id, workflow_id, version, graph, created_at, updated_at FROM workflow_snapshots WHERE id = ?1 AND is_deleted = 0;

第三步：展开真正开始过的节点。

SELECT node_id, node_type, status, session_id, input, output, error, started_at, finished_at FROM workflow_node_runs WHERE run_id = ?1 AND is_deleted = 0 ORDER BY created_at, id;

三个容易被拷打的设计点

  • workflow_runs 同时保存 workflow_id 和 snapshot_id：前者回答业务归属和列表查询，后者精确钉住执行版本。
  • 状态在 SQLite 中保存为整数：0 Pending、1 Running、2 Succeeded、3 Failed、4 Cancelled；Rust Domain 把它转换为强类型枚举。
  • 软删除后的行不参与名称/版本唯一索引，因此名字可以复用；删除级联和活动 Run 保护由 Repository 事务执行。
源码细节：workflows.published_snapshot_id 在迁移 SQL 中只是 TEXT，并没有声明 REFERENCES；不能假装数据库外键替你保证这个指针正确。发布、激活和删除约束由应用与 Repository 的事务维护。
Interview pressure

面试官会怎么追问

为什么 Run 不能只保存 workflow_id？

workflow_id 只能定位稳定身份，无法证明执行的是哪一版图。若随后 Draft 或激活版本改变，历史 Run 将无法复现。snapshot_id 才是执行版本证据。

为什么 graph 不拆成 node 表和 edge 表？

当前定义层需要原样保存 React Flow 作者文档与版本。把 graph 作为快照文本降低定义写入复杂度；运行引擎在启动时解析和验证 DAG。代价是数据库不擅长节点级查询。

软删除为什么配合部分唯一索引？

历史行仍保留审计价值，但只让 is_deleted = 0 的可见行参与名称与版本唯一性，从而允许删除后复用名称，同时避免物理删除立即破坏历史关联。
