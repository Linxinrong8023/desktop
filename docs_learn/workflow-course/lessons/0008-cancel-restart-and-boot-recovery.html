Lesson 0008 · 生命周期控制矩阵

取消是收口，
重跑是清账，恢复是判案

三者都会碰 Run 和 NodeRun，但目的完全不同：Cancel 把仍在执行的事实收敛为终态；Restart 主动抹去本轮可见执行痕迹并从头跑；Boot Recovery 则只依据崩溃前已提交的事实，判断续跑、保留等待或失败关闭。

本课胜利条件：面对任意中断时刻，能说清哪些记录会变、是否重新调度、为什么不会把未知执行误判为成功

先抓住三种意图

操作 它在回答什么问题 最终语义
Cancel 用户现在不想让这次 Run 继续了 同一 Run 进入 Cancelled，不再推进
Restart 用户要把这次 Run 当作一次全新的执行重跑 仍是同一个 run_id，从 Start 重新执行
Boot Recovery 进程意外退出后，数据库里的半成品到底该怎么办 按持久化事实选择 Fail / Preserve / Resume

Cancel：先把数据库变成终态，再停 Session

持有 per-run lock
  → DB 事务
      Pending / Running NodeRuns → Cancelled
      Run → Cancelled
      current_nodes → []
      COMMIT
  → 释放锁
  → best-effort stop 已绑定的 Sessions

顺序不能反过来。若先停外部 Session、随后数据库写失败，系统会留下“Session 已停，但 Run 仍是 Running”的矛盾事实。 现在先提交终态，因此即使停止 Session 失败，调度语义仍然明确：这次 Run 已取消。

迟到的完成回调也不能复活节点。回调尝试把 NodeRun 从 Running/Pending 改成 Succeeded 时，会发现它已经是 Cancelled，条件更新返回 NotRunning，Engine 将它当作幂等 no-op。

Restart：不是新建 Run，而是重置同一条 Run

仅拒绝当前 Running 的 Run
  → DB 事务
      旧的可见 NodeRuns → is_deleted = 1
      Run → Pending
      current_nodes → []
      output / error / started_at / finished_at → NULL
      COMMIT
  → Engine.start(same run_id)
      按同一 snapshot_id、workspace_id 从 Start 重跑

所以 Restart 后：run_id 不变，旧 NodeRun 仍作为软删除历史存在，新一轮会生成新的 NodeRun id。 如果业务需要保留两次彼此独立、同时可见的执行记录，应创建新的 WorkflowRun，而不是 Restart。

当前实现只拒绝 Running，因此 Pending（包括尚未启动或可能处于 HITL 的 Run）也能进入 restart_run。这里要区分“当前代码允许什么”和“产品语义是否还应收紧”。

Boot Recovery：对三种持久化现场作出不同判决

现场 A · 外部结果未知存在 Running NodeRun

进程死时 Agent 可能已经产生副作用，不能安全重放。Run 与所有非终态 NodeRun 标记 Failed，error 为 interrupted_by_restart。

现场 B · 只是调度断档A 已 Succeeded，B 尚无 NodeRun

A 的完成已提交，说明它不需要重跑。Engine 从冻结 DAG 与现有 NodeRuns 重新计算 Ready，创建并派发 B。

现场 C · 正在等人合法 Pending Agent NodeRun

只有节点是 interactive Agent、已有 session_id，且冻结图也证明它是交互节点，才保留等待，不自动推进。

其他 Pending 记录属于无法证明其语义的持久化异常，系统选择 fail closed：标记失败，而不是猜测它可以继续。

最容易在面试里说错的区别

比较项 Restart Resume / Boot Recovery
触发者 用户主动命令 进程启动时内部修复
成功节点 旧 NodeRuns 全部软删除，从头再跑 保留已成功节点，只补上未调度后继
Running 节点 当前 Running Run 不允许 Restart 因外部结果未知而判 Failed
run_id / snapshot 不变 不变

真正有区分度的竞态题

Agent A 的完成回调与用户 Cancel 几乎同时到达。不要只回答“有锁所以安全”，请分别推演：完成回调先拿到 per-run lock，和 Cancel 先拿到锁。两条时间线中，A、可能出现的后继 B、Run 的最终状态分别是什么？为什么最终都不会继续推进？

答题时必须覆盖的四个关键词

条件状态迁移、回调后的 run_schedule、Cancel 事务、迟到回调 no-op。
