Lesson 0003 · 运行引擎

一轮一轮调度 DAG

调度器不保存一份神秘的内存进度。每次 Start 或节点回调后，它都从冻结图与 NodeRun 记录重新计算：谁已完成、谁仍在运行、谁现在可以启动。

本课胜利条件：看到任意一组 NodeRun 状态，能手算下一轮 ready set

先推演一张四节点图

┌── Agent A ──┐ Start ──────┤ ├── Output └── Agent B ──┘

点击 Start 后，并不是一次性给四个节点都建记录。引擎只启动当前满足条件的一批节点，这一批叫一个调度波次。

真实执行时间线

Wave 0Start 入库

Run 从 Pending 变 Running，同时创建 Start NodeRun。

Wave 1Start 同步成功

Start 是控制节点，不创建 Agent Session。

Wave 2A、B 同时 Ready

两条 NodeRun 在同一事务波次创建，然后分别派发 Session。

Wait等待两边完成

A 先成功也不够；Output 的所有直接前驱都必须成功。

Wave 3Output 与 Run 完成

Output 汇总前驱输出；图耗尽后 Run 才变 Succeeded。

每轮只计算三个集合

completed

已经成功

状态为 Succeeded 的 NodeRun 对应节点。只有成功节点才能解锁后继。

in_flight

仍未结束

状态为 Running 或 Pending 的 NodeRun。交互节点等待人工输入时也是 in-flight。

ready

现在可启动

自己尚未完成、所有直接前驱都在 completed，且自己不在 in_flight。

drained

图已耗尽

ready 为空且 in_flight 也为空，此时引擎汇总输出并完成 Run。

current_nodes 在哪里？ 它不是 workflow_runs 的独立列，而是保存在 workflow_runs.state 文本列中的 JSON，例如 {"current_nodes":["agent-a","agent-b"]}。数组保存的是图节点 node_id，不是 workflow_node_runs.id。真正计算 completed / in_flight / ready 时，引擎仍会读取 NodeRun 行重新计算；这个数组是由事务同步维护的运行锚点。

Ready 规则不是“有一个前驱成功”

ready(node) = node 尚未成功 AND node 不在运行或等待输入 AND node 的每一个直接前驱都已成功
汇合点规则：在上面的图中，A 成功而 B 仍在运行时，Output 仍不 Ready。这不是调度丢失，而是在等待另一个直接前驱。

回调如何推动下一轮

Start / Resume / 节点成功回调 │ ▼ 读取 Run + Frozen Graph + NodeRuns │ ▼ 计算 completed / in_flight / ready ┌──────┴─────────┐ ▼ ▼ ready 非空 ready 为空 批量创建 NodeRun ├─ 有 in_flight：等待回调 派发 Agent └─ 无 in_flight：完成 Run

Agent 节点异步执行，完成后调用 complete_node，再触发一次调度。节点失败调用 fail_node，Run 进入 Failed，不再继续调度后继。

为什么每轮从数据库重算

  • 进程重启后不必依赖丢失的内存队列，resume 可以从持久化状态恢复计算。
  • 重复 Start、重复完成回调和迟到回调可以通过状态条件变成幂等 no-op。
  • 排障时数据库就是调度证据：缺少 NodeRun 通常表示它从未进入 ready 并被成功落库。
继续调度不等于重新执行。 普通的 run_schedule 只在同一个 Run 中根据现有 NodeRun 推进下一波； resume 用于补上“节点完成已落库、后继尚未调度”这类崩溃间隙，也不会重跑已成功节点。 只有显式 restart 才会把旧 NodeRun 软删除、清空 Run 的状态与结果，并从 Start 重新执行；创建新 Run 则会产生新的 run_id，不要把这四件事混为一谈。
Interview pressure

面试官会怎么追问

为什么 Pending 也属于 in-flight？

交互 Agent 第一轮结束后会停在 Pending 等待用户输入，但它并没有完成；若不算作 in-flight，调度器可能重复派发它或错误解锁后继。

为什么 ready 节点要批量落库后再派发？

同一波并行节点及 Run 的 current_nodes 需要形成一致的持久化事实；否则派发成功但数据库未记录会制造不可恢复的幽灵执行。

为什么节点失败后不继续计算 ready set？

当前 v1 采用 fail-fast：fail_node 同时使 NodeRun 和 Run 失败，Run 已进入终态，因此不会再调度后继。

2. 交互节点处于 Pending，调度器应如何理解？
