## 一个聊天窗口至少有三种“存在”

用户先输入草稿，再发送，再关闭标签页，第二天从历史列表打开。产品看上去都是“这个聊天”，后台却要区分业务记录是否存在、provider 是否有上下文、当前是否有执行者。混为一个布尔值会产生空会话、误取消和无法解释的恢复行为。

整体设计可以这样讲：Ora 会话是长期身份；provider 会话是执行绑定；窗口是观察和操作入口。首次实际发送才创建执行上下文，只读历史不需要启动 Agent；取消一轮、停止绑定和删除业务记录各有不同的资源与数据责任。

## 为什么不在打开空白页时创建所有东西？

### 问题与直观方案

打开窗口就创建 provider 和数据库行，看似流程统一，但用户可能没有发送，也可能在选择模型时退出。此时多了没有业务内容的会话，还占用进程资源。仅在发送后创建数据库行又会遇到外部创建成功、数据库失败的窗口。

### 当前实现与演算

**当前实现**：草稿由前端维护，首次发送时才准备 provider session；握手与可选模型配置成功后保存 Ora Session，并把同一条路由交给会话执行者。创建期间的释放保护负责回收尚未发布的 provider 资源。

| 阶段 | 前端 | SQLite `sessions` | provider / 内存 |
| --- | --- | --- | --- |
| 输入“修复重复重试” | 有草稿 | 没有 S | 没有 A1 |
| 开始创建 | 等待结果 | 仍无 S | A1 已创建，属于未发布资源 |
| 模型设置成功并保存 | 得到 S | S→A1，status=0，mcp_selection 已确定 | 路由交给 S 的执行者 |
| 首次发言 | 草稿转成已发送内容 | S 仍是同一行 | 用户输入写 JSONL，随后发 prompt |

**边界与缺口（读取推断）**：保护对象能处理正常错误和任务取消，不等于机器被强杀时能联系 provider 清理所有刚创建的会话。Ora 不能承诺第三方绝无空记录。

连续追问从“为什么延迟创建”走到“外部成功数据库失败怎么办”：先明确资源尚未发布，再说明回收责任；如果追问强杀，需要承认进程内保护不够。**可能方案**是保存创建操作意图与 provider 资源回执，再在启动时对账；代价是新增暂存记录、保留期限和 provider 查询依赖；查询不到不能擅自认定没创建，必要时展示待清理状态。

## 打开历史为什么不等于恢复执行？

### 当前实现

只读 load 使用 Ora 自有 JSONL。有执行者时，将 durable 截止位置、内存未完成内容和后续流拼接；没有执行者时有限回放。它不依赖 provider 的 load 历史，也不因用户查看记录就启动 Agent。

真正 prompt 时才按需 attach/restore。如果 provider 原会话无法恢复，系统可以创建替代上下文并使用 Ora 历史交接。这时业务 ID S 不变，provider ID 可能从 A1 变成 A2。已有 `mcp_selection` 仍属于 S，不能由于关联的工作流记录缺失就重新猜权限。

| 重启后的步骤 | `sessions` 投影 | JSONL | 判断依据 |
| --- | --- | --- | --- |
| 启动校正 | S, A1, status=1 | 保留 | 旧 Running 不证明新进程已连接 |
| 只打开历史 | 不变 | 读取 | 能看记录，不代表能继续运行 |
| 发送新输入 | 尝试恢复 A1 | 准备交接材料 | provider 的恢复结果 |
| 必须重建时 | 按提交边界换成 A2 | 保留此前记录，交接后有相应证据 | 创建成功与请求接受分别判断 |

**边界与缺口**：`status=0` 是 Running 绑定状态，不能独自表示“正在输出”。本轮执行、历史是否降级、自动标题窗口是不同维度。若要统计忙碌会话，应读取拥有该状态的运行者，而不是用数据库 Running 行数代替。

### 连续追问与替代方案

“只读也连 provider，这样更真实”要付出离线不可读、启动成本和 provider 历史格式依赖；“只读绝不接实时流”则漏掉进行中内容。当前分离读取和执行，辅以跟随，解决两者。

若面试官要求跨设备恢复，当前本地数据库和文件布局不能直接满足。**可能方案**：为业务 Session、转录版本与执行租约增加服务器所有权；保存设备身份、租约代次、最后持久位置。成本是同步冲突和网络依赖；离线允许读取缓存，发送需要有效执行租约，不能两个设备同时恢复同一 provider 后都认为自己拥有 prompt。

## 取消、停止、删除为什么不能共用一个按钮的后端语义？

### 问题与数据变化

用户说“不要继续了”可能指当前回答；关闭查看窗口只是不看了；删除则是移除 Ora 业务资料。最直观的统一处理是关闭窗口就杀进程，结果会影响共享连接上的其他会话。

**当前实现**：

| 动作 | 执行责任 | 数据变化 | 保留内容 |
| --- | --- | --- | --- |
| 关闭跟随视图 | 取消该订阅 | 不因此删除 S | 本轮可以继续 |
| cancel | 结束当前轮，处理取消响应 | JSONL 记录相应结束边界 | 健康会话可再发言 |
| stop | 卸载 S 路由，能力支持时 close provider | 生命周期状态更新 | Ora 历史、provider 自有历史 |
| delete | 先串行 unload，再软删除 | `is_deleted=1`；尝试删除 Ora JSONL | 不负责删除 provider 自有历史 |

停止和删除均不能粗暴杀掉所有共享该 Agent 的会话。Ora history 删除是尽力执行，失败会记录告警；因此数据库软删除成功不证明文件一定消失。两种存储的操作没有跨资源原子性。

### 连续追问：删除成功后磁盘还有文件，算不算 bug？

要先问产品合同。如果合同是从 Ora 列表删除并释放执行资源，这属于明确的清理残留；如果宣称彻底擦除敏感数据，则现有路径不足，且还涉及备份、provider 和文件系统恢复。不要用一个“软删除”词跳过范围。

**可能方案**：保存待清理任务，记录 Session、受控历史路径、失败原因与重试次数；列表隐藏与清理完成分别可见。代价是后台协调与磁盘扫描；删除前核验路径归属，失败保留责任，不能对 provider 私有目录递归猜删。该方案也不等于物理不可恢复擦除。

## 完整业务推演：重命名以后重启再删除

S 首轮生成时可能收到自动标题。用户手动改为“重复重试排查”，数据库只更新 title 及对应时间，不整行覆盖 Agent 绑定；当前自动标题窗口被锁定，迟到标题不应覆盖用户选择。

1. 操作前：`S(title=新对话, agent_session_id=A1, status=0, is_deleted=0)`，JSONL 含首轮内容。
2. rename 提交 title-only 更新，再通知前端重取。广播失败不回滚已保存标题；刷新仍可读到。
3. 应用重启：S 被校正 Stopped，自动标题的初始窗口不会重新开启。打开历史保持 A1 绑定不等于重新注册。
4. 用户删除：串行卸载 S，再软删除；随后清理 JSONL。如果清理失败，普通列表已经不可见但磁盘仍有待处理文件。

内存里的标题锁不是持久“人工命名”审计字段；恢复会话直接禁用初始自动标题路径，不能据此声称拥有跨设备的标题版本冲突协议。

**问题：用户删除时创建请求刚刚成功，另一个窗口仍在跟随。怎样分析是否泄漏资源、出现幽灵消息或删除后复活？**

<details><summary>分析提示与参考思路</summary>

先确定删除针对已有 S 还是尚未发布草稿，创建结果何时对外可见。针对 S 的操作需要经过同一生命周期所有者，异步回调还要校验当前状态，不能只依赖前端取消等待。跟随窗口应失去订阅或刷新删除状态；已经到达的消息不代表 S 复活。验证点是创建成功但保存失败、删除先于迟到绑定、同一 S 多视图、JSONL 删除失败。若设计持久创建意图，应另外测试重启对账，不能把正常取消测试冒充强杀测试。
