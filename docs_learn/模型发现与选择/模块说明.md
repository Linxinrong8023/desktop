## “我明明选了模型，为什么创建时还要检查？”

用户在工作区 W 看到 Agent A 提供模型 M1，选择后切换到了 Agent B；或者在发送前修改了插件配置。下拉框选项、用户偏好、provider 实际采用的模型此时可能是三回事。这个模块的价值是让 UI 表达意图，让真实执行上下文确认能力。

整体设计：创建前按当前工作区向插件询问可选模型；创建后以该 provider session 握手给出的配置选项为准。偏好留在客户端，实际配置交给会话运行时。不能根据模型名称猜容量、思考级别或者费用，也不能把“选择过”当成“本轮已经采用”。

## 为什么创建前目录不能成为永久的模型真相？

### 直观方案与它的反例

启动应用时查询一次所有模型并缓存，能让下拉框很快。但模型目录可能取决于凭据、插件版本和 cwd。W1 配置能用 M1，不代表 W2 能用；Effect 可能重启 CLI，而共享连接标识未发生对应变化，按连接 generation 缓存也可能过期。

### 当前实现与演算

**当前实现**：创建前调用插件模型发现能力，携带真实 cwd；不同 Agent 查询独立超时，返回成功组。运行时不把预会话目录永久缓存到共享连接。某些 Agent 只能在 ACP Session 创建后给出选项，预会话为空不证明它没有模型。

| 步骤 | 输入/读取 | 得到的事实 | 尚未证明的事 |
| --- | --- | --- | --- |
| 查询 W1 | A + W1 cwd | A 当前返回 M1、M2 | M1 会在稍后仍可用 |
| 保存偏好 | A→M1 | 用户希望选 M1 | provider 已采用 M1 |
| 插件配置改变 | 凭据/版本改变 | 原目录可能过期 | 新目录必然相同 |
| 创建会话 | A、W1、M1 意图 | 握手返回当前配置选项 | 需要继续确认选择是否合法并应用 |

如果另一个 Agent 查询失败，成功组仍可用于界面；这不等于失败 Agent 无能力，诊断要结合运行状态与日志。

### 连续追问与可能方案

追问“为什么不用 TTL”：TTL 控制最长陈旧时间，不能保证发送当刻正确；即使加缓存也必须在会话握手处校验。追问“如何提高体验”：**可能方案**是按 Agent、cwd、包版本、配置 revision 缓存带年龄的目录，并合并并发查询。新增缓存键和失效证据，成本是更多失效来源；刷新失败可以显示陈旧提示，但发送仍以握手校验为边界，不静默使用已失效模型。

## 用户偏好怎样变成实际配置？

### 当前实现与数据例子

用户对 A 选择 M1，客户端 `agent-model-preference` 在 localStorage 按完整 AgentRef 记住它。待创建或待切换时，pending-agent 状态保存本次意图；创建、切换、首次 attach 会带上它。已 attach 会话则依据自己的 config options 修改配置。

```text
客户端偏好（语义示例，非 store 序列化原文）
  demo/agent-a -> M1
  demo/agent-b -> M9
待应用意图（内存）
  S -> {目标 Agent: demo/agent-b, 目标模型: M9}
数据库 sessions（相关列投影）
  S -> {agent_cli: demo/agent-a, agent_session_id: A1}
```

点选 B/M9 后数据库仍可能是 A/A1。准备 B 成功、校验并应用 M9，再按切换提交边界更新 `sessions` 为 B/B1。pending 意图结束不代表每一轮都有模型审计记录；`sessions` 没有 model 或 model_id 列，当前也没有专门 models 表。

**边界与缺口（已确认）**：清除 localStorage 会丢失客户端偏好；换客户端不自动共享。SQLite 绑定只能说明哪个 Agent/provider session，不能回答“第 37 轮到底用的哪个模型”。思考强度等配置来自 provider 的实际合同，不能只凭名称拼一个通用下拉框。

### 连续追问：不支持 M9 时偷偷换默认值好吗？

先澄清用户选择是否具有成本、隐私或质量约束。静默降级可能违背这些约束；拒绝并保留选择失败原因更可解释。若产品选择允许回退，应明确提示实际采用的模型并记录回退，而不是 UI 保持 M9、后台用 M10。

**可能方案**：增加模型采用回执，保存请求值、实际值、配置选项版本、原因与会话/轮次关联。失败时没有确认就不能写“已采用”；成本是 provider 可能不给出完整身份，需要明确 Unknown，不能从返回文字猜模型。

## 用量展示为什么还不能回答“剩余上下文多少”？

### 问题与当前设计

用户看见输入 token=970、输出=17、缓存读取=18176，简单相加得到 19163，就想拿它减模型窗口。但这些指标的会计口径可能不同；usage 是这次调用还是累计？缓存算在 input 里还是另列？不同 Agent 元数据不能靠名字猜。

**当前实现**：运行时把协议响应 usage 规范化为独立字段，保留标准字段优先级；未有明确扩展合同时 accounting scope 为 Unspecified。缺失信息保留缺失，不能推定零。历史 assembler 忽略 `UsageUpdate` 这类会话附属更新，因此界面看到用量不代表历史文件已形成完整计费账本。

| 示例字段 | 值 | 可以说 | 不能说 |
| --- | --- | --- | --- |
| total_tokens | 19163 | provider 报告该值 | 自己重算总量必然一致 |
| input_tokens | 970 | 报告的输入字段 | 包含所有系统提示和缓存 |
| cached_read_tokens | 18176 | 报告缓存读取 | 必然可再从 input 扣一次 |
| accounting_scope | Unspecified | 口径未明确 | 一定是单轮/会话累计 |

### 连续追问与可能方案

如果面试官要求精确预算，要区分“发送前构造出来的请求估计”与“发送后 provider 计量”。前者用于避免超窗口，后者用于展示/结算；二者都需要明确 tokenizer、工具声明和系统保留预算。**可能方案**：保存每轮实际模型合同、预算版本、发送前估值和返回 usage 原始口径摘要；代价是元数据持久化与模型适配；预算信息缺失则留安全余量并处理 provider 拒绝，不能编造精确剩余额度。详细容量推演见智能体切换模块。

## 完整业务推演：目录已变但偏好还在

1. 原先客户端记住 A→M1，SQLite 的 S 绑定 A1；数据库没有 M1 列。
2. 配置更新后，预会话查询返回 M2、M3；旧 M1 偏好仍是用户历史意图，不能覆盖新能力事实。
3. 用户继续创建/切换，运行时根据新握手进行校验；不支持的选择不能被当成已配置。
4. 合法配置完成才继续发送。真实使用值位于当前会话/provider 配置，而不是从旧 localStorage 反推。
5. 应用崩溃后偏好可能仍在，Actor 配置内存消失；再次 attach 必须重建实际选项。若要审计此前某轮，用量和模型持久化缺口仍然存在。

先约定审计精度：展示估值、内部额度还是账单结算。保存用户请求、provider 确认、计量口径、定价版本和时间；缓存 token 不重复计算。没有实际模型证据时记录“请求 M1、未获得确认”，不能把偏好列改名 actual_model 就算完成。重试也可能收费，需要关联逻辑轮次与每次尝试，不能只统计最终成功响应。验证包括目录更新、未知模型、配置失败、重试多次、usage 缺失以及 provider 口径不明。
