# Ora 模块学习教材：沿连续追问理解设计

> 核对日期：2026-09-23；本地代码基线 `6660767f`（`project_learn`）。本目录只保留 21 个中文模块，每个模块一份 Markdown，以及本导航。没有修改产品代码或真实业务数据。

目标是面对校招面试官时，能从一个用户动作讲清判断依据、状态顺序与持久证据；改变容量、并发和失败条件后，仍能分析边界并提出可验证的方案。不要背函数名或把字段字典当设计回答。

## 怎样使用每篇教材

先读开场建立整体设计，再对每个决策回答“直观方案为什么不够”。沿例子推演操作前、中间、提交后与中断后的状态，最后先独立回答文末问题，再展开参考思路。源码是查证入口，不是理解正文的前提。

- **当前实现**：已经沿本地执行路径核实；注释、类型定义或旧提案不单独证明落地。
- **边界与缺口**：明确现有保证的条件；阅读推断不冒充故障复现。
- **可能方案**：尚未实现的设计，说明问题、机制、新增证据、代价和失败处理。涉及新表/字段时不能说成当前已有。

示例使用虚构 ID 和数据；短 ID/状态文字投影帮助推理，不是可直接导入的生产 SQL。Agent 两篇连续案例保留 2026-09-10 的固定示例时钟，核对日期则是本次日期。案例业务要求“最多重试两次”不等于 Ora Runtime 的三次停滞自动重试政策。

## 跨模块连续追问路线

| 从哪里开始 | 继续追问 | 要接到哪些模块 |
| --- | --- | --- |
| 换 Agent 继续工作 | 保存的历史是否等于可用上下文 → 摘要仍超限怎么办 → 交付确认是否等于理解 → 工具授权是否保留 | 历史、切换、模型、MCP、运行时 |
| 工作流失败重试 | 成功结果存了没有 → 文件是否回滚 → 远程副作用能否撤销 → Loop 从哪轮重新开始 | 版本、执行恢复、工作树、数据库 |
| 安装新版技能 | 包合法是否代表可用 → 文件已改是否 ready → 旧 worker 是否还有写权 → 用户改过文件怎么办 | 插件、配置、技能、Effect |
| 用户点击取消 | 请求取消是否资源已停 → 迟到创建如何清理 → 重启后谁负责 → 日志能否证明完成 | 架构、生命周期、任务、日志 |
| 审查后提交 | UI 内容是不是最新 → index 是否变化 → 路径是否仍属于该工作区 → 清理能否同时发生 | 前端、文件审查、工作区、工作树 |

每次口述都要明确“我知道什么、证据在哪、还不知道什么”。如果只能说“有事务”“有锁”“加摘要”“失败重试”，继续问它具体覆盖哪个窗口、没有覆盖哪一个窗口。

## 自测验收方法

1. 用两分钟讲清一个模块的场景、主要矛盾和整体方案。
2. 选一个决定，比较至少一种替代方案，说明采用条件与成本。
3. 不看正文画出一次操作的数据库/文件/内存变化，并标提交边界。
4. 在每个外部副作用前后制造一次中断，解释恢复依据；证据不足时承认 Unknown。
5. 将条件改为大历史、多窗口、慢工具、配置升级或重复请求，判断原保障是否仍成立。
6. 对未实现方案说清新增存储和验证方式，不把想法包装成项目成绩。

参考思路只是分析路径，不是唯一标准答案。你可以反驳当前设计，但要给出约束、代价及验证办法。
