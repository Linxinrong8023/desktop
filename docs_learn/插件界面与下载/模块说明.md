## 插件页面能显示，不代表它能执行任意宿主操作

用户打开 Workbench，点击弹出窗口，随即关闭；旧页面一个下载还在完成。宿主要判断结果属于哪个页面、哪个进程代次、哪个下载决定，不能根据一个看起来像插件的窗口名字授予权限。

整体设计：Surface 状态层只决定合法转移和待执行动作，Desktop host 执行原生窗口与文件操作。registry 保存可信实例身份，异步动作带操作票据，页面绑定插件进程代次；下载在开始时冻结策略，用户选择只结算一次。

## 为什么 registry 身份比页面传来的 pluginId 更可信？

### 当前实现与演算

**当前实现**：宿主从原生调用上下文查注册实例及来源。Workbench bridge 可调用方法是 manifest 声明与当前进程注册能力的交集，请求/响应各限 1 MiB。远程 Webview 不获得通用 Tauri IPC。页面不能靠传入另一个 pluginId、instanceId 或 label 前缀扩权。

| 对象 | 可信来源 | 示例 |
| --- | --- | --- |
| 实例 I1 | Host registry | 归属 demo/panel |
| 插件进程 | Lifecycle | generation=4 |
| bridge 可用方法 | 声明 ∩ 本次注册 | readReport |
| 页面请求 | 不可信输入 | “调用 deleteEverything”仍要拒绝 |

Workbench 包内资源还要经过 canonical asset root、扩展名、CSP 等检查；RemoteSite 导航限制为声明的 HTTPS origins。检查 origin 不能代替 registry，也不能用 CSP 代替宿主授权。

连续追问“插件升级了，旧页面能复用权限吗”：不能静默换代，页面绑定 generation4，新进程generation5 后旧页面调用需要失效/关闭。**可能方案**是显式迁移握手，保存新旧实例、能力版本与允许迁移状态；成本是序列化和敏感状态清理，握手失败重建页面，不自动把旧回调认成新页面操作。

## 为什么打开/关闭需要 OperationId，而不是只看当前状态？

### 场景、当前实现与完整演算

异步创建窗口没完成，用户已关闭。若回调总是把状态设成 Opened，会出现用户关掉的页面又冒出来。

**当前实现**：每个异步动作产生票据，完成必须匹配 pending operation；重建增加 ViewGeneration。Opening/Migrating 时收到 Close 先记住关闭请求，待原生动作完成立即收尾，不对外制造一个正常打开事件。

| 时刻 | 内存状态 | 输入 | 结果 |
| --- | --- | --- | --- |
| t0 | Opening，op=10，view=1 | 创建尚未完成 | 等待 |
| t1 | 同上 | Close | close_requested=true |
| t2 | 同上 | Opened(op=10) | 转 Closing，发 Destroy |
| t3 | Closing，op=11 | 迟到 Opened(op=9) | stale，拒绝 |
| t4 | Closing | Closed(op=11) | 移除实例 |

registry 锁只保护纯状态和 map，不在锁内做 Webview I/O，否则一个慢操作阻塞所有页面。当前没有 surfaces/webviews 表，这些状态随 Desktop 进程结束消失。

**边界与缺口**：内存状态机处理正常异步竞争，不提供重启恢复所有原生窗口操作。**可能方案**若产品要求恢复布局，持久化“用户期望打开的页面/布局”，重启新建实例，不恢复旧 operation ID；成本是无效插件/旧版本兼容，恢复失败显示可解释状态，不接纳上个进程的回调。

## 下载为什么要冻结开始时的策略？

### 问题与当前演算

页面在 trusted.example 下载报告，随后导航到另一个 origin。若完成时重新按当前页面决定导入位置，旧下载会被赋予新页面权限。

**当前实现**：开始时冻结页面 URL、规则与身份，写唯一 `.part` 暂存，完整后 promote。状态为 Staging → AwaitingChoice 或 Processing → Settled。用户选择的转移只允许一个动作；宿主导入/保存真正成功才报告成功，页面不能任意指定宿主目标路径。

```text
D1 开始：来源 origin=U1，规则=询问导入/保存，实例=I1
D1 写暂存：downloads/唯一文件.part
页面导航：变成 U2，不改 D1 规则
用户选“导入”：D1 -> Processing
第二次点击“保存”：不再获得第二次执行资格
宿主导入失败：结算为失败，不能因为下载完成就显示导入成功
```

下载状态没有 downloads SQL 表；文件可能留存而内存操作已失去，不能声称跨重启继续选择或断点续传。

### 连续追问与可能方案

如果用户要大文件续传，需要服务器支持 Range/版本验证，还要保存来源身份、ETag/摘要、已收字节、暂存身份和冻结规则。代价是磁盘配额与过期清理；来源内容变化重新下载，失败不能拼接成看似完整文件。若导入可能产生副作用，还应保存独立 import operation ID，不能用“下载 D1 已完成”当导入只执行一次的证据。

## 完整业务推演：插件停用时页面还在下载

1. 已验证插件定义建立 I1，绑定进程generation4，下载 D1 冻结规则。
2. 停用/卸载先关闭该插件全部实例，再停止进程。最后实例关闭后的延迟停机与再次打开有竞争，需要取消旧停机意图。
3. D1 后续结果核对原实例/操作身份，不能借用重建的 I2 权限。物理文件是否保留按下载处理责任判断，不能扫同名目录任意删除。
4. Windows/Linux/macOS 按插件隔离持久 Web profile；未适配平台存在共享默认存储回退与告警，不能一概宣称全部平台登录态完全隔离。
5. 原生嵌入不支持时可以退为独立窗口；这改变呈现，不应扩大 bridge 权限。

## 脱离案例自测

**问题链：为什么 URL 白名单不够 → 为什么 generation 也不够 → 为什么还要 operation ticket → 下载重复点击如何只执行一次 → 进程崩溃后是否仍然成立？**

<details><summary>分析提示与参考思路</summary>

URL 控制内容来源，registry 控制实例归属，generation 控制进程版本，ticket 控制具体异步动作，下载状态转移控制本实例内结算。它们保护不同维度，不能互相省略。崩溃后内存去重失效，若需跨重启保障就持久化操作身份和结果；文件存在不是成功回执。验证应覆盖打开中关闭、迁移中关闭、重建后旧回调、导航中下载、重复选择、宿主动作失败及旧代页面调用新进程。
