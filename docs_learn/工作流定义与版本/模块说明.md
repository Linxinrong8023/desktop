# 工作流定义与版本

## 编辑画布时，已经开始的任务应该听谁的？

用一个贯穿两篇工作流教材的案例：F 是“修复重复重试”。入口给出问题，分析节点 A 找原因，修改节点 B 产出补丁，检查节点 C 判断测试，最后 O 汇总。运行 R 已经走到 B，用户把草稿里的最大重试次数从 2 改成 5。如果 B 继续读最新画布，A、B、C 可能实际执行了三个不同版本。

整体设计：Workflow 提供稳定业务身份，draft 允许修改，发布生成不可变 snapshot，Run 固定引用其执行版本。保存、发布、部署、启动分别证明不同条件；运行时从已固定的图推导可达执行子图，不把画布上所有备用节点都当任务。

## 为什么不写一个 SOP Skill 就够了？

Skill 可以包含指令、参考资料和脚本，也可以指导调用 MCP，不能把它说成“只能提示、不能执行”。区别在流程推进责任：SOP 由 Agent 或配套脚本解释执行；当前 Workflow 由宿主根据持久节点状态、依赖和分支推进。

| 条件 | SOP Skill 可以做到 | 当前 Workflow 额外承担 |
| --- | --- | --- |
| 固定流程说明 | 文件版本化、脚本步骤 | 发布快照与 Run 明确关联 |
| 需要人确认 | 指令要求 Agent 发问 | 持久等待状态、统一完成入口 |
| 重启后继续分析 | Agent 历史或脚本自行恢复 | NodeRun/轮次账本支持确定性调度判断 |
| 公司系统调用 | Skill 引导 MCP 或脚本 | 节点配置与结果组织；连接器仍需真实存在 |

**连续追问：那简单单 Agent 任务也该套工作流吗？** 不必。增加节点会增加交接、模型调用和配置成本。适合反复执行、需要显式责任与恢复的流程；临时探索由单 Agent 加 Skill 可能更合适。固定快照也不保证模型每次生成相同结果，不能把流程稳定宣传为答案确定。

## 为什么不只给工作流加一个 version 字段？

### 直观方案为什么不够

在同一行 graph 上递增 version，能知道“现在是第几版”，却无法重建旧 R 实际读到的图。给每次鼠标移动都保存完整不可变版本，又产生大量无业务含义的发布记录。当前把编辑保存和执行承诺分开。

### 当前实现与数据演算

**当前实现**：创建 F 与初始 draft 在同一事务完成。draft 原位更新。发布复制 draft，生成新的快照，并在事务中移动 published 指针。版本名在同一工作流的未删除快照中唯一。

以下 graph 用 G1/G2 表示完整 JSON 文档的内容摘要，生产列里保存的仍是 JSON 文本，不是字符串 G1。

| 时刻 | `workflows` | `workflow_snapshots` | `workflow_runs` |
| --- | --- | --- | --- |
| 创建 | F, published=NULL | D, workflow_id=F, version=draft, graph=G1 | 无 |
| 发布 v1 | F, published=V1 | D=G1；V1/version=v1/graph=G1 | 无 |
| 部署 R | 不变 | 不变 | R, workflow_id=F, snapshot_id=V1, workspace_id=W |
| 编辑重试条件 | published 仍 V1 | D=G2；V1 仍 G1 | R 仍 V1 |
| 发布 v2 | published=V2 | V2=G2，V1 保留 | R 仍 V1，新运行才选新发布版本 |

因此，诊断 R 时先沿 `snapshot_id` 找 V1，再结合它的 NodeRun、变量池、Session 历史，不能打开当前 draft 就判断“当时不该这样”。

**边界与缺口**：固定 graph 不会自动冻结世界。插件升级、外部 API 数据、模型服务变化仍可能影响执行。部署保存技能实际交付路径等回执，缩小可变依赖，但不等于整个操作系统和模型都可重放。

### 连续追问：不可变快照能保证可重复吗？

先说它保证定义稳定，再分别检查代码版本、模型、凭据、外部数据和文件基线。需要更强复现实验时，**可能方案**是执行清单：snapshot digest、包版本/摘要、模型确认、工作树提交、输入数据版本及工具合同。它需要新增清单或 payload 版本，并付出存储、版本保留和隐私成本；依赖不可获得时明确标记不能复现，不能偷偷替换后声称同一次实验。

## 保存、发布、部署和启动为什么要分层验证？

### 场景与最直观方案

用户编辑一半时，图还缺连线或角色配置。如果保存必须满足运行所有条件，画布无法保留半成品；如果发布完全不检查结构，团队得到一个看似可用却无法解析的版本。

### 当前实现与演算

**当前实现**：草稿可表达编辑中的状态；发布验证稳定 ID 和可发布结构，数据库适配器在发布事务内再次验证，防止并发草稿写入让早先验证失效。执行分析先验证文档身份和归属，从入口提取可达节点，再解析实际执行配置。部署检查角色、技能交付前提；启动检查可执行节点及图规则；会话 setup 再检查当前 MCP 安装与配置。

假设 G1 有 `Start→A→B→C→O`，旁边放备用节点 X，X 有过期角色配置但不在入口可达路径。完整快照保留 X；执行投影不派发 X，不为它创建会话或收集运行前依赖。来自备用区域的连线也不能凭画布存在就阻塞可达节点的执行前提。身份和归属等文档约束仍要检查，不能把“未执行”理解为任意坏文档都可忽略。

| 检查通过 | 实际证明 | 仍可能在后面失败 |
| --- | --- | --- |
| draft 保存 | 编辑内容被保存 | 发布结构不合法 |
| 发布 | 结构满足发布要求并固定 | 所需角色/技能不可用 |
| 部署 | 工作区与交付前提成立 | provider 当前不可用 |
| 启动图校验 | 执行图结构、节点类型可运行 | MCP 配置变更、模型调用失败 |

Start、Agent、Condition、Output、Loop、Iteration 已有执行实现；Prompt、Tool 等“类型可识别”不等于能运行。Loop 内外各是 DAG，不是允许任意画布有向环。

### 连续追问：事务内再验证有什么价值？

t0 读取 D=G1 并验证，t1 另一个编辑保存 D=G坏，t2 发布若只复制当前 D，就把未验证内容发布了。事务内对实际复制内容复核关闭这个窗口。但它不自动解决两个编辑器最后写入覆盖的问题。

**可能方案**：draft 增加 revision，保存带 expected_revision；版本不符返回冲突并保留本地修改。新增字段及冲突内容，代价是合并 UX；自动保存失败保持 dirty，不能把迟到成功响应当成最新编辑已保存。前端已有防抖、写入串行与过期响应防护，跨客户端并发版本协议不能由这些本地机制推导出来。

## 回滚与激活为什么是两种操作？

### 当前实现与完整演算

假设 published=V2，draft=G3，历史 V1=G1。

| 操作 | draft 之后 | published 之后 | 已有 R→V1 |
| --- | --- | --- | --- |
| Rollback 到 V1 | G1 | 仍 V2 | 不变 |
| Activate V1 | G1 | V1 | 不变 |

Rollback 是把历史内容拿回来编辑；Activate 是改变以后选用的发布版本，同时同步 draft。两者都不把正在运行的 R 悄悄搬到新快照。删除 draft、当前发布快照或活动运行依赖的快照受到业务规则限制。

数据库 `workflow_snapshots.workflow_id` 有外键，但 `workflows.published_snapshot_id` 没有同等物理外键；指针正确性依赖业务校验和事务。直接手工 SQL 可制造错属引用，不能以“用了 SQLite”概括所有约束。

### 连续追问：运行失败时必须永远用旧版本吗？

固定版本是默认执行依据，不代表永远禁止显式迁移。当前失败续跑已有切换新发布快照的兼容性检查：核对节点、类型、变量合同及已完成复合区域，先检查再进行文件回滚等动作。它是显式受约束接管，不是每一步偷读当前版本。

**可能方案**：对复杂迁移保存变换计划、旧新快照摘要、保留节点集合、作废结果集合及操作者确认。成本是迁移历史与兼容规则；检查失败保持原 R，不应先改文件再发现无法迁移。

## 完整业务推演：一次发布响应丢失

1. 初始 F 指向 V1，D 已编辑为 G2。客户端请求发布版本 v2。
2. 在事务里读取并验证要复制的 graph，插入 V2，更新 F 指针；两者一起提交。
3. HTTP/IPC 响应丢失。用户仍可能看到“未完成”，但数据库已有 V2，不能盲目说发布失败。
4. 重查版本列表及 F 指针判断事实；同一版本名重试会遇到唯一性检查。这里不存在“重试必自动返回原发布结果”的通用承诺。
5. 新部署 R2 记录 V2，旧 R 继续 V1；画布再修改 G3，不改动这两次运行的依据。

失败窗口从“事务中间状态”转移到“提交已发生而客户端不知道”。**可能方案**是发布 request ID 与输入摘要去重回执，存于新操作记录；多一份结果保留责任，但可安全查询原请求。若相同 request ID 带不同输入应冲突，而不是覆盖。
