# 工作流执行与恢复

[返回学习导航](../README.md)

> 核对日期：2026-09-23。代码基线：`6660767f`。文中的短 ID（S、W、R 等）是便于阅读的示例代号，不是可直接写入所有生产接口的合法标识。数据表仅投影本节相关列，省略列不代表不存在。
> **当前实现**来自本地生产路径；**边界与缺口**区分明确行为与阅读推断；**可能方案**均未宣称已实现。测试入口是证据索引，不代表本次全部运行。

## 同一张图，为什么重启后不能简单“从头再跑”？

延续版本模块的 F：S0 入口，A 分析原因，B 修改代码，C 检查，O 汇总。进一步让 A 后面并行跑 B 与审查节点 D，二者汇合后再到 C。B 已改文件、D 已提交审查报告，此时应用崩溃。从头执行会重复副作用，从内存下一步继续则已经丢失进度。

整体设计：Run 引用固定快照，NodeRun 记录实际执行尝试；调度根据持久节点状态、变量和分支重新推导。节点完成与输出/分支事实一起提交，外部 Agent 执行放在事务和串行 gate 之外。恢复不是一个动作，而是识别中断、保留证据、确定作废范围、选择文件恢复策略，再显式续跑。

## 为什么 ready 集合要从持久事实推导？

### 最直观方案与问题

内存维护“下一个节点队列”，每收到完成通知就把后继塞进去，简单但怕重复通知、乱序和重启丢队列。只看一个前驱成功就派发汇合节点，又会在另一个输入未准备好时执行。

### 当前实现与完整演算

**当前实现**：调度器依据固定图、已提交 NodeRun 与分支决定推导 ready 集合。同一 R 的状态转移串行提交，独立异步节点可并行工作；不会持有该串行入口等模型返回。尚未开始的节点没有 NodeRun 行，UI 的“未开始”是对图与实际记录的差集。

| 波次 | 当前数据库事实（状态码：1运行、2成功） | ready / 动作 |
| --- | --- | --- |
| 1 | 入口成功 | A 可开始，创建 NA/status=1 |
| 2 | NA/status=2，分析变量已提交 | B、D 同时可开始，创建 NB、ND |
| 3 | NB/status=2，ND/status=1 | C 仍不可开始 |
| 4 | NB、ND 均成功且输入就绪 | C 可开始 |
| 5 | C 的分支选择及完成已提交 | 只推进选中路径；不把未选分支当失败依赖 |

R 在 `workflow_runs` 保存 snapshot_id、run_status、state/input/output 等；NodeRun 在 `workflow_node_runs` 保存 node_id、scope_id、status、session_id、input/output/error/payload。完整对话归 Session JSONL，节点 output 是最终助手文本，校验后的结构化结果进入所属执行变量池。表里没有每个流式 token 的工作流副本。

### 连续追问：重复收到 NB 完成是否会运行两次 C？

依赖判断必须读取已提交状态，完成提交还要核验节点仍处于允许转移状态，不能让迟到回调复活终态。新的 scope/尝试身份把旧执行与新执行分开。它减少重复调度，但还不能证明 C 调用的外部服务恰好执行一次，后面继续拆这个问题。

**可能方案**：当扩展到多调度器实例时增加租约、所有者代次及条件写入。新增 run lease/epoch，成本是续租、时钟和过期恢复；失去租约后停止派发，迟到结果依据代次拒绝。当前进程内 run gate 不能被宣传为分布式锁。

## 为什么“保存结果”和“标记成功”必须一起做？

### 场景与当前设计

B 返回 `{"changed":true,"tests":"pending"}`。若先把 status 改成功再保存结果，崩溃后 C 看到 B 成功却没有输入；反过来，先存结果后改状态，恢复可能又执行 B。

**当前实现**：仓储将节点完成、结果变量、Condition 决定等相关状态按对应事务一起提交。下面展示逻辑变化，`state` 的省略号表示该所有者的 JSON 投影，不是完整可导入记录。

```text
提交前
workflow_node_runs: NB {status:1, output:null, scope_id:ROOT1}
所属变量池: 尚无 B 的有效输出

同一个完成事务
workflow_node_runs: NB {status:2, output:"已修改重试逻辑", finished_at:t1}
所属变量池: B.changed=true, B.tests="pending"
相关分支事实: 只有 Condition 完成时才写入其选择

提交后
发送 WorkflowRunInvalidated {run_id:R}，观察者重新查询
```

广播发生在提交之后。通知丢失可能让界面暂时陈旧，但不能让数据库回到运行中；前端用后续事件、刷新和轮询补偿，不根据事件内容独立拼一份业务真相。

### 连续追问：外部操作已成功，数据库提交失败怎么办？

这是不同失败窗口。若 B 已创建远程工单 X，回调准备把 NB 改成功时数据库失败，原子事务只保证本库状态不半成。它不能撤销 X，也不能知道 X 未发生。重新执行 B 可能创建 X2。

**边界与缺口（确定的保证范围）**：当前没有覆盖任意工具的通用 exactly-once 协议。Agent Runtime 的停滞重试也可能重新产生工具调用。Git checkpoint 只对文件状态提供恢复素材，不撤销网络请求。

**可能方案：外部副作用账本。** 解决跨本库与外部系统的未知结果。派发前保存稳定操作键、规范输入摘要、所属 NodeRun/尝试及状态，外部调用带幂等键；成功后保存回执，再完成节点。新增示意记录（**不属于当前数据库**）：

| operation_id | logical_step | input_digest | state | receipt |
| --- | --- | --- | --- | --- |
| OP1 | R/B/create-ticket | h1 | unknown | NULL |

恢复时用 OP1 查询或重试同一请求，不能换 OP2。成本是外部 API 必须支持幂等/查询，以及记录保留、超时与重复 ID 冲突管理。若外部只支持不可查询的非幂等调用，Unknown 需要人工确认或业务补偿；outbox 可以保证派发责任不丢，但单靠 outbox 不能消除接收方重复执行。

## Loop 与逐项遍历为什么需要两套轮次语义？

### 问题与最直观方案

“遍历三个文件”每轮输入来自数组；“修改到测试通过”为下一轮反馈当前结果。把两者都写成 node_id→最新结果，会覆盖旧轮证据，分支没产出时还可能误读上一轮值。

### 当前实现：Iteration 的逐项账本

输入 `files=["a.ts","b.ts","c.ts"]`，I 的 region 包含检查节点 Q，collect 指向 Q 的结构化结果。轮次串行，区域内部可以有并行分支。`workflow_node_runs.iteration` 是从 **0** 开始的逐项索引；外层行是 NULL。

| 行 | node_id | iteration | scope_id | status | 说明 |
| --- | --- | --- | --- | --- | --- |
| NI | I | NULL | ROOT1 | 1 | 外层容器 |
| NQ0 | Q | 0 | ROOT1 | 2 | a.ts 成功 |
| NQ1 | Q | 1 | ROOT1 | 3 | b.ts 失败 |
| NQ2 | Q | 2 | ROOT1 | 2 | 仅 continue 策略下继续 |

启动一轮时 item/index 与首批行一起提交；结算轮次账本和后续推进也有对应原子边界。完成暴露 `output`、`entries`、`failed_count`，错误策略不改变输出类型。continue 下上例失败数为 1；fail 下在 b.ts 停止，不能出现 c.ts 的执行。空数组成功；输入非数组、超过安全上限等容器自身错误不能靠 continue 吞掉。若分支绕过 collect 目标，该轮失败，不借用 Q 上一轮输出。

### 当前实现：Loop 的独立作用域

Loop L 表示最多 3 轮修复，每轮依据同一份已完成变量池计算反馈与终止条件。`workflow_execution_scopes` 每轮有独立 scope，round_index 从 **1** 开始；不是上面的 iteration=0。根 scope 由 `workflow_run_root_scopes` 指向。

| 表 | 关键投影 | 作用 |
| --- | --- | --- |
| workflow_execution_scopes | ROOT1, run_id=R, parent_loop_node_run_id=NULL | 根执行身份 |
| workflow_execution_scopes | LROUND1, run_id=R, parent_loop_node_run_id=NL, round_index=1, status=2 | 第一次 Loop 的池与状态 |
| workflow_execution_scopes | LROUND2, run_id=R, parent_loop_node_run_id=NL, round_index=2, status=1 | 第二次独立池 |
| workflow_node_runs | Q1, node_id=Q, scope_id=LROUND1 | 第一轮 Q |
| workflow_node_runs | Q2, node_id=Q, scope_id=LROUND2 | 第二轮 Q，不覆盖 Q1 |

数据库限制同一父 Loop 同时只有一个活跃轮；作用域身份不可修改。内外分别是 DAG，拒绝不支持的嵌套复合结构和跨域连线。Loop 最大轮次在 1–100 范围内。

### 连续追问：同时更新两个反馈变量为什么要从同一池读取？

假设反馈规则 `x_next=y, y_next=x`，本轮 x=1,y=2。依次覆盖原池会得到 x=2,y=2，正确的同时反馈应是 x=2,y=1。当前从完成池计算下一轮输入，不原位破坏本轮证据。追问无限收敛怎么办：轮次上限防止无界执行，但不证明业务质量收敛。

**可能方案**：加入质量指标、连续无改进次数及成本预算，保存每轮判据和停机原因。代价是指标可能被模型输出误导；判据解析失败按失败处理，不能默认“已通过”。验证应包含振荡、无进展、空产出、最后一轮通过和越界。

## 崩溃、人工等待、失败续跑分别依据什么恢复？

### 当前实现与失败矩阵

| 中断位置 | 可用证据 | 当前处理/边界 |
| --- | --- | --- |
| 普通 Agent 正在运行时重启 | Running 行、Session 历史 | 启动清扫识别中断，不能把旧进程当作仍在执行 |
| Iteration 某轮子节点中断 | iteration、容器、轮次账本 | 中断轮失败后交给容器策略；continue 可推进下一项，fail 停止 |
| 人工节点等待输入 | 持久等待状态、Session 绑定 | 等待可被查询；追问与完成走统一 gate 并核验终态 |
| 异步 Session 创建晚于取消 | 节点已终态 | 迟到绑定不能发布并复活节点 |
| 失败后用户续跑 | 失败/取消集合及后继 | 软删作废尝试，保留不需作废的成功证据，重新推导 |
| 复合节点失败后续跑 | 容器整体范围 | 当前按容器作为续跑单位，从第一轮重新开始，不支持任意内部断点续跑 |

根节点失败后停止新派发，已经运行的兄弟可以收尾；Loop 内部失败有同轮取消和上抬边界。因此“失败”时仍要检查兄弟副作用，不能假定所有工作同一时刻停止。

### 文件回滚为什么不是恢复的默认同义词？

节点前尽力建立 Git checkpoint，保存可获得的文件变化与 checkpoint 错误。创建 checkpoint 失败不阻止执行。续跑可选择保留文件、恢复失败节点文件或恢复整个检查点；要检查并行兄弟修改和复合范围，回滚前再做备份 checkpoint。不安全选项明确禁用。

演算：B 修改 x.ts 后失败，D 同时修改 y.ts 并成功。恢复整个旧检查点可能抹掉 D 成果；只恢复 B 文件还需核实 D 是否也动过 x.ts。不能仅凭“B 失败”就递归清工作树。切换新快照还需先过兼容性检查，避免文件已回滚但版本不能接管。

**可能方案**：更细的文件修改归属或隔离每节点工作树，保存基线、补丁与合并回执。成本是存储与冲突处理；合并失败保留各节点产物，人工处理，而非自动挑一个版本。它仍不能回滚邮件、工单或远程数据库。

## 完整业务推演：从派发到失败续跑

1. R 固定 V1，ROOT1 为当前根 scope。部署回执冻结技能实际路径；节点 MCP 白名单会保存在其 Session 上。
2. 调度提交 NB、ND Running，再在 gate 外启动 Agent。prompt 接纳后才发布 session_id；并发取消赢了则拒绝迟到发布。
3. D 完成，结果和状态一起保存。B 工具改文件后输出结构不合法：NodeRun 留最终原文/失败详情，完整过程在 Session 历史。
4. 失败阻止新派发 C，但检查已经工作的兄弟是否收尾。失效事件通知前端重读状态，事件不是提交证明。
5. 用户选保留 D，恢复 B 相关文件并续跑。先核验 checkpoint、变更范围和快照兼容；再作废应清除的尝试及后继，保留历史用于诊断。
6. 重建 ready 集合，产生新尝试。若 B 曾发远程请求，用户仍需依据外部凭据决定能否重试；当前数据库成功记录不能替代外部对账。

## 脱离案例自测

**第一条追问链：为什么结果必须事务提交 → 事务失败了外部请求是否撤销 → 加 outbox 是否就 exactly-once → 对方无幂等接口怎么办 → 怎样验证？**

<details><summary>分析提示与参考思路</summary>

本地事务保护 NodeRun 与变量一致；外部已发生的副作用不在事务内。outbox 防丢派发责任，接收方仍需幂等或收件箱去重。无幂等/查询时，业务要选择重复风险、漏做风险或人工确认，不能承诺两者同时消失。测试在“远端成功、本地未知”窗口注入断连，用真实副作用计数而不是只检查状态机最终绿灯。还要测试相同键不同输入冲突和去重记录过期后的风险。

</details>

**第二条追问链：为什么每轮隔离 → 第二轮分支没产出如何处理 → continue 会不会隐藏失败 → 重启后会不会重跑第一轮 → 手动续跑是否从第二轮开始？**

<details><summary>分析提示与参考思路</summary>

隔离避免复用旧变量；collect 未执行应结算失败。continue 必须保留 entries 与 failed_count，让下游决定是否容忍部分结果。自动引擎重建从持久账本恢复，不重复已完成轮；它和用户对失败复合容器发起续跑不同，后者当前以整体为单位重做。回答时区分 Iteration 的 0-based iteration 与 Loop 的 1-based round_index，不能把两者说成同一个游标。验证要覆盖中断轮、已结算轮、空数组、分支绕开收集和旧回调晚到。

</details>
