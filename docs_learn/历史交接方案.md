# 历史交接方案

> 整理日期：2026-09-23。本文记录本次讨论收敛后的设计，供后续实现与审查使用，不表示文中的机制已经全部实现。字段、状态和数值示例均为设计示意，最终命名应在实现时与现有契约统一。
>
> 核心策略：Ora 保留可获取的原始历史，维护自己的压缩摘要。真正切换 Agent 时，以“最新有效摘要＋保留点之后的原文”交接。Agent 内部发生压缩，可以触发 Ora 检查是否需要整理历史，但不要求 Agent 返回它的内部摘要。

## 1. 要解决的问题与设计边界

用户可能因为 Agent 反复尝试仍无法解决问题，或者账号额度即将耗尽，希望换一个 Agent 继续同一项工作。新 Agent 不仅需要看到当前文件，还需要知道用户约束、已经作出的决定、修改原因、失败尝试和未完成事项。

直接把所有历史交给新 Agent，会遇到三个问题：

1. 历史持续增长，最终可能超过目标 Agent 或压缩模型的输入窗口。
2. 每次从头总结成本高，用户只是临时切换一下选择器，也不应该因此付费总结。
3. 摘要会丢失细节；缺少回查机制时，新 Agent 无法核实摘要中的结论。

本方案用增量摘要减少重复处理，用延迟交接避免无效调用，用原始历史查询补充细节。

设计范围包括历史组织、摘要生成、切换准备和异常恢复。它不承诺新 Agent 一定比原 Agent 更强，也不承诺摘要无损恢复原 Agent 的所有内部状态。

## 2. 先区分四个对象

| 对象 | 含义 | 谁管理 |
| --- | --- | --- |
| Ora session | 用户看到的同一段持续对话，切换 Agent 后身份保持不变 | Ora |
| Agent 原生 session | 某个 Agent 自己维护的会话和运行状态 | 对应 Agent，Ora 保存必要绑定 |
| Ora 历史 | Ora 实际接收到并保存的用户消息、回复、工具信息等 | Ora |
| Ora 摘要 | 从历史中生成、服务于后续交接的压缩记录 | Ora 的交接机制 |

Ora 历史与 Agent 内部上下文不完全相同。Agent 可能有系统提示、内部状态、未暴露的信息和自己的压缩策略；Ora 只能保存自己可获取的内容。本文所说的“保留完整历史”，指保留 Ora 已经获取的原始记录，不代表拥有 Agent 未暴露的全部内部信息。

另外，以下两个事件要明确区分：

- **Agent 内部压缩**：Agent 为继续当前会话整理自己的上下文。
- **Ora 历史压缩**：Ora 生成一份用于跨 Agent 交接的摘要，并保留原始历史。

二者可以在触发时机上关联，但产物、覆盖范围和用途各自独立。

## 3. 历史存储：正文在 JSONL，元数据在数据库

### 3.1 存储职责

沿用 Ora 当前的基本分工：数据库记录 session 身份、归属和运行绑定等元数据；对话正文按 session 保存到 JSONL 文件。

计划参考 Pi 的记录组织方式，为历史条目建立稳定 ID、父记录关系和明确的压缩边界。参考的是这种组织思路，不是声称 Ora 当前已经实现了 Pi 的所有字段和行为。

| 内容 | 本方案中的存放位置 |
| --- | --- |
| session 元数据、Agent 绑定等 | 数据库 |
| 用户消息、Agent 回复、可获取的工具调用及输出 | session 的历史 JSONL |
| Ora 生成的摘要及覆盖边界 | 同一 session 的历史 JSONL |
| 交接尝试及交接成功记录 | 通过历史或运行状态的结构化记录保存，具体契约待实现 |
| 图片和附件 | 沿用现有资源存储；摘要只放可解析的引用和必要说明 |

**本版不采用单独的摘要数据库表作为摘要正文的主存储。** 如有查询性能需要，数据库可以维护可重建的索引，但不能形成与 JSONL 内容互相冲突的第二份摘要事实来源。

### 3.2 一行 JSONL 不等于一整轮对话

JSONL 只是“一行一条 JSON 记录”的文件形式，不规定一次 prompt 或一次完整回复必须占一行。

Ora 当前的历史保存会整理流式片段、消息和工具状态，不能简单理解为每个 ACP notification 都直接占一行，也不能理解为整个 turn 只有一行。新增摘要类型时应保留现有历史的读取语义，不能直接把物理文件行号当成逻辑消息编号。

同一逻辑条目可能在后续追加更正。因此，压缩应读取历史模块还原出来的有效记录，而不是直接把所有物理行原样拼进 prompt。固定处理范围时，也不能只记一个最大序号，忽略较早条目的后续版本。

### 3.3 压缩不删除原文，也不自动成为普通聊天气泡

生成摘要后，旧消息仍然可查询。摘要只是为后续输入提供一个更短的入口，不是替换或销毁历史。

摘要使用独立的记录类型。普通历史加载可以将它显示为一个可展开的“已整理历史”事件，或者由产品决定默认隐藏；不能因为它存在同一文件，就自动当成用户或 Agent 的普通发言渲染。

同样，交接时注入目标 Agent 的文本，应带有可识别的来源或关联信息，避免被回显后再次当成新用户内容收入历史，造成摘要反复嵌套。

## 4. 摘要必须记录哪些边界

只保存摘要文本不够。Ora 还需要知道这份摘要适用于哪条历史路径，处理到哪里，以及哪些原文要继续保留。

建议记录以下语义，字段名仅为示意：

| 字段 | 作用 |
| --- | --- |
| `id` | 摘要记录自身的稳定标识 |
| `type` | 区分摘要、普通消息、工具记录等 |
| `parentId` | 摘要记录在历史路径上的父记录，不等于摘要覆盖终点 |
| `sourceHeadId` | 生成摘要时固定的源历史末端 |
| `sourceRevision` | 读取源历史时的版本或等价快照凭据，识别旧条目的后续更正 |
| `previousSummaryId` | 本次使用了哪份旧摘要；首次生成时为空 |
| `firstKeptEntryId` | 源历史中第一条需要保留原文的消息 |
| `summary` | 压缩后的交接摘要正文 |
| `createdAt` | 摘要生成时间，按项目约定记录本地时间 |
| `generator` | 使用的生成方式、服务或模型，便于诊断成本与质量 |

这些边界由 Ora 根据实际输入确定和校验，不能仅相信模型在输出里自行声称“我已经总结到了某条消息”。

`parentId` 用于组织历史关系；`sourceHeadId`、`sourceRevision` 和 `firstKeptEntryId` 用于说明摘要处理范围。前者不能替代后者。

如果某次摘要覆盖全部已选源记录、不保留源范围内的原文，应显式表达“无保留尾段”；此后新产生的消息仍需接在摘要之后。具体可使用专门的边界类型，不要让空值同时代表“不知道保留点”和“没有保留尾段”。

选择“最新摘要”时，实际应选择**当前历史路径上最新且仍有效的摘要**。其他分支的摘要、覆盖了错误版本的摘要、未完整保存的摘要都不能只因为创建时间较新就被选中。

## 5. 交接内容的唯一拼接规则

```text
没有有效摘要：
  当前路径上可用于交接的原始历史

有有效摘要：
  最新有效摘要 S
  + 从 S 的保留点开始，到当前截止位置的原始消息
```

这里的“原始消息”指还原后的有效用户、Agent 和工具记录等，不包含再次展开的旧摘要，也不重复加入历史里的交接注入文本。

### 5.1 第一次压缩

```text
原始历史：m1 … m80 | m81 … m100
                    ↑
                  保留点

摘要 S1：概括 m1 … m80
本次源历史截止：m100
保留原文：m81 … m100

此时可用于交接的内容：
  S1 + m81 … m100
```

在这个例子中，`sourceHeadId = m100`，`firstKeptEntryId = m81`。两者并不矛盾：本次处理看到了 m100，但选择让 m81 到 m100 继续以原文保留。

### 5.2 又产生了新消息

```text
新产生：m101 … m120

此时可用于交接的内容：
  S1 + m81 … m120
```

不要写成 `S1 + m81 … m120 + m101 … m120`。保留点之后的原文已经包含新增消息，再拼一次会重复。

### 5.3 再次压缩

```text
本次输入：S1 + m81 … m120

生成摘要 S2：在 S1 基础上吸收 m81 … m110 的有效进展
新的保留点：m111
本次源历史截止：m120

新的可交接内容：
  S2 + m111 … m120
```

S2 延续 S1 中仍有效的事实，并吸收后续变化；后续明确撤销或修改的决定要替换旧结论。原始 m1 到 m120 和旧摘要 S1 仍保留，供回查与诊断。

## 6. 两条执行路径：是否有独立压缩服务

这里的“有服务”指已经启用且当前可调用的独立压缩能力，可以由 Ora 官方提供，也可以由用户配置 API Key 和模型。仅仅填写了配置但服务不可用，不等于本次压缩一定可执行。

| 情况 | 平时如何处理 | 真正交接时如何处理 |
| --- | --- | --- |
| 独立压缩服务可用 | 按触发条件后台增量生成摘要 | 优先复用；超过输入预算时再补做压缩 |
| 没有独立压缩服务 | 不做后台 LLM 总结，可做确定性的整理和大小估算 | 能直接交接就直接交接，否则尝试原 Agent 或独立临时会话 |
| 服务已配置但暂时失败 | 保留旧摘要和全部原文，记录失败状态 | 直接交接、其他可用执行方或明确失败，取决于当时输入大小与能力 |

不配置独立服务，不等于禁止切换 Agent；它意味着不能依靠独立服务提前摊平长历史的整理成本。

## 7. 有独立服务时，怎样触发后台压缩

### 7.1 主要信号：Agent 自己发生上下文压缩

当适配器可靠地向 Ora 暴露“发生了上下文压缩”的事件时，Ora 标记一次“需要检查历史整理”。

这只依赖事件，不要求获得 Agent 内部的压缩摘要，也不把该摘要自动当作 Ora 的交接记录。不同适配器是否支持、暴露的是开始还是完成事件，应由适配层明确标识，不在业务层猜测。

收到信号不立即打断当前 Agent，更不向它正在执行的会话插入总结指令。采用简单策略：等当前 turn 到达稳定结束边界后，检查是否有足够新增内容，再决定是否启动后台任务。

如果一个 turn 异常结束，只有在确认其运行已停止、已有历史已整理为可读取状态后，才把它作为一次可处理边界；不能把短时间没有新通知当作 turn 已结束。

### 7.2 兜底信号：待处理历史增长过大

Ora 历史和 Agent 内部上下文大小并不一致，例如 Agent 已截断工具输出，而 Ora 保存了更长的原始结果。因此，即使没有压缩通知，也需要检查自上次摘要以来的新增内容规模。

当新增待处理内容超过设定阈值，也可以申请一次后台压缩。阈值优先依据预处理后的体积或估算 Token，而不是只看消息条数：一条很长的工具输出可能超过几百条短消息。

具体阈值暂不在本文写死，应结合所选模型的输入窗口、成本和实际历史样本确定。

### 7.3 合并重复触发

对同一个 Ora session：

1. 没有足够新增内容，跳过。
2. 已有任务处理同一范围，复用该任务。
3. 任务运行期间又发生压缩事件，只标记还有待检查内容，不并发重复总结同一范围。
4. 当前任务完成后，重新检查剩余新增内容，未达到阈值就等待下一次触发。

不因每条消息、每次切换选择器或每个重复通知都调用一次 LLM。

### 7.4 固定快照，成功后发布

```text
收到触发信号
  → 等待 turn 结束并整理历史
  → 检查新增量与已有任务
  → 固定源历史范围及版本
  → 读取旧摘要和需要处理的原文
  → 独立服务生成候选摘要
  → 校验范围、输出大小和必要结构
  → 持久保存新摘要
  → 将其作为后续可选的有效摘要
```

后台任务运行时允许后续对话继续，但摘要只声明覆盖它实际读取的快照。后续产生的消息留在摘要之后。若旧记录发生更正，需要识别其是否影响摘要有效性，补做处理或作废候选结果，不能假装已经覆盖。

## 8. 真正切换时才准备交接

### 8.1 选择 Agent 与执行切换分开

```text
当前由 A 工作
  → 用户在选择器选 B
  → B 只是待使用的 Agent，不生成交接摘要

如果用户没有发消息，又选回 A：
  → 继续 A，不产生由这次选择导致的总结调用

如果用户第一次向 B 发送消息：
  → 开始交接准备
```

独立后台压缩可能因历史增长而恰好发生，但它与用户单纯点击选择器是两件事。

### 8.2 首次向 B 发送消息的顺序

1. 确认 A 的上一 turn 已结束，固定交接历史范围。
2. 暂存用户这次发给 B 的新请求，保留它的独立身份。
3. 查找可复用的摘要或已完成交接结果，组装候选交接内容。
4. 检查整份目标请求的预算，包括交接内容、用户新请求及可知的其他开销。
5. 内容足够短就直接使用；需要压缩才调用合适的执行方。
6. 保存生成结果和交接尝试的关联信息。
7. 准备 B 的会话，在同一工作区注入交接信息，并提交用户的新请求。
8. 确认 B 的请求已按协议进入可跟踪的执行状态后，提交本次绑定变化，释放 A 不再需要的运行资源。

新请求应清楚地位于历史之后，不能在总结时被揉成“以前已经执行过的任务”。它可以提前作为待处理消息持久保存，但构建交接历史时须排除，再作为本次请求单独提交一次。

“写进 stdin”不等于“目标已成功接收并执行”。具体确认点需要依据适配器协议定义；无法确认时进入可恢复状态，不能盲目重复发送可能产生副作用的请求。

### 8.3 为什么 A 还能总结

用户选中 B 时，不立即销毁 A。真正向 B 发起请求后，如果选择由 A 总结，则先让仍保留的 A 完成总结，再推进切换。

“释放 A”指释放当前交接不再需要的运行资源，不等于删除它的原生会话历史，也不等于杀死可能被其他 Ora session 共用的整个 Agent 进程。

## 9. 需要总结时，由谁执行

### 9.1 独立压缩服务可用

由独立服务读取 Ora 选定的历史快照，在独立请求中总结，不占用当前业务会话的上下文。后台压缩和切换时补做压缩使用同一套历史选择、预算和摘要记录规则。

### 9.2 没有独立服务，原 Agent A 仍可用

优先让 A 在当前会话中生成交接摘要。A 已经掌握当前任务上下文，通常不需要再次把 Ora 全部历史灌给它。

本次指令明确要求总结当前目标、约束、已完成工作、失败尝试、未完成事项和证据引用；不继续执行开发任务。执行期间限制修改类工具，必要时仅允许读取历史或其他明确需要的只读工具。

但 A 对自身上下文的总结不等于它重新核对过全部 Ora 历史。若较早信息不在其可见上下文中，应通过历史查询补充；不能声称总结一定包含所有原始细节。

### 9.3 A 已没额度、进程不可用或总结失败

如果 B 支持独立临时会话，并且当前有可用额度，可以用 B 的临时会话处理选定的 Ora 历史。压缩完成后，再把结果交给 B 的正式工作会话。

临时压缩会话与正式工作会话必须隔离，避免把全部分块、中间摘要和总结指令累积到正式上下文里。完成或失败后清理临时资源。

这是按能力启用的兜底，不假设每个 Agent 都支持。没有可用执行方且内容又不能直接交接时，明确提示原因，保留原历史、已有摘要和未发送的新请求，允许用户配置服务或稍后重试。

分块只是处理输入大小的方法，不会凭空提供模型额度。所有执行方都不可用时，不能靠“再分块”完成压缩。

## 10. 超长历史的预算与分块策略

### 10.1 两道预算检查

第一道检查针对压缩请求：压缩模型必须能容纳压缩指令、输入历史、必要元数据和预留输出。

第二道检查针对交接请求：摘要、保留原文、资源引用和用户新请求一起进入目标 Agent，不能只检查摘要正文是否够短。

```text
压缩输入预算
  = 压缩模型窗口
  - 总结指令及请求开销
  - 预留输出
  - 安全余量

交接内容预算
  = 为目标适配器设定的安全输入预算
  - 用户新请求及可知的其他开销
```

能够使用所选模型的 Token 计数能力时就使用；没有对应能力时采用保守估算和安全余量，遇到上下文超限响应再缩小输入。不能把固定字符比例视为所有模型的精确 tokenizer。

Ora 可以严格约束自己构造的请求；对于目标 Agent 隐藏的系统提示和内部工具开销，仍需由适配层提供能力信息或采用保守边界。限制输出长度有帮助，但不能独自证明整个请求一定放得下。

### 10.2 先做确定性整理，再判断是否分块

规则整理可以减少冗余，但不承担语义总结职责：

- 合并已知属于同一逻辑条目的流式片段和状态更新。
- 去掉重复的协议包装与已识别的回显。
- 将大体积工具结果、图片和附件转成带定位信息的引用，保留关键状态、错误和必要上下文。
- 保留原始记录和查询入口，不以“时间很久”作为直接删除历史的理由。

对于 m101 到 m100000 这样的超长历史，首次整理依然可能有显著成本。提前维护摘要的作用是减少日后重复扫描，不是让第一次处理任意长度历史都变成一次廉价调用。

### 10.3 分块总结与最终合并

```text
待压缩内容放不下
  → 按逻辑消息边界分成 C1、C2、C3……
  → 各块在独立上下文里生成限长结果 D1、D2、D3……
  → 在预算内合并为最终摘要 S
```

优先保持完整的工具调用及结果关联。单条消息本身过大时，需要先将大载荷转为可回查引用，或使用带来源标识的子片段，不能只依赖“按消息切块”。

各块输出保留来源范围、明确决策及其修正关系、失败尝试和未决问题。最终合并时按历史顺序解释变化：后续明确修正覆盖旧决定；无法确认是否被撤销的事项标记为待核实，不能凭空消除冲突。

如果各块结果合起来仍然太大，可在预算允许时做有上限的分组合并。每个输入、输出和合并层级都受约束，不能因为一次放不下而无限“摘要的摘要”。

### 10.4 必须存在的成本上限

| 限制 | 目的 |
| --- | --- |
| 单次输入预算 | 每个压缩调用都有受控大小 |
| 单次输出上限 | 防止局部摘要过长 |
| 最终交接摘要上限 | 为保留原文和新请求留空间 |
| 整个压缩任务的调用次数、Token 或费用上限 | 防止极端历史产生不可控成本 |
| 合并层级和重试次数上限 | 防止无限递归和无限重试 |

输出约束同时放在 prompt 和模型调用参数中，不能只依赖 prompt 自觉遵守。到达上限仍无法生成合格交接内容时，停止并报告，保留原始历史和已有有效结果；不能静默截掉旧历史后声称完整交接成功。

## 11. 摘要应该保留什么

摘要围绕接手任务组织，而不是平均缩短每条消息。建议使用以下内容结构：

1. 当前目标和用户明确提出的约束。
2. 已确认的方案，以及后续被撤销或替换的旧决定。
3. 已完成的修改、相关文件和当前工作区定位。
4. 已运行的验证及真实结果；区分“已验证”和“计划验证”。
5. 尝试失败的方法、错误现象和失败原因，避免新 Agent 重复循环。
6. 未完成事项、阻塞因素和建议的下一步。
7. 关键结论对应的消息、工具结果、图片或附件引用。
8. 不确定、缺失或存在冲突的信息，以及需要回查的位置。

不要求记录所有重复讨论，也不能把旧 Agent 的推测变成既定事实。内部未暴露的思维过程不是本方案成立的前提。

生成摘要时允许利用保留尾段理解前后修正关系，但摘要不能以此声称保留尾段已经被删除或完全替代。尾段仍按边界原样接入，拼接时不重复插入同一条原始消息。

## 12. 图片、附件与历史查询工具

### 12.1 大载荷以引用进入交接文本

摘要中保留资源类型、来源消息、必要说明和可解析标识。例如：

```text
用户在 m57 提供了错误截图，资源标识 image-57。
已确认现象：保存按钮点击后出现错误提示。
精确错误文字仍需读取截图核实，不根据摘要猜测。
```

即使原始历史目前内嵌了 base64，也不应把整段 base64 复制进摘要。资源标识通过 Ora 的读取能力解析，不要求新 Agent 知道数据库文件位置或原始二进制存储细节。

引用只解决定位问题。目标 Agent 仍需要有可用的读取工具和相应内容处理能力；例如没有视觉能力时，不能声称它读到了图片中的全部信息。

### 12.2 工具必须由程序绑定当前 Ora session

历史正文在文件中，因此工具应由 Ora 的历史读取接口提供，不让 Agent 直接操作数据库查正文。

工具名称和 MCP 具体形式尚未确定，但需要具备以下语义：

- 查询当前 session 某段历史，支持分页和返回体积限制。
- 按记录 ID 获取消息或工具结果。
- 搜索相关内容，并返回可进一步读取的定位信息。
- 读取当前 session 可访问的图片和附件引用。

当前 Ora session 的作用域由程序在会话绑定或工具执行上下文中注入。不能仅在 prompt 中写“不要访问其他 session”，也不能相信 Agent 任意传入的 sessionId。

即使工具接受 sessionId，服务端也必须校验它与授权范围一致。Agent 原生 sessionId 不能被当作 Ora sessionId 直接使用。

读取结果也需要分页和限长，否则“回查原文”本身可能再次把上下文撑大。相关内容来自历史证据，应与当前用户指令区分，避免把旧工具输出中的文字当成新的执行命令。

## 13. 连续切换的完整模拟

假设当前在同一个 Ora session 和 worktree 中开发支付重试功能。

| 阶段 | 发生的事情 | Ora 如何处理 |
| --- | --- | --- |
| A 工作到 m100 | A 发生内部上下文压缩 | 收到通知，turn 结束后检查新增量；服务可用则生成 S1，保留点 m81 |
| A 工作到 m120 | 用户只选择 B，未发送消息 | 不因选择产生总结调用，A 的运行绑定尚未正式交接 |
| 用户又选回 A | 仍未向 B 发消息 | 继续使用 A，没有这次切换导致的交接费用 |
| 用户再次选 B 并发送新请求 | 真正开始交接 | 候选内容为 S1＋m81…m120；新请求单独提交 |
| 候选内容在预算内 | 无须再总结 | 将候选内容及新请求交给 B |
| B 继续工作到 m160 | 有新的讨论、修改和验证 | 所有可获取的新记录继续保存在同一 Ora 历史中 |
| B 的压缩事件触发整理 | 满足新增阈值 | 用 S1＋m81…m160 生成 S2，假设新保留点为 m141 |
| 用户真正发请求给 A | 再次交接 | 使用 S2＋m141…m160，并附上本次新请求 |

如果最后一次是恢复 A 的旧原生会话，不能假设 A 自动知道 B 的工作。需要根据 A 上次已经接收的历史边界补齐后续变化；如果无法可靠定位该边界，使用新的 A 原生会话注入完整的当前交接包更容易保证行为清晰。

“复用摘要”与“复用旧原生会话”是两件事。摘要缓存可复用，不意味着把同一段交接文本反复追加到同一个目标会话。

工作区也要随交接保留：B 应使用对应的同一 worktree 路径及当前文件状态，不只接收一个分支名。摘要中的文件说明是理解入口，实际文件和必要检查才是当前状态的依据；未提交和未跟踪文件不能因为 Git 存在就被视为已经备份。

## 14. 失败、取消与恢复

| 情况 | 处理策略 |
| --- | --- |
| 后台压缩失败 | 保留旧摘要和原文；不阻止原 Agent 正常继续 |
| 摘要生成成功但保存失败 | 不将其发布为新的有效检查点；交接保持可重试状态 |
| A 总结失败或额度耗尽 | 尝试可用的独立服务或 B 临时会话；都不可用则明确失败 |
| 用户在准备交接时取消 | 停止未执行的交接步骤；已经成功保存的有效摘要可留作后续复用 |
| B 启动失败 | 保留交接产物与新请求，允许重试，不重新总结同一历史范围 |
| B 是否收到请求不确定 | 保留交接尝试标识并核对状态；不能盲目重发业务请求 |
| 用户在准备期间改选 C | 旧操作完成后不能覆盖新选择；由操作标识或代次校验当前结果是否仍适用 |
| 压缩期间发生历史更正 | 检查快照版本和受影响范围，补做处理或放弃失效产物 |
| 重启时发现文件末尾有不完整记录 | 按历史模块的恢复规则处理，不将残缺摘要视为有效 |
| 历史本身存在已知缺口 | 在交接中说明缺口，不声称摘要恢复了没有保存的信息 |

摘要保存成功和目标请求成功不是一个原子事件，需要分别记录。失败时允许复用已经完成的阶段，不能每次都从头总结，更不能因为总结成功就认定 Agent 已切换成功。

对摘要结果的缓存至少要区分源历史路径和版本、保留边界、摘要策略版本及适用输入预算。没有新消息但旧条目被更正、用户切换分支或目标预算变小时，也需要重新判断是否仍可直接复用。

## 15. 额度显示如何配合

额度提示可以帮助用户在原 Agent 仍能回答时主动交接，例如：“当前账号本周期额度较低，可以切换 Agent 继续。”

界面需要区分：

- 上下文窗口使用情况：当前会话还能容纳多少内容。
- 已消耗的 Token：调用统计，不等于剩余额度。
- 账号剩余额度：服务方提供的周期百分比、重置时间或其他限额信息。

只展示实际拿到的数据，显示更新时间和不可用状态。不能用上下文剩余 Token 推断账号还能调用多少次。

额度提示属于辅助能力，不是交接前提。账号用量可能滞后，仍需保留 A 突然不可用时的执行方兜底。各 Agent、账号和适配器实际能提供什么字段，需要实现时验证。

## 16. 当前确定的策略与待确定参数

### 16.1 本次讨论确定的方向

- Ora 自己管理历史和交接摘要，不依赖 Agent 内部摘要一定能够通过 ACP 返回。
- 历史正文在 JSONL；参考 Pi 的条目关系和压缩边界设计，摘要也写入历史。
- 原始历史保留；新 Agent 可以使用限制在当前 session 内的工具回查。
- 可用独立服务负责后台压缩；Agent 压缩事件是主要信号，历史规模是兜底信号。
- 单纯选择另一个 Agent 不触发交接；第一次真正发送请求时才准备。
- 优先复用摘要和适用的交接结果，不为每次切换强制多调用一次 LLM。
- 没有独立服务时仍可交接，按输入大小与执行方可用性决定是否总结。
- 超长输入使用受预算约束的分块与合并，不直接丢弃久远历史，也不无限递归总结。
- 只有成功保存且边界有效的摘要才进入后续复用路径。

### 16.2 实现前仍需确定的细节

| 项目 | 待确定内容 |
| --- | --- |
| 历史格式 | 条目关系、摘要类型、版本快照和旧文件兼容的具体契约 |
| 适配器能力 | 压缩通知、独立临时会话、请求确认与原生会话恢复支持程度 |
| 压缩服务 | 官方服务或用户配置的入口、模型、限额和失败处理 |
| 预算参数 | 新增内容阈值、输入输出上限、调用总预算和重试次数 |
| 保留尾段 | 保留哪些近期消息，怎样保持工具调用及结果的关联 |
| 历史工具 | 查询接口、资源引用格式、分页限制与 session 作用域绑定 |
| 交接状态 | 成功确认点、重复发送防护、取消及重启恢复契约 |
| 界面 | 后台压缩进度、失败提示、摘要查看入口与额度展示 |

以上参数是实现细化，不改变本方案的主流程。具体字段和能力应以实现时核对的代码及协议为准。

## 17. 实现后的验收场景

1. A → 选择 B → 未发消息 → 选回 A：不因这次选择生成摘要。
2. 已有摘要、没有新增历史：复用，不再次调用 LLM。
3. 有新增历史但交接内容仍在预算内：直接交接，不强制总结。
4. Agent 压缩通知重复到达：相同历史范围最多有一个有效的压缩任务。
5. 没有压缩通知，Ora 历史增长超过阈值：独立服务可用时仍能触发整理。
6. 后台任务运行期间新增消息：新消息不被误标记为已压缩。
7. 旧工具记录追加更正：能够识别摘要覆盖快照是否失效。
8. A 没额度、B 支持临时会话：压缩与正式工作上下文隔离。
9. 所有执行方不可用：给出明确错误，保留历史、旧摘要和用户待发送请求。
10. 分块摘要总量仍过大：在预算内有界合并，超预算停止而非无限递归。
11. A → B → A：A 能获知 B 的新增工作，不依赖恢复旧会话自动同步。
12. 目标接收状态不明确：不会无条件重复提交同一个可能修改文件的请求。
13. 图片、大工具输出和附件通过引用回查，查询结果也受分页及体积限制。
14. Agent 尝试读取其他 session：服务端拒绝，不依赖 prompt 自我约束。
15. 重新加载历史：摘要可被正确识别，不作为新用户消息重复显示或再次交接。
16. 交接后仍在正确的工作区和 worktree 中，已有未提交文件保持可用。

## 18. 与早期讨论的区别

| 早期想法 | 本版采用的策略 |
| --- | --- |
| 尽量直接获取 Agent 内部压缩摘要作为交接 | 不依赖内部摘要，Ora 维护自己的摘要；压缩事件可以用于触发检查 |
| 摘要正文单独放数据库表 | 摘要作为历史类型写入 JSONL，数据库继续管理元数据 |
| 用户一选 B 就让 A 总结并销毁 | 真正向 B 发送请求时才准备交接，确认交接后再释放不再需要的资源 |
| 每次切换都主动调用 LLM 压缩 | 先复用、先检查大小，必要时才调用 |
| 只能让 A 总结 | 独立服务优先承担后台工作，A 和有能力的 B 临时会话提供其他执行路径 |
| 历史太长就直接砍掉很久以前的消息 | 原始历史保留，通过有预算的分块、增量摘要和按需回查处理 |
| 有了 Agent 压缩通知就不需要其他大小检查 | 通知负责触发时机，输入预算和历史大小兜底仍需保留 |
