# 测试方案

## 一、整体思路：把功能是否正确，变成可以反复执行的检查

项目没有专门的测试团队，开发过程中的质量保障主要靠：**先把重要业务规则写成核心测试用例，由开发者用实际测试逐项提供证据，再通过自动化检查和必要的手工验收持续验证。**

从仓库规范和实际代码看，可以把这套方法概括为：

**设计评审 → 核心用例与验收标准 → 分层测试并记录证据 → 本地及 CI 复查 → 按功能要求做手工验收。**

这里的“正确”不只是正常流程能跑通，还包括：失败后数据是否完整、取消后资源是否释放、重启后能否恢复，以及一个工作区的操作是否影响另一个工作区。

## 二、具体怎么做

### 1. 用“核心测试用例＋证据表”明确要保证什么

`specs/` 补充了一套很关键的方法：**设计说明回答“系统应该怎样工作”，核心用例回答“怎样证明它做对了”。** 按[规范要求](/Users/silon/ora/desktop/specs/AGENTS.md)，设计决策文档（ADR）先评审，获批后再维护对应核心用例；代码实现并验证后，同步更新设计和证据。

核心用例按**业务行为和风险**组织，比如“卸载不能误删用户原有插件”，而不是按测试文件或函数数量组织。每个用例写清楚：有什么风险、操作前是什么状态、如何触发、必须得到什么结果、禁止发生什么，以及用哪些测试证明。

例如，[插件集合包卸载用例](/Users/silon/ora/desktop/specs/test-cases/desktop/plugin/extension-pack/pack-uninstall.md)要求：先单独安装一个插件，再安装包含它的集合包，最后卸载集合包；原有插件必须保留，集合包新安装且符合删除条件的成员才被移除。文档还关联了实际测试函数，方便核查。

每项要求都单独记录证据状态：

| 状态 | 含义 |
| --- | --- |
| `Covered`：已覆盖 | 有测试直接证明这项完整要求 |
| `Partial`：部分覆盖 | 只证明部分情况，或只验证了底层规则 |
| `Missing`：缺少证据 | 尚无直接证明这项要求的测试 |

**一个测试通过，不代表它所在功能的所有要求都已覆盖。** 例如，[重复执行用例](/Users/silon/ora/desktop/specs/test-cases/desktop/core/effect/convergence.md)将“重复执行不增加操作记录”列为已覆盖，但“外部内容和完整持久状态都保持不变”仍标为部分覆盖。缺少证据也不等于实现一定有错，而是尚未证明。

业务规则改变，或代表性测试新增、删除、弱化时，都要同步检查用例和证据表。再结合[功能变更指南](/Users/silon/ora/desktop/docs/feature-change-guide.zh.md)要求的实际接口测试，形成“规则—用例—代码证据”的对应关系，让评审者能看出哪些风险已验证、哪些仍有缺口。

### 2. 分几层测试，各自解决不同问题

| 测试范围 | 用容易理解的话解释 | 项目中的做法 |
| --- | --- | --- |
| 单元测试 | 单独检查一条规则或一个小模块 | 检查领域对象、参数校验、数据转换等，出错时容易定位 |
| 集成测试 | 检查几个真实模块接起来是否正确 | 通过后端业务接口，配合真实 SQLite、Git、文件系统，验证数据变化和业务结果 |
| 前端交互测试 | 模拟用户操作，检查页面反应 | 使用 Vitest 和 React Testing Library 渲染组件、点击按钮，检查加载、成功、失败和切换工作区后的状态 |
| 桌面宿主与完整流程测试 | 检查桌面接入层，以及较长的业务链路 | 单独测试 Tauri 命令执行层；在 `e2e/` 中组合真实后端、文件数据库、插件和测试 Agent，验证会话及工作流流程 |

**这些层次互相补充。** 小范围测试方便定位问题，完整流程测试负责发现“各部分单独正常，接起来却不对”的问题。

需要准确理解：目前查看到的 `e2e/` 主要通过后端公开接口运行流程；前端交互测试使用模拟浏览器环境。它们不等于已经在真实桌面窗口中自动点击并验收了全部界面。

### 3. 保留关键真实依赖，把外部行为做成可控制的替身

测试里既有真实组件，也有模拟组件，选择依据是当前要验证什么。

- **要验证数据是否真的保存、回滚或恢复，就使用真实数据库和文件。** 测试在临时目录创建独立环境，避免不同用例互相污染。
- **要验证前端如何处理响应，就控制后端响应的时机和结果。** 前端仍使用生产环境的客户端，只替换传输部分；没有配置的测试操作会直接报错，避免漏写模拟行为却默认成功。
- **要验证 Agent 接入和会话流程，就启动专门的 `fake-agent` 测试进程。** 它按约定返回结果、制造失败或等待取消，使这些场景可以稳定复现，也让这组测试不依赖真实模型的随机输出。

这保证了测试既能触及真实业务链路，又能按需制造难以手工复现的情况。测试 Agent 验证的是程序的接入和控制逻辑，不代表真实模型的回答质量已经得到验证。

### 4. 专门测试“不顺利时会怎样”

这部分是项目测试中很值得在面试里讲的特点。下面都是现有代码中的例子：

| 场景 | 测试怎么制造问题 | 要保证什么 |
| --- | --- | --- |
| 请求乱序返回 | 连续触发刷新，控制新请求先返回、旧请求后返回，也让部分请求失败 | 旧结果不能覆盖新状态；A 工作区的操作不能改变 B 工作区 |
| 数据库写到一半失败 | 在指定写入点故意报错，再检查数据库并重新打开 | 不能留下“只成功了一半”的数据；之后仍可正常完成操作 |
| 取消会话或删除资源 | 启动一个等待取消的 Agent 请求，再取消或删除 | 实际执行确实停止，相关状态和历史记录按规则处理 |
| 工作流执行失败后恢复 | 让第二个节点失败，再调用恢复接口 | 能继续完成；已经成功的第一个节点保持原来的身份和开始时间 |
| 进程意外退出 | 在真实克隆流程中强制结束 Node，再启动恢复 | 沿用原来的执行记录，避免重新派发产生重复执行 |

并发测试通过可控的异步响应安排先后顺序；流程测试等待实际事件或状态出现，而不是简单“睡几秒就当成功”。这让失败场景更容易重复，也减少测试偶尔通过、偶尔失败的问题。

### 5. 把检查接入日常开发和 CI

**开发时先跑与修改相关的小范围测试，再扩大到对应测试组。** 项目提供了统一入口：

| 命令 | 检查范围 |
| --- | --- |
| `task test:frontend` | 前后端接口生成结果是否同步、前端静态检查、工具脚本和前端包测试 |
| `task test:crates` | Rust 工作区静态检查和测试，不包含下面单列的桌面及 E2E 包 |
| `task test:tauri` | Tauri 桌面包的静态检查和测试 |
| `task test:e2e` | 完整流程测试包的静态检查和测试 |
| `task test` | 依次执行以上四组检查，作为跨仓库改动的统一收尾入口 |

除了运行测试，还有几道配套检查：

- **提前检查常见错误：** 类型检查、Rust Clippy、代码格式检查，以及前后端生成接口的一致性检查。它们能提前发现问题，但不能代替业务测试。
- **不忽略测试警告：** 前端测试由脚本包装，向标准错误输出写入内容也会判失败。例如 React 的异步更新没有被测试正确等待，即使断言通过，也不能直接算整组通过。
- **自动复查：** GitHub Actions 在 PR 提交时按修改路径运行受影响的测试组，在代码推送到 `main` 后运行全部组。Rust 工作区在 Linux、macOS、Windows 上检查，其他测试组在 Linux 上检查。

CI 的 `ci-ok` 会汇总结果，失败或取消都会反映出来，可作为合并前的必需检查。但仓库文件不能证明远端已开启强制分支保护；本地提交钩子也主要检查格式，并不会每次提交都跑全量测试。

### 6. 对真实用户流程补充手工验收，并留下记录

仓库还为插件集合包提供了[本地手工验收清单](/Users/silon/ora/desktop/specs/test-cases/desktop/plugin/extension-pack/manual-release-qualification-sop.md)：启动真实 Desktop，按步骤验证安装、页面反馈、重启后保留状态、更新、卸载，以及下载失败和回滚。

验收需要记录日期、操作系统、相关仓库版本，以及每个场景的通过／失败和证据。这样才能知道“哪个版本、在哪个环境、验证过什么”，也便于区分代码问题、插件内容问题和环境问题。

这是特定功能已有的验收方案，不能推断所有功能都有同样的手工流程；该文档记录手工验收待执行的基线，也不能仅凭清单存在就说已全部验收通过。

## 三、面试时可以这样回答

> 我们虽然没有专门的测试团队，但有一套核心测试用例和证据管理方法。重要设计先评审，再按业务风险列出必须满足和禁止发生的结果，由开发者编写测试逐项证明，并明确记录已覆盖、部分覆盖和缺少证据的地方。
>
> 具体测试分几个层次：小范围测试检查规则，集成测试使用真实数据库和 Git 验证业务结果，前端测试模拟用户操作，还有完整流程测试验证会话、工作流等链路。
>
> 我们比较重视异常情况，例如请求乱序、数据库写入失败、操作取消和进程重启。以工作流恢复为例，测试会让第二个节点失败，再验证恢复后能够继续完成，而且不重新执行已经成功的第一个节点。
>
> 这些检查有统一命令，PR 和主分支也会通过 CI 自动运行。插件集合包等功能还有真实桌面的手工验收清单，并记录版本、环境和结果。这样，评审时既能看到测试结果，也能看到未覆盖的风险；后续改动再持续验证这些行为。
