# 技能交付与效果协调

> 核对日期：2026-09-10；依据本地 `project_learn` 分支源码。本文是当前实现学习说明。

[返回学习导航](../README.md)

## 模块职责

理解 Effect 如何将“想要哪些技能”转换为真实文件、消费者协调和可证明的 ready 状态。

## 设计逻辑与执行流程

Effect 是期望状态与外部实际状态的协调系统。Source／Revision 回答交付什么；Scope 是工作区；Consumer 是谁使用；Target 是某 Scope 下的消费者；Resource 是实际被改动的资源，例如技能目录。多个 Target 可以共享资源。

1. 发布不可变 Revision，替换 Scope 下 Desired 时用 generation CAS，避免并发旧编辑器覆盖新选择。
2. 从 Consumer 能力／Target 声明构造 Target Projection 和 Resource Requirements，合并资源贡献，冻结 Materialization 输入。
3. 写 reconcile request，worker 通过 lease／claim token／resource fence 取得权利，阻止过期 worker 提交。
4. 创建 Attempt 和操作意图；需要时先协调消费者到 safe-to-mutate，再修改受管理文件。
5. 保存 operation artifacts 和 managed ledger，验证实际文件及 consumer readiness，再推进 applied／ready generation。
6. 异常进入显式条件、重试或 recovery_required。不能仅因文件复制完成就宣布 Agent 已读取新配置。

完整字段和物理外键见[数据库设计](../数据库设计/模块说明.md)。MCP 不走本模块。

## 数据库表与持久化

| 表组（逐表名称） | 持久化事实与写入时机 |
| --- | --- |
| `effect_scopes` | workspace 作用域、lifecycle、期望 generation；业务建立和推进 |
| `effect_sources`、`effect_revisions` | 源身份、发布指针、不可变内容与可用性；源发布／协调 |
| `effect_desired_effects` | 选中的 revision、参数、selector；替换选择时写 |
| `effect_consumers`、`effect_consumer_revisions` | 消费者身份、能力版本；声明更新时写 |
| `effect_targets`、`effect_target_declarations` | Scope 下的消费者与声明／fence；目标协调时写 |
| `effect_resources`、`effect_target_resource_bindings` | 资源描述、目标关联和协调合同；资源解析时写 |
| `effect_target_projections`、`effect_target_projection_effects` | 冻结目标选择及其 Desired 明细；计划阶段 |
| `effect_resource_requirements`、`effect_resource_requirement_effects` | 目标对资源的要求与对应 Desired；计划阶段 |
| `effect_resource_projections`、`effect_resource_projection_contributors` | 合并的资源计划及来源目标；计划阶段 |
| `effect_resolved_materializations` | 每个 managed identity 的具体输入和合同；计划冻结 |
| `effect_managed_items` | 已应用资源的身份、fingerprint、revision、generation；操作提交 |
| `effect_target_status`、`effect_resource_status` | desired／observed／applied，Target 还有 ready；每阶段推进 |
| `effect_conditions` | 阻塞原因、影响、重试策略、观察时间；诊断状态变化 |
| `effect_reconcile_requests`、`effect_resource_claims` | 唤醒、目标领取、资源租约与 fencing；worker 调度 |
| `effect_reconcile_attempts`、`effect_attempt_resource_projections` | 一次尝试的冻结输入、资源顺序和阶段；尝试开始／推进 |
| `effect_coordination_receipts` | 可安全修改／已重新激活的证据；协调确认 |
| `effect_operations`、`effect_operation_artifacts` | 外部修改意图、phase、恢复材料；执行前登记，执行后推进 |
| `effect_readiness_receipts` | readiness 的 proof；验证成功 |
| `effect_audit_events` | 不可变审计事件及安全详情；对应变化发生时 |

上述共 30 张 Effect 表。数据不能只存在 worker 内存，否则重启后无法区分“没做”与“已改文件但尚未确认”。落地技能文件在工作区资源路径，备份／staging artifact 在适配器管理路径，不在 SQL BLOB。

`effect_operations.detected_at` 是 0010 新增的恢复发现时间；仅 recovery_required 时非 NULL，不能早于 prepared_at。审计 `updated_at` 和恢复发现时间不再混用。

## 目前存在的缺陷与限制

- **已确认的复杂性**：完成有多层含义，`ready ≤ applied ≤ observed ≤ desired`，只看单个 phase 或 generation 容易误报成功。
- **已确认的边界**：资源变更不可能与 SQLite 同一物理事务，必须先登记意图并保留恢复证据；recovery_required 不是随便重试即可清除的普通报错。
- **设计风险**：模型包含多个带版本 JSON 合同，数据库外键不能代替合同解析和适配器校验；新增能力需要同步验证计划／操作／恢复三条路径。
- **已确认的隔离边界**：MCP revision 与配置值禁止进入 Effect；Consumer ready 也不能代表每个 ACP 会话都处于可发送状态。
