## 文件已经复制了，为什么仍不能告诉用户“技能已生效”？

W 中两个 Agent A/B 共用技能目录。用户将 retry-review 从 v1 更新到 v2；文件复制成功，但 A 仍在使用旧进程缓存，B 正忙。此时若显示全部 ready，会把资源变化和消费者采用混为一谈。若 A/B 各自更新目录，又会争抢同一个物理资源。

整体设计：Effect 保存期望、计划、外部操作责任与采用证据。Target 表示某个消费者在某工作区的就绪边界，Resource 表示真正要修改的目录，两者多对多。先冻结输入和取得有效写权，再安全改文件，最后验证消费者；无法确认的副作用进入恢复隔离。

## 为什么一个技能选择要拆成 Source、Target 和 Resource？

### 直观方案与当前选择

只记 `workspace W 已安装 K1`，说不清 K1 的哪一版、为谁交付、谁拥有目录、另一个 Agent 是否仍需要它。

**当前实现**：Source/Revision 定义交付内容与不可变版本；Scope 对应 Workspace；Consumer 描述执行者及能力；Target 是 Scope 中的消费者；Resource 是实际目录。多 Target 的贡献先合并并检查合同，再形成资源计划。

| 实体/真实表 | 示例投影 | 回答的问题 |
| --- | --- | --- |
| effect_scopes | E, workspace_id=W, generation=8 | 这次工作区期望版本 |
| effect_sources / effect_revisions | SRC1→REV2 | 哪份技能内容 |
| effect_desired_effects | D1, scope_id=E, revision_id=REV2 | 用户选择什么 |
| effect_targets | TA→A；TB→B | 哪些消费者应采用 |
| effect_resources | RES1, scope_id=E, resource_key=共享技能目录的规范身份 | 哪个资源被修改 |
| effect_target_resource_bindings | TA→RES1；TB→RES1 | 谁依赖同一目录 |

同资源有冲突要求不能最后写入者获胜；计划阶段要产生明确 Condition。目录相同不意味着消费者 readiness 相同。

### 连续追问：A 取消技能，能立即删目录吗？

先检查 B 是否仍贡献同一项。只按 A 的目标差集删除会破坏 B。**可能方案**若要减少冲突，可按 Agent/版本隔离目录，保存独立 Resource 与绑定；成本是磁盘重复和 provider 发现规则兼容，清理仍要核对资源所有权。它简化共享竞争，不替代采用验证。

## generation 和 fencing 分别防什么？

### 当前实现与完整演算

用户 E1/E2 都读取 Scope generation=7。E1 用预期 7 替换完整 Desired Set 成功，推进 8；E2 仍带 7 则冲突。规范化后无实际变化不推进。它防旧编辑覆盖新意图，但不阻止旧 worker 改文件，后者需要 claim/fence。

| 时刻 | 请求/权威状态 | 能否提交 |
| --- | --- | --- |
| worker X 领取 TA | claim_token=11，租约有效 | 只能在其权威范围协调 |
| X 同时领取 RES1 | resource_fence=6 | 才获得资源操作资格 |
| X 卡住，租约失效，Y 接管 | 新 token/fence | Y 使用新权威重读事实并计划 |
| X 迟到回来 | 仍持旧 token/fence | 不能覆盖 Y 的持久结果 |

相关事实存在 `effect_reconcile_requests`、`effect_resource_claims` 和 Target/Resource 的 fence 字段，不能只留在 worker 内存。共享资源按稳定顺序领取，领取后重新读取可变事实，关闭“先计划后抢到资源”的竞争窗口。

**边界与缺口**：fence 是执行资格，不是倒流时间的能力；如果旧 worker 已经产生不确定文件副作用，不能仅因新 token 到手就断言磁盘干净。此时要结合操作意图与 artifact 恢复证据。时钟日志也不能替代单调权威版本。

**可能方案**：对外部资源原生支持 fencing 的适配器，把 fence 传给资源端并拒绝旧写；成本是资源合同升级。普通文件系统没有业务 fence API，仍需受控所有者和 journal，权威丢失后保留不确定状态，不能通过反复重试掩盖。

## 为什么要在修改文件之前登记 Operation？

### 直观方案与当前实现

做完文件复制再记录“成功”，崩溃后无法区别没做与做了没记。Effect 在副作用前保存冻结的 Attempt、projection、Prepared Operation 与 artifact 权限；阶段单调推进。

| 步骤 | 数据库/文件事实 | 断在此处如何判断 |
| --- | --- | --- |
| 准备 | effect_reconcile_attempts phase=prepared，固定 projection | 计划输入不会被新选择悄悄替换 |
| 协调消费者 | coordination_receipts state=safe_to_mutate | 知道安全点证据对应哪个尝试 |
| 准备外部操作 | effect_operations OP1 phase=prepared；artifacts 有 staging/backup 权限 | 有责任与恢复材料，但尚不能说已修改 |
| 文件已变 | RES1 内容变成 v2，OP1 可能仍 prepared | 最关键的不确定窗口 |
| 应用进度 | OP1 phase=applied，随后验证资源；managed ledger 尚未最终提交 | 已观察到应用，但整个尝试未完成 |
| 验证/激活 | 所有需协调参与者重新激活成功后，一起记激活阶段；再验证本 Target ready | 中途不能把部分激活回执当整个 barrier 已通过 |
| 完结事务 | operation/attempt finalized、managed ledger、水位、readiness 等一起最终提交 | 此后 artifact 清理失败保留清理责任，不反向抹掉已提交事实 |

`effect_operations.detected_at` 在 recovery_required 时记录发现时间，与业务 updated_at 分离。未准备副作用前的瞬时错误可退避；准备后副作用状态不明、且有效 claim 不再存在等恢复条件满足时，进入 RecoveryRequired 并保留备份/暂存。当前不是所有隔离都能自动修复。

### 连续追问：为什么不看到新文件就补记成功？

路径存在、内容相同都不足以证明它由 OP1 创建。用户可能手工写了相同内容，或路径已经被替换。当前覆盖/删除依赖 ledger、`.ora-managed.json`、native identity 与上次 fingerprint 等所有权证据一致；漂移内容保留。

**可能方案**：提供显式恢复向导，展示预期/观察内容摘要、操作记录、备份和所有权，再允许保留用户版本或重做受管版本。新增恢复决策记录、操作者和选择证据，代价是交互与备份空间；证据不足时保留隔离，不能为了显示绿色而认领未知文件。

## applied 与 ready 差在哪里？

### 当前实现与数值演算

Target 的约束为 `ready ≤ applied ≤ observed ≤ desired`，Resource 没有消费者 ready。下面用于解释水位的逻辑含义；它们不是承诺本次副作用路径逐行持久化的四个中间快照。当前该路径在消费者验证后通过 finalize 事务提交最终 ledger、水位与 ready，应用中的证据应查看 Operation/Attempt。

| 阶段 | desired | observed | applied | ready | 可向用户解释 |
| --- | --- | --- | --- | --- | --- |
| 选择 v2 | 8 | 7 | 7 | 7 | 新选择已保存 |
| 计划已观察 | 8 | 8 | 7 | 7 | 已理解要改哪些资源 |
| 文件应用 | 8 | 8 | 8 | 7 | 文件已改，但消费者未确认 |
| A 确认可用 | 8 | 8 | 8 | 8 | TA 对该版本已 ready |

TB 可能仍 ready=7，因此 RES1 applied=8 不能让所有 Target 自动变 8。readiness receipt 绑定 target、generation、consumer_revision、projection_digest，旧版本消费者的回执不能证明新版本准备好了。

连续追问“那 MCP 是否也写这些表”：不写，MCP 是会话运行输入；共享 barrier 只代表协调安全点共用，不能把 MCP Active 与 Effect ready 合并。ready 也不证明模型一定会遵循技能，只证明交付/消费者合同所要求的准备。

**可能方案**：对高价值技能增加行为验收任务，记录输入、预期关键行为、采用版本和结果。解决“可发现但不会用”的质量问题，成本是模型调用和非确定性；失败标质量未达标，不能篡改底层文件应用事实。交付正确和模型效果应分别展示。

| 责任 | 表 |

| 源与选择 | effect_scopes、effect_sources、effect_revisions、effect_desired_effects |
| 消费者与资源归属 | effect_consumers、effect_consumer_revisions、effect_targets、effect_target_declarations、effect_resources、effect_target_resource_bindings |
| 冻结计划 | effect_target_projections、effect_target_projection_effects、effect_resource_requirements、effect_resource_requirement_effects、effect_resource_projections、effect_resource_projection_contributors、effect_resolved_materializations |

| 调度权威 | effect_reconcile_requests、effect_resource_claims |

## 完整业务推演：应用完成但激活失败

E 从 7 推进 8，TA/TB 合并对 RES1 的需求；worker 有效领取后保存计划及 OP1。协调确认可改，再修改受管目录，保存 operation applied 并验证。假设 A 已重新激活、B 激活失败：当前重新激活是全参与者 barrier，不在仍为 Verified 的 Attempt 下保存一个假的完整激活集合；最终 ledger/ready 提交尚未完成。此时不能只看文件 v2 就把 TA/TB 都标为 ready=8，甚至不能把内存曾计算出的 applied 水位当成已持久提交。应展示操作阶段与未完成责任；权威失效后按恢复规则处理。若重启，worker 依据持久操作与 artifact 证据对账，不能扫描目录就补出 B 回执，也不能无条件再覆盖已漂移的用户文件。

<details><summary>分析提示与参考思路</summary>

先定义期望、执行权威、资源所有权和消费者采用四种事实。CAS 防旧意图，claim/fence 防旧资格，ledger/marker/identity 防误改用户资产，receipt 防伪造已采用。故障注入应卡在 Prepared 后、rename 后、ledger 提交后、消费者激活前后，另测两个 Target 共资源、租约转移旧 worker 迟到、用户改文件及新 generation 到来。仅断言最终文件内容正确不够，还要检查没有误删、旧结果不能覆盖、恢复责任没有丢。
