## 工具安装了，为什么这个节点仍然不应该能用？

工作流中的审查节点只允许读代码，部署节点才允许调用发布工具。如果安装一个 MCP 就让所有节点自动获得它，能力扩展会悄悄扩大授权；如果把服务列表只存在 NodeRun 关联里，删掉旧关联后恢复会话又可能猜错权限。

整体设计：安装提供可选目录，Session 自己保存选择；setup 用同一条解析路径生成完整服务列表与无秘密的版本身份。列表投递、Host 健康探测、Agent 实际使用是三种证据，不能相互替代。

## 为什么选择要直接保存到 Session？

### 直观方案、当前实现与演算

通过“这个 Session 属于哪个工作流节点”临时反查白名单很直观，但关联可能缺失、图可能已编辑，切换 Agent 也不应扩大授权。

**当前实现**：`sessions.mcp_selection` 为 JSON 文本。新普通聊天明确写 Automatic；工作流保存冻结的 Explicit 列表；恢复、重建、切换、刷新均读取该行。迁移 0011 对历史会话采用显式空集合，避免升级就凭空授权。

| 会话 | mcp_selection 实际形状示例 | 含义 |
| --- | --- | --- |
| 新普通 S | `{"mode":"automatic"}` | 按当前合格插件自动发现 |
| 审查 T | `{"mode":"explicit","pluginIds":["demo/search"]}` | 只使用 search |
| 无工具 U / 迁移旧行 | `{"mode":"explicit","pluginIds":[]}` | 不交付 MCP |

安装新 `demo/deploy` 后，S 的有效集合可能变化；T/U 不因此多出发布工具。工作流 draft 修改开关影响后续运行，不改变已有 T 的持久选择。节点 `skills` 提示需要哪些能力也不等同于 MCP 授权白名单。

### 连续追问：显式插件不完整时能不能跳过？

Automatic 只纳入合格且配置完整的成员；Explicit 表达执行前提，缺包、坏声明、缺配置会让整个 setup 失败，不能静默缩小成另一个工具集合。过滤必须先于读取配置，避免无关凭据进入解析路径。

**可能方案**：用户可选择“必需/可选”成员时，必须新增明确定义的选择合同及降级回执，记录实际集合和缺失原因；成本是下游行为复杂化。必需成员仍失败，可选缺失才继续，不能把所有错误都自动视为可选。

## 为什么不把工具配置写进工作区文件，让 Agent 自己发现？

### 当前实现与例子

**当前实现**：MCP 不走 Effect 文件投影，不创建 `.mcp.json` 或 provider 专有配置。包声明解析出 stdio/http transport，设置引用解析成值，通过 ACP `session/new` / `session/load` 的 `mcpServers` 交付。stdio 每次复核包内普通可执行文件，HTTP 检查 Agent 能力；非空集合要求支持 session/load，以便后续刷新。

```text
持久输入
  插件不可变 assets/config.json：transport 与 Setting 引用
  store.json：值和 revision=7
  sessions(T).mcp_selection：Explicit [demo/search]
内存解析结果
  有效列表：[demo/search 的命令/参数/env 或 HTTP headers]
  版本身份：[pluginId, packageVersion, configurationRevision, transport]
输出
  一次完整 ACP setup payload
```

秘密值只应留在配置存储、短时快照、ACP payload 和必要探测执行参数中；不能写进 SQLite、工作区、版本摘要、日志或 UI 回读。这里的 MCP 子进程 env 与给 Agent 全进程注入环境变量不是同一件事。

写工作区配置的替代方案有兼容现有 CLI 的优势，但要解决多会话不同授权、凭据泄漏、用户文件所有权与更新撤销。当前 Session 注入使选择边界明确；代价是依赖 provider 对会话集合的正确执行。

**边界与缺口**：本地文档记录部分 provider 曾把 MCP 注册保留在共享进程层，导致 Host 正确发送空集合也未必使 provider 隔离干净。这里引用的是项目的兼容性记录，不是本次对第三方最新版本进行的外部验证。不能把 Host 白名单宣称为对所有 provider 的强安全沙箱。

**可能方案**：对不可靠 provider 采用按授权集合隔离进程，或让工具调用经过受控代理再次鉴权。需要保存/维护进程授权指纹或代理会话权限，成本是更多进程/调用延迟；鉴权失败拒绝调用，不依赖提示词告诉模型“别用”。

## 配置从第 7 版变为第 8 版，怎样不插进正在执行的轮次？

### 当前实现与演算

Desired/Active 版本存在内存，身份由插件、精确包版本、配置 revision、transport 等组成。变更发脱敏唤醒。忙 T 等当前 prompt 结束，空闲直接刷新；刷新期间新 prompt 被 barrier 挡住。成功才更新 Active，过程中新的 Desired 不能丢掉。

| 时刻 | Desired | Active | 行为 |
| --- | --- | --- | --- |
| t0 | 7 | 7 | 允许 prompt |
| t1 保存配置 | 8 | 7 | 当前轮继续；下一轮等待 |
| t2 刷新 8 时再保存 | 9 | 7 | 保留更新水位 |
| t3 8 投递成功 | 9 | 8 | 仍有待刷新工作 |
| t4 9 失败 | 9 | 8 | 阻止过期配置启动新 prompt |

MCP 与 Skill 变更、Agent 替换共享安全时点协调，但不共享 Effect 数据模型，也没有 MCP 专用 Effect 行。已停止 Session 不在后台强行刷新，下次 attach 再构造。

连续追问“旧凭据必须立即失效”：当前忙会话等待是可用性取舍，不是紧急撤权协议。**可能方案**是变更分普通与撤销，撤销阻断新工具调用并取消在途操作；新增撤销版本及回执，成本是工具端配合和取消后未知副作用。不能靠删除本地配置撤回第三方已接受请求。

## Host 健康检查成功，为什么仍不能宣布“模型能用工具”？

### 当前实现与证据层次

Host 复用 setup 解析产物，进行有界 initialize、initialized、tools/list，然后拆连接；stdio 探测还要回收子进程。当前硬超时 8 秒，同身份并发合并。健康失败不改变选择、不缩小服务列表，也不使 setup 失败。

| 证据 | 能证明 | 不能证明 |
| --- | --- | --- |
| 配置 Complete | 必填值与声明校验通过 | 服务在线 |
| setup 响应成功 | 完整列表投递并被接受 | Agent 已完成工具初始化 |
| Host Healthy | Host 在当时完成握手/列工具 | Agent 同环境成功，模型已选用工具 |
| 工具调用回执 | 某次具体调用结果 | 以后一直健康 |

健康只在内存，没有 TTL 或定期后台复检；重启回到 Unknown。键包含版本/配置/transport，需要 workspace context 的成员再绑定 cwd；插件卡片没有 cwd 时是 Unknown(context_missing)，不能拿伪造目录探测。HTTP/stdio 环境差异也可能造成 Host 与 Agent 观察相反。

**可能方案**：增加 Agent 侧工具集合回执和能力探针，关联 session、provider generation、MCP revision 与工具 schema 摘要。解决“投递后是否采用”的证据缺口，代价是协议扩展/适配；无回执时保留 Unknown。探针成功还要和业务任务调用分开，不能把健康状态作为永久授权。

## 完整业务推演：切换 Agent 后工具刷新失败

T 保存 Explicit search，Agent A 正在运行。用户切 B，准备新 provider 时仍读取 T 的选择，不重新用 Automatic。B 必须满足 transport 和 load 能力；不满足则 setup 失败，不交付半份列表。若准备成功再进入切换提交，后续凭据 revision8 需要刷新；刷新失败阻止下一轮使用旧列表。Host 健康可能 Healthy，但它不能越过 B 的失败。SQLite 的选择始终不变，配置文件可能已变，Active 则暂留旧值。

## 脱离案例自测

**问题链：为什么安装不是授权 → 为什么权限存 Session → 显式集合缺一个为什么整体失败 → 正确投递为何还可能越权 → 健康探测能否补这个漏洞 → 怎样验证？**

<details><summary>分析提示与参考思路</summary>

从 Host 权限决定、传输、provider 执行、工具端鉴权分别回答。探测只测连通性，不证明 provider 隔离。验证至少创建两个共享 Agent 进程的 Session：一个允许 search，一个显式空；检查真实工具可见/调用结果，而不仅断言发送 payload。再覆盖切 Agent、孤儿工作流关联、升级迁移、配置不完整、刷新期间变更多次、健康缓存 cwd 隔离。发现 provider 不遵守时要报告边界并选择隔离/代理方案，不能靠提示词保证安全。

</details>
