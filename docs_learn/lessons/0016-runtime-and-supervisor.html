Lesson 0016 · 静态资料与动态服务

为什么 Agent 需要 Runtime 和 Supervisor？

Skill 插件交付的是“放在那里供人读取的资料”；Agent 插件交付的是“必须持续在线并能双向通信的服务”。Runtime 让服务运行，Supervisor 让服务保持可用。

先不用术语：一本书与一条客服电话

Skill 像一本书：文件安装完成后，内容就在那里。Ora 可以索引、选择并物化它；真正需要时，Agent 再读取。书不需要自己醒来等待请求。

Agent 像客服电话：只有安装号码远远不够。电话必须接通、对方必须在线、通话中断还要恢复，并且多个用户的通话不能串线。

因此，Agent 需要 Runtime 的根因不是“它使用 JavaScript”，而是它提供随时间运行的行为。即使以后插件入口改成其他语言，只要它仍是一项长期通信服务，就仍需要运行环境和生命周期管理。

Skill 安装后，Ora 已经拿到了完整价值

Skill 插件包
  ↓ Manager 校验 SKILL.md 和目录
InstalledPlugin::Skill
  ↓ Backend 读取并写入 Skill catalog / Effect source
需要使用时再物化到 Agent 声明的目录

这条链没有一个 Skill 自己的进程。Skill 插件不接收 JSON-RPC 请求，不发送 notification，也没有“运行到一半崩溃”的状态。它可能有错误文件，但不会有连接丢失、握手超时或进程崩溃。

Agent 安装后，只拿到了启动它的方法

Agent 插件包
  ↓
Deno main.js 插件进程
  ↓ agent/start
Agent CLI 子进程
  ↓ ACP initialize
可用的 Agent connection

任何一层都可能失败：Deno 可能启动失败，运行时合同可能缺方法，agent/start 可能失败，Agent CLI 可能退出，ACP initialize 也可能超时。因此仅仅“有进程”不等于“用户现在能对话”。

Runtime 到底负责什么？

在这套系统里需要区分两个相邻概念：

层主要职责它回答的问题
Plugin Runtime运行 Deno main.js，处理注册与外层 Plugin JSON-RPC插件代码能否运行并与 Ora 通信？
Agent Runtime建立 ACP Peer、协商能力并把 Session 接到共享 Agent connection这个 Agent 是否真的能服务对话？

Supervisor 不是“启动脚本”，而是连接监督者

每个已安装 Agent 都有一个 application-scoped ConnectionSupervisor。它的核心目标是：

建立连接请求 Lifecycle 确保插件运行，再调用 Agent 合同
确认 Ready完成 agent/start 与 ACP initialize
维持连接观察当前 generation，连接丢失时让路由失败
故障恢复退避重试，频繁失败时打开熔断并标记 Failing

它还向其他模块提供 Starting / Ready / Unavailable / Failing 状态，并让 Session 根据 AgentRef 找到正确的共享连接。

最容易混淆的所有权：Supervisor 负责 Agent 连接的可用性，但不私自拥有 Deno 插件进程。它通过 ensure_running() 请求 Plugin Lifecycle；Lifecycle 仍是插件进程的唯一所有者。

为什么只有 Lifecycle 还不够？

Lifecycle 看到的是：

main.js 进程正在运行 → Running

但用户真正需要的是：

合同完整
+ agent/start 成功
+ Agent CLI 存活
+ ACP initialize 成功
= Agent Ready

这些 Agent 专属事实不应该塞进通用 Plugin Lifecycle。否则 Lifecycle 就必须理解 ACP、模型目录、Session 路由和 Agent 重试策略，最终不再是所有插件共用的底层模块。

为什么 Skill 不需要 Supervisor？

Supervisor 解决的是长期服务不可靠的问题。Skill 没有自己的长期服务：

问题AgentSkill
需要常驻进程需要不需要
需要双向协议Plugin RPC + ACP不需要
需要 Ready 状态需要不需要
可能运行中掉线可能不存在掉线
需要退避重试需要读取或物化失败时由调用方重试

面试表达：Skill 插件贡献的是静态声明和文件，安装校验后由 Host 索引与物化，不存在独立连接生命周期。Agent 插件贡献的是长期动态服务，必须运行适配器与 Agent CLI，并维护 ACP 连接。Plugin Lifecycle 统一拥有插件进程；Connection Supervisor 则在其上负责 Agent 的启动编排、ACP 初始化、Ready 状态、generation 隔离和故障恢复。
