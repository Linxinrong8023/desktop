Lesson 0021 · Contract & Capability Negotiation

Agent Ready 前，为什么要确认三次？

ora/register、agent/start 和 ACP initialize 不是重复握手。它们依次确认：插件适配器会什么、它启动了什么协议、真实 Agent 支持什么能力。

先看三层对象

Ora Host
  ↕ 外层 Plugin RPC
Deno main.js（Agent adapter）
  ↕ 内层 ACP
真实 Agent CLI

因为中间有两条协议、两个进程，仅仅确认 main.js 活着，不能证明真实 Agent CLI 已经启动，更不能证明它支持恢复 Session 等可选功能。

第一次：ora/register 确认适配器合同

Deno 插件进程启动后，通过外层 Plugin Runtime 发送一次 ora/register：

{
  methods: ["agent/start", "agent/stop", "agent/listModels"],
  emits: ["agent/acp"],
  effectSurfaces: [...]
}

它回答的问题是：

“这个 main.js 声称 Ora 可以调用哪些方法，它又可能主动发出哪些 notification？”
  • 注册在这一代插件进程中不可变，只允许发送一次；
  • Agent adapter 层会检查 start、stop、listModels 和 emitted agent/acp 是否完整；
  • 合同不完整是确定性错误，直接 Failing，不重试。
它没有证明：Agent CLI 已经启动，也没有说明真实 Agent 支持 session/load、session/list 等 ACP 能力。

第二次：agent/start 确认 CLI 与传输协议

合同完整后，Ora 调用外层 Plugin RPC 的 agent/start，传入工作目录和 Host 版本。插件此时才真正启动 Agent CLI，并返回：

{
  protocol: "acp",
  acpVersion: 1
}

它回答的问题是：

“我已经把底层 Agent 拉起来了；接下来的 agent/acp payload 应按哪种协议和 major version 理解？”
  • CLI 没安装时返回 AGENT_NOT_INSTALLED，Supervisor 保持 Unavailable 并静默重试；
  • 当前 Host 只接受 protocol = ACP、major version = 1；
  • 不支持的协议版本属于确定性不兼容，立即 Failing。
它仍没有证明：内层 ACP 请求真的可以往返。插件可能启动了错误程序，CLI 也可能已卡死。

第三次：ACP initialize 与真实 Agent 协商能力

Supervisor 创建 AcpPeer，再通过 agent/acp 向真实 Agent CLI 发送内层 ACP initialize。Ora 在请求里介绍自己和客户端能力；Agent 在响应里返回它支持的能力。

Ora → Agent：
  ACP v1
  clientInfo = ora
  我能接收 Session config options

Agent → Ora：
  是否支持 session/load
  是否支持 session/list
  是否支持 session/close
  是否支持 session/delete
  其他 Agent capabilities
不是 MCP 清单：这里返回的是这个 Agent 在 ACP 协议中的能力，例如能否 load、list、close 或 delete Session。Ora 安装了哪些 MCP 插件属于另一套插件贡献与配置，不由 Agent 的 ACP initialize 枚举。会话前模型列表也由外层 agent/listModels 单独读取。

它回答的问题是：

“真实 Agent 的 ACP 通道是否真的可用？接下来的 Session 生命周期可以调用哪些可选能力？”

initialize 当前最多等待 15 秒。超时或普通协议错误属于真正的可恢复故障：回收旧 generation、计入 crash circuit，再按退避策略重试。

三次确认放在一张表里

阶段协议层谁对谁确认什么
ora/registerPlugin RPCmain.js → Ora适配器的方法与 notification 合同
agent/startPlugin RPCOra → main.jsCLI 已启动，以及 payload 的协议与版本
ACP initializeACPOra AcpPeer ↔ Agent CLI真实通道可用，以及 Agent 的可选能力

什么时候才发布 Ready？

Plugin Lifecycle Running
+ ora/register 合同完整
+ agent/start 成功且 ACP v1 兼容
+ agent/listModels 成功
+ ACP initialize 成功
= Agent connection Ready

所以 Ready 不是“一个进程存在”，而是 Host 已经拿到一条经过合同检查、版本检查和能力协商的可用 Agent connection。

面试表达：Agent Ready 前有三层确认。ora/register 固定 Deno adapter 的外层 Plugin RPC 合同；agent/start 让 adapter 拉起 CLI，并确认 agent/acp 中承载的协议及 major version；随后 AcpPeer 与真实 CLI 执行 ACP initialize，验证通道并协商 Session 可选能力。三者分别验证适配器接口、传输版本和真实 Agent 能力，任何一层都不能替代下一层。
