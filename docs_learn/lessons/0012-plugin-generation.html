Lesson 0012 · Generation

插件 ID 没变，为什么连接不能继续复用？

同一个插件可以停止、崩溃并重启。插件 ID 仍是 official/my-agent，但重启后的进程已经不是原来的那一个，所以每次启动尝试都有独立 generation。

Generation 是“这一次进程生命”的编号

可以把插件 ID 想成酒店房间号，generation 想成这一批房卡的版本。房间仍是 302，但上一位住客的旧房卡不能打开新住客时期的 302。

同样，插件重启后，旧连接、旧注册能力和迟到通知都属于上一代进程，不能混进新一代。

Plugin ID: official/my-agent

generation 1：Deno 进程 A → 注册 A → 通知流 A
                     ↓ 崩溃 / 停止
generation 2：Deno 进程 B → 注册 B → 通知流 B

连接为什么要钉在 generation 上

PluginGenerationLease 只允许调用它取得时对应的那一代进程，并携带该 generation 的注册信息。进程结束后，旧 lease 不能复活，也不能自动跳到新进程。

需要再次调用时，消费者重新向 Lifecycle 获取当前连接。这样调用者不会拿着 generation 1 的 handle，误把请求发给 generation 2。

通知也必须携带 generation

通知是异步的，旧进程退出附近可能还有消息在队列中。Lifecycle 把每条 inbound notification 标记为：

{
  plugin_id: "official/my-agent",
  generation: 1,
  method: "agent/acp",
  params: ...
}

如果当前连接已经是 generation 2，消费者就能识别并丢弃 generation 1 的迟到消息，避免旧 Agent 的回复进入新会话连接。

不允许两代重叠：停止一代时，Lifecycle 会等待插件进程及其受管子进程树真正退出，再允许替代 generation 启动。generation 标记负责识别归属，等待退出负责避免两套进程同时拥有同一插件身份。

为什么不在原来的 main.js 上无限重试 agent/start？

因为一次失败可能是“部分成功”，Host 无法证明原进程仍然干净：

Host 调用 agent/start
  ↓
main.js 已经拉起 CLI 进程 A
  ↓
但响应丢失或超时
  ↓
Host 只知道“没有拿到成功响应”
并不知道 CLI A 是否已经存在

如果直接在同一个 main.js 上再次调用 agent/start，插件可能又拉起 CLI B，旧管道、监听器、定时器和迟到通知也可能继续存在。除非协议明确保证 agent/start 幂等并且能彻底复位，否则重复调用不能证明系统回到了干净状态。

Ora 选择把整个 generation 当作故障隔离边界：先尝试 agent/stop，再由 Lifecycle 结束并回收插件进程树，下一次从新的 main.js、新注册、新管道和新 CLI 开始。这样无需要求每个第三方插件都正确实现复杂的进程内恢复。

Generation 的定义：它不是“Actor 正在消费的消息编号”，而是同一个 Plugin ID 的一次完整进程生命，包括这一代 main.js、注册信息、子进程、RPC 连接和通知流。Actor 不接收旧代消息只是 generation 隔离带来的结果。

当前重试有没有次数限制？

  • Agent CLI 未安装、插件被禁用或暂时不存在：不会因为次数耗尽而停止；从 250ms 开始指数退避，最长间隔 30s，在本次 Ora 进程生命周期内持续尝试。
  • 真正的启动错误或连接崩溃：一分钟内前三次允许重试，第四次失败打开 restart circuit，状态变成 Failing，本次 Ora 进程内停止自动重试。超过一分钟的旧失败会移出计数窗口。
  • Agent 运行时合同不完整：属于确定性错误，立即变成 Failing，不进行无意义重试。

面试表达：Plugin ID 标识安装身份，generation 标识一次具体启动。Lifecycle 的 lease、registration 和 notifications 都绑定 generation；旧 lease 不能自动跳到新进程，迟到通知带 generation 可被识别。替换前还会 shutdown-and-wait，避免同一插件的两代进程重叠。
