Lesson 0008 · Agent Focus

Agent 插件为什么有两个进程？

运行 Agent 插件时，main.js 和真正的 Agent CLI 不是同一个程序。前者是适配器，后者才是提供对话能力的 Agent。

两层分别是谁

Ora Backend需要一种统一方式使用所有 Agent。
Deno 插件进程运行 main.js，把统一合同转换成具体 Agent 操作。
Agent CLI 进程Claude、Codex、OpenCode 等真正的 Agent 程序。
模型与工具由 Agent CLI 自己管理上下文、模型调用和工具行为。
Ora Backend
    ↕ Plugin JSON-RPC
Deno: main.js                 适配器 / 胶水层
    ↕ ACP over child stdio
真实 Agent CLI                真正的 Agent

启动不是执行 main.js 后立刻完成

  1. Agent Supervisor 请求连接已安装的 Agent 插件。
  2. Plugin Lifecycle 按需启动 Deno，并在里面执行 main.js。
  3. main.js 注册 Agent 合同：start、stop、listModels、ACP 通道等。
  4. Backend 验证合同后调用 agent/start。
  5. 插件选择具体 CLI，并通常通过 ora/childprocess/spawn 请宿主拉起它。
  6. 此后插件在 Ora 与 CLI 之间双向转发 ACP 帧。

main.js 不只是“启动脚本”

它至少承担四类适配职责：

  • 决定如何启动与停止具体 CLI；
  • 向 Ora 报告可选模型；
  • 在 Ora 与 CLI 之间转发 ACP；
  • 可选地声明 Skill surface，并配合 Effect 等待空闲和重启。
所有权要分清：插件逻辑上决定并管理 Agent CLI 的生命周期；但为了可靠清理进程树，CLI 通常由宿主的 childprocess API 在操作系统层真正创建和回收。Lifecycle 则是 Deno 插件进程的唯一所有者。

面试表达：Agent 插件采用双进程适配模型。Lifecycle 启动 Deno 执行 main.js，它实现 Ora 统一的 Agent 插件合同；收到 agent/start 后，适配器选择并通过宿主 childprocess 能力启动真实 Agent CLI，再透明转发 ACP。这样 Ora 不需要内置每个 CLI 的启动方式和差异。
