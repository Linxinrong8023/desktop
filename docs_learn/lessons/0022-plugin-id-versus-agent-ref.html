Lesson 0022 · Two Identities

同一个 Agent 插件，为什么有两个身份？

PluginId 回答“Lifecycle 管理哪个安装包”，AgentRef 回答“Session 绑定哪个 Agent provider”。它们来自同一个 Manifest，但字符串不同，不能直接比较。

从一份 Manifest 开始

namespace = "official"
identifier = "ora-space.opencode"
kind = "agent"

Ora 会从中得到两个运行时身份：

身份当前示例回答的问题
PluginIdofficial/ora-space.opencode哪一个已安装插件包和进程？
AgentRefora-space.opencode这个 Session 绑定哪一个 Agent provider？
注意分隔符：PluginId 把 source namespace 与包名用 / 连接；AgentRef 直接使用 Manifest 的 identifier。这里 identifier 自己可以包含一个点，例如 ora-space.opencode。

PluginId 属于插件管理世界

Plugin Manager 和 Lifecycle 需要知道完整安装地址：

PluginId = official/ora-space.opencode

installed/official/ora-space.opencode/<version>
data/official/ora-space.opencode/
Lifecycle.ensure_running(plugin_id)
Lifecycle.stop(plugin_id)

它用于安装、扫描、配置、启动、停止、卸载，以及绑定 Plugin process generation。因为这些操作针对的是一个具体插件包。

AgentRef 属于会话与 Agent Runtime 世界

Session 不关心包安装在什么目录，也不应该直接操作 Lifecycle。它只保存：

session.agent_ref = "ora-space.opencode"

Agent Runtime 以 AgentRef 为键寻找 application-scoped Supervisor：

AgentRef
  ↓ ConnectionSupervisors.for_agent(...)
对应 ConnectionSupervisor
  ↓ Supervisor 内部保存 AgentSource
PluginId + package name

Supervisor 正好位于两个世界的交界处：上层 Session 用 AgentRef 找它；Supervisor 启动时获得的 AgentSource 同时包含 PluginId 和包名，因此它能用完整 PluginId 请求 Lifecycle 管理插件进程。

不是另一张独立映射表：ConnectionSupervisors 的核心索引是 AgentRef → ConnectionSupervisor。发现插件时，Ora 从同一个 InstalledPlugin 取得 plugin.id 与 plugin.name，构造 AgentSource 后交给对应 Supervisor。二者的对应关系因此集中在 Supervisor 创建与同步过程，不需要每个 Session 自己推导。

Session 能不能直接保存完整 PluginId？

技术上完全可以。如果从零设计，并能接受 Session 与插件安装地址直接耦合，直接保存 official/ora-space.opencode 会省掉一次身份转换。当前 Ora 保留两种身份，主要是因为：

  • Session 表达“绑定哪个 Agent provider”，Lifecycle 表达“管理哪个插件安装包”；
  • 已有 Session、历史和协议一直持久化 package identifier，改为完整 PluginId 需要兼容迁移；
  • Session 可以比插件安装状态活得更久，未知 AgentRef 表示暂时未安装，而不是损坏数据。

这是一个带成本的架构选择，而不是语法上的硬性要求：收益是领域语义和历史兼容，代价是必须集中维护两种身份的对应关系。

改用 PluginId，能不能连 Supervisor 一起省掉？

不能。两个 ID 只造成身份转换，Supervisor 并不是为转换 ID 而存在。即使 Session 直接保存 PluginId，仍需要 Supervisor 负责：

请求 Lifecycle ensure_running
→ 调用 agent/start
→ 完成 ACP initialize
→ 发布并维持 Ready connection
→ 管理重试、generation、路由和 teardown

因此，直接保存 PluginId 最多省掉 AgentRef → AgentSource 的身份查找，省不掉 Agent connection 的运行时监督。

为什么不直接比较两个字符串？

"ora-space.opencode"
!=
"official/ora-space.opencode"

如果拿 Session 的 agent_ref 直接去 Lifecycle 查插件，结果永远找不到。当前代码把转换集中在 ConnectionSupervisors 和 AgentSource 附近，避免每个调用方自己拼接 official/。

不要手工补前缀：当前 resolver v1 只有 official namespace，也不代表业务代码应该写死它。正确做法是从验证后的 InstalledPlugin 建立 AgentRef ↔ AgentSource 关系。

插件卸载后，为什么 Session 还保留 AgentRef？

AgentRef 是持久化的开放字符串，不是“当前安装列表”的外键。一个会话可以比提供它的插件活得更久：

Session 仍记录 ora-space.opencode
  ↓ 但 Supervisor 已不存在
for_agent(agent_ref) 查找失败
  ↓
报告 agent_runtime_unavailable
而不是把 Session 判成损坏数据

这样重新安装提供相同 AgentRef 的插件后，会话仍知道自己原来绑定谁；系统不必因为插件暂时不可用而抹掉历史身份。

同一个 AgentRef 被两个插件声称怎么办？

Supervisor 集合按 AgentRef 建立。如果第二个插件声称已经被占用的 AgentRef，Ora 会忽略第二个，而不是让它悄悄接管用户原有会话。因为“让另一个包接管同一 Agent 身份”比拒绝重复来源更危险。

面试表达：Agent 插件同时跨越插件管理域和会话域，因此保留两个身份。PluginId = namespace/name 是 Lifecycle 的包与进程地址；AgentRef = package identifier 是 Session 持久绑定和 Supervisor 的查找键。发现插件时，Ora 从 InstalledPlugin 构造同时持有二者的 AgentSource，并以 AgentRef 索引 Supervisor；上层按 AgentRef 找共享连接，下层按 PluginId 管理插件 generation。这并非唯一可行设计：Session 直接保存 PluginId 可以省掉身份转换，但会改变现有持久化合同，而且仍然省不掉 Supervisor 的连接管理职责。
