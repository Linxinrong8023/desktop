Lesson 0026 · Agent Plugin Author

defineAgent 帮你接好插座，但不会替你实现 Agent

写 Agent 插件时，不需要手工拼出完整的 Plugin JSON-RPC 合同。插件作者把四个业务回调交给 defineAgent，SDK 负责把它们装配成 Ora 认识的标准接口。

先看最小心智模型

插件作者提供四个回调
  start       怎样启动并接通真实 Agent
  stop        怎样停止真实 Agent
  listModels  会话前能展示哪些模型
  onAcp       怎样把 Ora 发来的 ACP 帧交给 Agent
        ↓
defineAgent 装配标准合同
  agent/start
  agent/stop
  agent/listModels
  agent/acp 双向 notification
        ↓
plugin.run()
  发送 ora/register，然后开始处理消息
最容易混淆的时间点：调用 defineAgent(...) 时只是把回调登记到本地 Plugin 对象；调用 plugin.run() 才向 Ora 发送 ora/register；之后 Ora 调用 agent/start，插件才真正启动 Agent CLI。

SDK 自动完成什么？

SDK 自动完成意义
一次性注册三个控制方法避免插件漏写合同名称或漏注册方法
声明并接收 agent/acp建立 Ora 与插件之间统一的 ACP 外层通道
校验 agent/start 参数插件实现只会收到合法的 cwd 与 hostVersion
返回 protocol = acp、acpVersion = 1让所有标准 Agent 插件采用一致的启动响应
把模型结果包装成合同格式补齐默认值并形成 { models: [...] }

插件作者仍然必须完成什么？

defineAgent 只统一“接口形状”，不了解 OpenCode、Claude Code 或其他 CLI 的具体行为。真正的适配仍由插件作者负责：

start(context, send)
  → 决定启动系统命令还是插件随包二进制
  → 请求 Ora Host 创建 Agent CLI 进程
  → 保存进程句柄
  → 持续读取 CLI stdout 中的 ACP 帧
  → 每读到一帧就调用 send(frame) 发回 Ora

onAcp(frame)
  → 把 Ora 发来的 ACP 帧写入 CLI stdin

stop()
  → 执行该 Agent 特有的优雅退出
  → 必要时请求 Host kill
  → 清理本地句柄，允许以后重新 start

listModels()
  → 返回无需创建 Session 就能展示的模型目录

因此，Agent 插件的最小闭环不是“写出四个空函数”，而是同时完成真实 CLI 的生命周期和ACP 的双向管道。

两条 ACP 方向不要写反

Ora → Agent：agent/acp 到达 SDK → SDK 调用 onAcp(frame) → 插件写入 CLI stdin。

Agent → Ora：插件读取 CLI stdout → 插件调用 send(frame) → SDK 包装成 agent/acp notification。

文档漂移提醒：旧说明可能写成“插件自己拥有 Agent 进程，Ora 不接触 stdio”。当前推荐实现是插件决定启动和停止策略，但通过 createHostProcesses 请求 Ora Host 创建并持有真实 OS 进程；插件拿到的是可读写的代理流。这与我们前面学过的“策略归插件、进程机制归 Host”一致。

面试表达：defineAgent 是 Agent 插件合同的装配器。插件作者提供 start、stop、listModels 和 onAcp 四个业务回调，SDK 统一注册三个控制方法和双向 agent/acp notification，并完成参数与返回结构的标准化。SDK 不会替插件理解具体 CLI；插件仍需通过 Host Processes 管理 CLI 生命周期，并在 CLI stdio 与 ACP frame 之间建立透明双向管道。
