一条 prompt 到底在哪里被包装和解析？

同一条消息经过三层代码，但每层只理解自己负责的协议：ACP 层理解 Agent 业务，Plugin Runtime 理解外层信封，main.js 负责适配和转发。

从前端发往 Agent

前端通过 Ora 前端契约发送用户 prompt，不直接构造 ACP。
Session actor + ACP Peer构造带 ACP id 的 session/prompt。
Plugin transport把完整 ACP JSON 放进 agent/acp notification。
main.js取出 ACP，按具体 CLI 的 stdio framing 写给真实 Agent。

  ↓ Ora 前端/后端契约
Session actor
  ↓ 构造 ACP request id=42
ACP Peer
  ↓
agent/acp notification { params: ACP(id=42) }
  ↓ Plugin Runtime framed JSON-RPC
main.js
  ↓ CLI stdio
真实 Agent CLI

Agent 返回前端

真实 Agent CLI
  ↓ ACP 更新 / ACP response id=42
main.js
  ↓ agent/acp notification { params: ACP(id=42) }
Plugin Runtime / plugin_agent bridge
  ↓ 基本不解释 ACP 业务内容
ACP Peer
  ↓ 解析 ACP、按 id=42 找到原 prompt
Session actor
  ↓ 转换成 Ora 会话事件
前端
  ↓ 渲染文本、工具调用、状态等

每层到底理解什么

层理解的内容不负责
Plugin Runtime外层帧、JSON-RPC id、method、注册能力不理解 session/prompt、工具调用等 ACP 语义
main.js adapterAgent 启停、CLI stdio、ACP 转发、Agent 差异通常不替 Ora 处理会话业务
ACP Peer / Session actorACP request/response、session update、取消与路由不关心 Deno 帧怎样编码
前端Ora 的会话事件和展示模型不直接处理插件协议或 CLI stdio
“透明转发”的范围：对 Ora 的 plugin_agent bridge 而言，ACP payload 基本是不透明的；进入 Backend 的 ACP Peer 后才会解析。具体 main.js 可以处理换行 framing，未来也可以把某个私有 CLI 协议翻译成 ACP，但它对 Ora 一侧必须呈现标准 ACP。
SDK 与 main.js 再分一层：Plugin SDK 负责读取四字节长度、帧类型和外层 Plugin JSON-RPC，随后才调用 main.js 注册的 onAcp(frame)。因此 Agent-specific main.js 通常拿到的已经是 ACP JSON 对象；它主要处理 CLI stdio 的读写和 framing，再调用 SDK 的 notify("agent/acp", frame) 发回。业务语义仍由 ACP Peer 处理。

面试表达：前端不感知插件协议。Session actor 通过 ACP Peer 生成 ACP，plugin transport 将整帧作为 agent/acp notification payload 穿过 framed Plugin JSON-RPC；main.js 转给真实 CLI。返回路径相反，Plugin bridge 保持 payload 透明，ACP Peer 才负责业务解析与 correlation，Session actor 再映射成前端事件。
