Lesson 0024 · Model Discovery

模型列表为什么要问两次？

Ora 既能向 Agent 插件调用 agent/listModels，又能从 ACP session/new 或 session/load 的 configOptions 中发现模型。它们不是重复接口，而是回答不同时间、不同作用域的问题。

路径一：插件级 agent/listModels

Ora Backend
  → Plugin RPC request: agent/listModels
  → main.js 的 listModels()
  → { models: [...] }

这条路径不需要先存在 ACP Session。Agent CLI 已由插件启动，但 Ora 还没有为某个 Workspace 创建 provider session，因此它适合回答：

“这个 Agent 总体上愿意提前公布哪些模型？”

Backend 在构建每个 Agent connection generation 时调用一次，并把结果保存进 RuntimeConnection.models。连接重建时才重新读取；插件返回空数组也是正常结果。

路径二：ACP Session configOptions

Ora AcpPeer
  → ACP session/new(cwd) 或 session/load(...)
  → Agent CLI
  → { sessionId, configOptions: [...] }

configOptions 是 Agent 针对这个具体 Session 返回的配置选择器。模型通常是其中一个 select 选项，优先通过 category = "model" 识别。它适合回答：

“在这个目录、账号和 Session 上，现在真正能选哪些模型，当前又选中了哪个？”

选择模型时还需要 agent_session_id，Ora 会发送 ACP session/set_config_option；Agent 返回的新 configOptions 才是最终权威结果。

为什么不能只保留一条？

问题agent/listModelsSession configOptions
需要 Agent Session 吗不需要需要 new/load
作用域Agent connection 级快照具体 Agent Session
能表达当前选择吗只提供 default 提示提供 currentValue
能直接用于修改吗不能可通过 set_config_option 修改
可能受 cwd 等上下文影响吗不带 Session 上下文可以反映 Session 上下文
白话理解：agent/listModels 像商店门口的商品目录；Session configOptions 像进入具体门店后拿到的实时货架与购物车状态。目录可以提前看，但真正下单要以后者为准。

当前前端实际上走哪条？

当前 Chat 和 Workflow 的模型选择器主要使用第二条路径：Ora 先创建一个 Warm Session，让 Agent 通过 session/new 返回真实 configOptions，然后按 AgentRef 缓存模型选择器，减少下一个聊天界面的等待。

Backend 仍实现并保存 agent/listModels 快照，也暴露了 list_agent_models 查询能力；但不能据此断言当前 Chat 选择器完全依赖它。这里要区分“插件合同存在”与“某个前端目前如何消费”。

面试表达：Ora 有插件级和 Session 级两条模型发现路径。agent/listModels 是 Plugin RPC 控制方法，不依赖 ACP Session，结果按 connection generation 缓存，适合提前提供 Agent 级目录；ACP session/new/load 返回的 configOptions 属于具体 Session，能反映 cwd、账号和当前选择，并通过 session/set_config_option 修改。当前 Chat 与 Workflow 主要通过 Warm Session 使用后者，因此协议能力和当前 UI 消费路径要分开描述。
