Lesson 0019 · Trust Boundary

Agent 插件到底安全吗？

Ora 会验证 Agent 插件的身份、结构和通信合同，也会统一回收进程；但这不等于插件代码受到严格的最小权限沙箱。当前 Agent 插件实际上拥有很高权限。

先区分四种“可信”

把插件想成进入办公楼的外部工程师：

检查类比它真正保证什么
下载哈希文件封条没被调包下载内容与发布内容一致，不保证发布者没有恶意
Manifest / Manager证件和工具清单格式正确身份、kind、路径与必需文件满足宿主规则
运行时合同声明会办理哪些业务必需方法和 notification 已注册，不能越过声明乱发协议消息
进程权限进入楼后能打开哪些门代码运行时真正可以读取、联网或执行什么
关键结论：InstalledPlugin 是“结构上可信的宿主视图”，不是“代码绝对安全”的证明；运行时合同完整，也只能证明协议形状正确，不能证明 handler 内部没有恶意行为。

当前 Agent 插件实际拥有什么权限？

Lifecycle 启动 Agent 插件的 Deno main.js 时，当前会授予：

--allow-run       可以执行其他程序
--allow-read      可以读取整个文件系统
--allow-env       可以读取整个进程环境
--allow-net       可以访问网络

它没有直接获得 Deno --allow-write，但 --allow-run 意味着它可以启动具有当前用户操作系统权限的子进程；真实 Agent CLI 本来就需要修改 Workspace、执行工具和访问模型服务。因此不能把它描述成“只能在插件目录里活动的严格沙箱”。

读取风险：插件代码可能读取用户文件和环境变量中的凭据。

联网风险：插件代码可能把读取到的内容发送到网络。

执行风险：插件及其 Agent CLI 可以执行命令，对 Workspace 产生真实修改。

当前源码把 Agent 插件描述为“权限大致接近宿主”，并明确称为一个有意记录、未来再收窄的安全缺口。

那为什么还需要 Host child-process API？

你可能会问：既然 Agent 插件已经有 --allow-run，为什么还要通过 ora/childprocess/spawn？

Host child-process API 主要解决的是所有权和可回收性，不是把高权限插件突然变安全：

  • Host 把子进程绑定到当前 Plugin generation；
  • 插件停止、崩溃、更新或卸载时，Host 会回收整棵进程树；
  • packageCommand 由 Host 在插件安装目录内解析，插件不必自己拼宿主绝对路径；
  • stdin、stdout、stderr 与 exit 被统一建模，跨平台使用 Unix process group 或 Windows Job Object 清理。
Host child-process API
= 谁启动、谁拥有、谁清理的可靠边界
≠ 第三方代码已经受到最小权限隔离

为什么当前会给这么大权限？

Agent 与普通 UI 插件的需求差异很大。它需要：

  • 读取项目文件与 Agent 自身配置；
  • 读取 API key 等环境配置；
  • 连接模型服务与工具服务；
  • 启动 Agent CLI 和命令行工具。

当前实现优先让不同 Agent CLI 能稳定接入，再把能力收窄留作后续安全工程。这是工程取舍，不是安全已经完成。好处是未来可以只调整 Lifecycle 的启动权限或增加 Host capability，而不必改变上层 agent/acp 通道。

已经具备的防护仍然有价值

防护能防什么不能防什么
包与路径验证错误布局、路径逃逸、缺少必需文件合法文件中的恶意代码
不可变能力注册运行中偷偷改变协议面、发送未声明消息已声明 handler 内部做坏事
Host storage逻辑路径逃逸、symlink 穿透、超大文件Agent 广泛读取和执行权限
generation 与进程树回收故障后残留旧进程、旧消息串入新连接进程存活期间主动泄露数据

面试表达：Ora 对插件的“可信”分层处理：安装层验证身份、结构和路径，Runtime 验证不可变能力合同，Lifecycle 与 Host Processes 保证 generation 隔离和进程树回收。但 Agent 插件为了驱动 CLI，目前获得 run、全盘 read、env 和 net 权限，实际接近宿主权限，所以它不是严格的第三方代码沙箱。这是当前明确记录的安全缺口；现有协议边界使未来能够在不改变 ACP 数据面的前提下收窄权限。
