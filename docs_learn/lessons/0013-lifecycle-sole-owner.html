Lesson 0013 · 只学一个原因

为什么插件进程必须统一管理？

因为如果两个模块都能自己启动和停止进程，系统会同时出现两个互相矛盾的“真相”。

只看这个具体事故

第一步：Plugin Lifecycle 启动了 Deno 进程 A，并记录“插件正在运行”。

第二步：Agent Supervisor 不经过 Lifecycle，又自己启动了 Deno 进程 B。

第三步：用户在设置页点击停止。Lifecycle 只知道 A，于是停止 A，并显示 stopped。

结果：进程 B 仍在后台运行。页面说已停止，电脑里却还有真实插件进程。

Lifecycle 知道：进程 A
Supervisor 私有：进程 B

用户点击 Stop
  ↓
Lifecycle 停止 A
  ↓
UI 显示 stopped
  ↓
但 B 仍在运行  ← 系统状态已经自相矛盾

统一管理解决什么

规则变成：

任何模块想使用插件
        ↓
都向 Lifecycle 提出请求
        ↓
只有 Lifecycle 能真正启动或停止进程

这样 Lifecycle 说 running 时，确实有它管理的进程；它说 stopped 时，也不会有其他模块偷偷留下第二个进程。

这一课唯一要记住的句子：统一管理不是为了代码看起来整齐，而是为了让“系统报告的状态”和“电脑里真实存在的进程”始终是同一个事实。

主要原因不是避免重复代码

Claude、Codex、Gemini 对应的 Supervisor，是同一个 ConnectionSupervisor 实现创建出的多个内存实例，不需要为每个插件重新写一套启动代码。

同一份 ConnectionSupervisor 代码
  ├── 实例 A：监督 Claude 连接
  ├── 实例 B：监督 Codex 连接
  └── 实例 C：监督 Gemini 连接

即使把启动代码放进这个公共实现，也能复用代码。真正的问题是：Supervisor 和设置页、更新流程如果都能启动或停止插件，就会有多个模块同时声称自己掌握插件的真实运行状态。因此 Ora 把进程所有权交给 Lifecycle；Supervisor 只提出“请确保它正在运行”的请求。

重复启动还可能进一步造成两个 Agent CLI、两份 ACP 回复和双倍资源消耗，但这些都是“出现两个真实进程”之后的后果，本轮不用继续展开。
