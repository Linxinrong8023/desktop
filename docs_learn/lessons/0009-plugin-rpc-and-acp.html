Lesson 0009 · Protocol Layers

“都用 ACP 通信”为什么还不够准确？

ACP 是 Agent 业务协议，但 Ora Backend 与 main.js 之间还需要插件底座自己的通信协议来启动、停止和承载 ACP。

用快递信封理解两层协议

ACP 帧像信纸上的业务内容：创建会话、发送 prompt、工具调用、流式更新。

Plugin JSON-RPC像 Ora 插件系统规定的快递信封：它既能发送 start/stop 等控制请求，也能把整张 ACP 信纸装进名为 agent/acp 的通知里。

Ora Backend
  │
  │ Plugin Runtime 二进制帧
  │ └── JSON-RPC notification: method = "agent/acp"
  │     └── params = 一个完整 ACP JSON 消息
  ▼
main.js 适配器
  │
  │ Agent CLI 的 stdio
  │ └── 转发 ACP 消息
  ▼
真实 Agent CLI

哪些不是 ACP

消息所属层用途

agent/acpPlugin Runtime notification承载一个完整 ACP 消息

为什么 ACP 用 notification 承载

先认识 request/response

JSON-RPC request 带一个 id，发送者会等待相同 id 的 response：

发送：{ "id": 7, "method": "agent/start" }
等待：{ "id": 7, "result": { "protocol": "acp" } }

这适合 agent/start：Backend 需要知道启动是否成功，并且这个控制调用应该在较短时间内结束。

notification 是只负责投递

JSON-RPC notification 没有 id，外层发送者不等待外层 response：

发送：{ "method": "agent/acp", "params": ACP消息 }
外层到此结束，不等待 agent/acp 的 Plugin RPC response

ACP 内部已经自带 request/response

例如一条简化的 ACP prompt 自己已经有 id：

ACP 请求：{ "id": 42, "method": "session/prompt", ... }
...中间可以持续几分钟并产生很多流式更新...
ACP 响应：{ "id": 42, "result": ... }

如果把这条 ACP 请求再包装成 Plugin RPC request，就会变成：

外层 Plugin request id = 7
└── 内层 ACP request id = 42

这时插件面临两个都不理想的选择：

  1. 立刻回答外层 id 7：只能表示“收到信封”，不能表示内层 id 42 的 prompt 已完成；外层 id 没提供有用结果。
  2. 等 prompt 完成再回答 id 7：prompt 可能运行几分钟，外层控制调用的 timeout 会先到；取消时还要判断取消 id 7、id 42，还是两个都取消。

因此外层只用 notification 把完整 ACP 消息送过去，不再增加第二个 id。真正的请求、响应、取消和长时间运行全部由内层 ACP 的 id 42 管理。Ora 的 Agent adapter 基本不解释、不改写这个 payload，只负责把它送到另一端。

Plugin Runtime 的物理帧：Ora 与 Deno 的 stdio 上，每条消息使用四字节大端长度、一个帧类型字节和 UTF-8 JSON payload。stdout 只承载协议，日志走 stderr，避免普通输出破坏协议流。

面试表达：Agent 插件有协议分层。外层是 Plugin Runtime 的 framed bidirectional JSON-RPC，用于注册和控制调用；ACP 作为 agent/acp notification 的 payload 透明穿过外层，再由适配器转给 CLI。因为 ACP 已有自己的 correlation 和 cancellation，使用 notification 可以避免双重超时与请求关联。
