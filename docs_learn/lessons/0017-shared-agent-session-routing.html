Lesson 0017 · Multiplexing 与 Session Route

一条 Agent 连接，怎么保证多个对话不串线？

Ora 为每个 Agent 维护一条共享 connection，但为每个 Agent Session 建立独立路由。消息不是广播给所有会话，而是根据 agent_session_id 投递到唯一的 Session channel。

类比：一栋楼只有一个大门

共享 Agent connection 像整栋楼共用的大门。

agent_session_id 像房间号。

RouteRegistry 像门卫手中的“房间号 → 独立信箱”登记表。

所有消息都从同一个 Agent connection 进来，但门卫先看房间号，再投入对应信箱，所以 Session A 不会读到 Session B 的事件。

先区分两个 Session ID

ID谁创建主要用途
ora_session_idOra数据库、历史记录、前端与 Session actor 的稳定身份
agent_session_idAgent 在 session/new 时返回；load 时复用已有值ACP 连接上的实际会话地址，也是中心路由表的键

一个 Ora Session 绑定一个 Agent Session。Ora Session 可以长期存在；更换 Agent 或重建连接后，它可以绑定新的 agent_session_id。

不是一张表，而是两张关键表

表键 → 值解决的问题
RouteRegistryagent_session_id → SessionChannel已经知道 Agent Session 后，消息应该投进哪个 actor 的队列？
PendingRequestsrequest_id → agent_session_id普通 response 只有 request ID 时，它原来属于哪个 Agent Session？

路由时不必先把 agent_session_id 转换成 ora_session_id：RouteRegistry 已经直接指向对应 actor 的 SessionChannel。代码里另有一张 agent_session_id → ora_session_id 的 SessionTraceRegistry，但它主要用于日志和追踪，不承担正常事件分发。

路由是什么时候注册的？

Session setup
  ↓ 向共享 AcpPeer 发送 session/new
Agent 返回 agent_session_id = "provider-42"
  ↓
Supervisor.open_session_channel("provider-42", ora_session_id)
  ↓
RouteRegistry 写入：
"provider-42" → Session A 的独立事件队列

每个 Session actor 持有自己的 SessionChannel。这个 channel 包含当前共享 connection、独立事件队列、故障控制队列以及一份自动注销的路由凭证。

发送 Prompt 时怎么走？

Session A actor
  ↓ session/prompt(sessionId = "provider-42")
AcpPeer 分配 request id = 17
  ↓ 记住 17 属于 provider-42
共享 agent/acp transport
  ↓
Agent

AcpPeer 的 pending 表同时记录 ACP request ID 与 Agent Session ID。因此并发的 Session A、B 即使都在等待响应，也能按各自的 request ID 正确关联。

发送之前：
PendingRequests[17] = agent-101
PendingRequests[18] = agent-205

收到 response(id = 17)：
取出 PendingRequests[17]
→ 恢复 agent-101
→ 再查 RouteRegistry[agent-101]

Agent 返回消息时怎么分流？

Agent 回来的消息主要有三类：

消息怎样找到 Session
session/update消息参数本身带 sessionId
权限请求请求参数本身带 sessionId
Prompt 最终响应响应只带 request ID；AcpPeer 从 pending 表找回对应的 agent_session_id
 
Agent 返回 ACP frame
  ↓ Plugin Runtime 解开 agent/acp 外层
AcpPeer 解析并补全 agent_session_id
  ↓
RouteRegistry[agent_session_id]
  ↓
唯一 SessionChannel
  ↓
对应 Session actor
  ↓
对应前端对话

为什么不会因为一个慢 Session 拖垮所有人？

每个 Session 都有独立、有界的 FIFO 事件队列，当前容量是 256。这样：

  • 同一 Session 内，update 与最终 response 保持进入连接时的顺序。
  • Session A 的队列满了，只移除 A 的路由并通知它 overflow。
  • Session B 仍继续使用相同的 Agent connection。

还有三个防串线保护

generation：每条路由记录属于哪一代 connection。旧 generation 断开时只使旧路由失效。

route token：同一个 session id 重新注册后，旧 actor 销毁时不能误删新路由。

setup buffer：session/new 尚未返回 session id 时，Agent 可能已经发送 update；Supervisor 在 setup 窗口暂存它，注册路由后再补投。

职责边界：Supervisor 拥有共享 connection 和中心 RouteRegistry；每个 Session actor 只消费自己的 SessionChannel。Agent CLI 负责生成 ACP 消息，但不需要知道 Ora 的前端窗口或数据库 Session。

面试表达：一个 Agent connection 可以复用给多个 Session。在 session/new 返回 provider session id，或 load 恢复已有 id 后，Ora 在 Supervisor 的 RouteRegistry 中注册一条 generation-bound 路由，目标是该 Session actor 的独立有界 FIFO。通知和权限请求直接携带 session id；普通响应由 AcpPeer 用 request id 从 pending 表恢复 session id，然后统一分流。队列隔离、generation 和 route token 共同防止慢会话、旧连接和旧 actor 污染其他 Session。
