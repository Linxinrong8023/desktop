Lesson 0020 · Symmetric Teardown

启动与退出必须对称

启动 Agent 时依次建立插件进程、Agent CLI、协议连接和 Session 路由；退出时必须反方向拆掉这些资源。只发一句“请停止”远远不够。

类比：关一家仍在生产的工厂

先通知生产线停机：让它保存状态、关闭文件和管道。

再关闭控制室：不再接收新命令，等待正在处理的工作收尾。

最后由总闸兜底：如果有人拒绝退出，就切断并确认整座工厂已经无人运行。

Agent teardown 也是“先礼后兵”：先给插件自行清理的机会，最终仍由 Host 保证操作系统进程树真的消失。

为什么不能只调用 agent/stop？

agent/stop 是 Ora 对 main.js 的控制调用。它表达的是：

“请用你最了解的方式，优雅停止你启动的 Agent CLI。”

插件最了解具体 CLI：可能要关闭 stdin、发送该 CLI 自己定义的退出指令（不是 ora/shutdown）、等待缓存落盘。但插件可能有 bug、已经卡死，或者 Agent CLI 根本不响应。因此它只能是优雅清理机会，不能是最终资源保证。

当前边界：agent/stop 最多等待 2 秒。超时或报错只记录警告，不阻止后续强制清理。

你觉得奇怪，是因为这里有两种“拥有”

所有权谁拥有具体含义
逻辑所有权Agent 插件决定启动哪个 CLI、传什么参数、怎样优雅退出、怎样转发 ACP
资源所有权Ora Host真正保存 OS process handle、stdio 和进程树记录，并保证最终 kill/reap

因此，“插件启动 Agent”更准确地说是：插件提出启动方案，通过 ora/childprocess/spawn 请求 Host 执行；Host 真正在操作系统里创建进程，再给插件一个 processId 用来写 stdin、关闭或请求 kill。

main.js：我要运行 opencode acp，并在停止时先关闭 stdin
Host：我来真正 spawn，保存进程句柄，并保证整棵树最终消失

agent/stop 先询问逻辑所有者：“你知道怎样礼貌结束它，请先处理。”如果逻辑所有者失灵，资源所有者仍能说：“这个 processId 和它的后代归我登记，现在强制回收。”两者不是重复，而是专属语义与最终保证的分工。

agent/stop 不是绕过 Host 的第二条进程管理通道

Ora Backend
  ↓ Plugin RPC：调用 agent/stop
main.js 的 stop() handler
  ↓ Host request：ora/childprocess/closeStdin 或 kill
PluginProcessHost
  ↓ 根据当前 generation 的 processId 查找 OS handle
ora-process
  ↓ 真正执行 close / kill / wait
Agent CLI

也就是说，agent/stop 是一条业务控制命令：Ora 请适配器选择正确的停止动作。只要动作涉及受管 OS 进程，适配器仍要请求 Host 执行。它没有从 Host 手里拿走 process handle，也没有出现第二个进程管理员。

还可以把 processId 理解成 Host 发给插件的一张“取号凭证”：插件可以拿凭证请求写入、关闭 stdin 或 kill；Host 检查它属于当前 Plugin generation 后，才对自己持有的真实进程执行操作。

为什么不让 Ora 一开始就直接杀？

Ora 当然可以直接杀，而且超时后确实会这样做。但直接 kill 是强制终止，Host 不知道每一种 Agent CLI 的优雅退出语义：

  • 有的 CLI 应该先关闭 stdin，让它自己完成收尾；
  • 有的 CLI 需要收到自己的退出指令或信号；这属于 agent/stop 的实现，不是 ora/shutdown；
  • 插件还可能需要清空自己的内存引用、停止输出泵或等待缓存落盘。

这些差异正是 adapter 存在的原因。如果全部硬编码进 Ora，新增一种 Agent 就要修改主程序，重新退化为内置 Agent。

第一选择：Ora → agent/stop → adapter 选择优雅方案 → Host 执行
超时兜底：Ora → Host 直接 kill 仍存活的整棵进程树

这次“绕一圈”换来的不是更多进程控制权，而是把 Agent 专属停止策略留在插件，把通用 OS 执行和最终兜底留在 Host。代价是一轮控制调用，收益是宿主不需要认识每一种 CLI。

CLI 已经退出，还要杀什么？

如果 Agent CLI 已经成功退出，就不需要再杀一次。但还要区分三件事：

动作含义是否每次都发生
exitCLI 自己正常结束，或者收到 kill 后结束执行最终必须发生
kill向仍未退出的进程强制发送终止请求只在需要时兜底
wait / reapHost 确认进程已退出，收集退出状态并清除进程记录无论怎样退出都要做

另外，Agent CLI 退出只结束了第二个进程；执行 main.js 的 Deno 插件进程仍然存在。agent/stop 的 SDK 合同本来就是“停止 Agent，但暂时保留插件进程”。在整个 connection generation 结束时，Lifecycle 才继续用 ora/shutdown 停止 Deno 进程。

agent/stop 成功
  ├── Agent CLI：已经退出 → Host wait/reap，不再强杀
  └── Deno main.js：仍在运行 → Lifecycle 随后停止它

agent/stop 失败或卡死
  ├── Agent CLI：可能仍在运行 → Host 最终 kill + wait/reap
  └── Deno main.js：Lifecycle 发送 ora/shutdown，必要时强杀

完整退出链

Supervisor 判定 connection generation 结束
  ↓ 使这一代 Session routes 失败
agent/stop（最多 2 秒，best effort）
  ↓ 插件有机会优雅停止 Agent CLI
Lifecycle.stop(plugin_id)
  ↓
Plugin Runtime 发送 ora/shutdown
  ↓ 等待 Deno main.js 正常退出
超时仍未退出
  ↓
Host 检查 Deno 与受管子进程树
  ↓ 只强杀仍存活者；等待并回收全部退出状态
才允许新的 Plugin generation 启动

这条链有两次“请你自己停”的机会：agent/stop 面向真实 Agent CLI，ora/shutdown 面向 Deno 插件进程。最终的 kill/reap 则是不相信第三方清理逻辑一定正确的 Host 兜底。

每一层谁负责？

负责人退出职责为什么归它
Supervisor判断 Agent connection generation 已结束，触发 teardown它知道连接是否健康、是否需要替换
Agent 插件 main.js处理 agent/stop，执行 CLI 专属优雅退出只有适配器了解具体 Agent 的停止方式
Plugin Lifecycle停止 Deno 插件进程并阻止 generation 重叠它是插件进程唯一所有者
PluginProcessHost / ora-process强杀、等待并回收完整 OS 进程树只有 Host 能给出跨平台的最终清理保证

为什么必须等待旧树退出再重启？

假设 Host 只发送停止请求，马上就启动 generation 2：

generation 1：main.js A 仍卡住，Agent CLI A 仍占用管道
generation 2：main.js B 已启动，Agent CLI B 也开始工作

这时同一个插件身份下有两套真实进程。旧通知可能迟到，两个 CLI 可能同时修改 Workspace，甚至监听同一端口。generation 标签能帮助识别旧消息，却不能阻止旧进程继续产生副作用。

关键区别：generation 标记解决“这条消息属于谁”；等待并回收进程树解决“旧的执行者是否真的不存在”。两者必须同时存在。

哪些情况都会走清理？

  • Agent connection 异常，需要重试新的 generation；
  • Ora 正常关闭 Backend；
  • 插件被停止、更新或卸载；
  • Deno 插件自己意外退出——Host 仍会清理该 generation 启动的子进程。

所以清理不是只服务“正常关机”，它更重要的价值是在第三方代码失控时仍能收口。

面试表达：Agent 的 teardown 是分层且有兜底的。Supervisor 先使旧 connection generation 和路由失效，再以短超时调用 agent/stop，给适配器优雅停止 CLI 的机会；随后 Lifecycle 停止 Deno 插件并发送 ora/shutdown。Host 最终会等待并回收整棵受管进程树，只对仍存活的进程强杀；确认旧 generation 已退出后才允许替代 generation 启动，从而同时避免旧消息串线和真实副作用重叠。
