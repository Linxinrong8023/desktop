Lesson 0023 · Three Independent Clocks

三个 Generation，是三只不同的时钟

generation 都表示“第几代”，但必须先问：谁的第几代？Ora 里与 Agent 插件主线最容易混淆的是 Plugin process、Agent connection 和 Workspace Effect 三种 generation。

先记一句：同样写着 generation = 3，也不代表三者属于同一件事；不同 owner 的计数器不能互相比较。

第一只时钟：Plugin process generation

owner：Plugin Lifecycle
身份：PluginId + PluginGenerationKey
推进：同一个插件进行新的进程启动尝试

它描述某个 main.js 插件进程的具体一生。Lease、运行时注册、Plugin RPC、notification 和 Host 管理的子进程树都钉在这一代。旧进程结束后，旧 lease 不能自动跳到新进程。

第二只时钟：Agent connection generation

owner：Connection Supervisor
身份：AgentRef + connection generation
推进：一条新的 Agent connection 完成启动和 ACP initialize

它描述“第几条已经 Ready 的 Agent 连接”。Session 路由、Warm Session 和每代读取一次的模型列表都绑定这一代。旧连接失败时，Supervisor 使这一代路由失效；下一条成功 Ready 的连接才推进计数。

当前 Agent 故障恢复会结束其背后的插件进程，因此新 connection 通常也伴随新 Plugin process generation；但两个计数器由不同模块拥有，数值没有相等合同。例如某次插件启动没有完成 ACP initialize，Plugin generation 已经发生，connection generation 却不会因此成为 Ready 的新一代。

第三只时钟：Workspace Effect generation

owner：Effect 系统
身份：WorkspaceId + Effect Generation
推进：完整的 Workspace Skill 期望状态被新版本替换

它描述“这个 Workspace 想要哪一版 Skill 集合”，用于 compare-and-swap，以及区分 desired、observed、applied、ready 状态。它不是进程编号，也不是连接编号。

所以插件收到下面的调用时：

effect/restart {
  generation: 7
}

这里的 7 表示“完成重启后应当看到 Effect 期望状态第 7 版”，不是“重启 Plugin generation 7”。Effect 只是使用当前 live Plugin lease 协调消费者；参数属于 Effect 系统。

一个最小场景

Plugin process generation = 5
Agent connection generation = 2
Workspace Effect generation = 9

用户启用一个新 Skill
↓
Workspace Effect generation = 10

此时只保证 Effect generation 改变。如果 Agent 支持不中断热加载，Plugin process 仍可保持 5，Agent connection 也可保持 2。是否需要协调或重启取决于插件声明的 Effect 策略，不能把 Effect 更新直接等价成进程重启。

面试表达：Ora 中的 generation 不是一个全局序号，而是不同 owner 的单调版本。Lifecycle 的 Plugin generation 隔离每次 main.js 进程生命；Supervisor 的 connection generation 隔离每条完成 ACP 初始化的 Ready 连接及其路由；Effect generation 版本化一个 Workspace 的完整 Skill 期望状态。三者可能因同一次故障联动变化，但数值不可比较，也不存在必须同步递增的合同。
