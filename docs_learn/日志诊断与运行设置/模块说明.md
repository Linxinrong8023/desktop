# 日志诊断与运行设置

> 核对日期：2026-09-10；依据本地 `project_learn` 分支源码。本文是当前实现学习说明。

[返回学习导航](../README.md)

## 模块职责

理解公开错误、请求完成日志、日志级别保存与故障定位证据。

## 设计逻辑与执行流程

`ora-logging` 集中设置进程 subscriber、JSON 格式、文件 rotation 和固定时区；各层用包装宏记录结构化上下文。外层请求生命周期记录一次完成，底层不重复打印同一传播错误。

日志基本字段为 timestamp／level／target／message，可加 request_id／trace_id、context 与 error。公开错误给 UI 稳定类型和诊断身份，具体来源链在内部保留。

Desktop 用 `ORA_LOG_LEVEL` 覆盖本次进程有效级别，否则读取保存偏好，默认 info。环境覆盖不改数据库。

运行时切换级别由 manager 串行化：先改过滤器，再保存偏好；保存失败回滚过滤器，调用者取消也要完成已经开始的提交或补偿。LoggingGuard 必须存活到退出，确保后台 writer 有机会排空。

## 数据库表与持久化

| 数据 | 存储 | 写入时机 |
| --- | --- | --- |
| 用户日志级别偏好 | `user_config`，key=`log_level` | 保存运行设置 |
| 结构化日志正文 | `<app_data_directory>/logs/ora.log` 的日轮转文件 | 事件输出；当前配置保留三天 |
| 当前 filter、环境覆盖、请求进行态 | 内存 | 进程运行期间 |
| Effect 审计 | `effect_audit_events` | Effect 业务变化；与普通运行日志不是同一体系 |

没有普通 logs／request_logs 表。诊断下载复制当前日志文件到用户选择的位置，不从数据库重建日志。事件时间使用本地 RFC 3339 偏移，SQLite 审计常用 epoch 毫秒；日志文件轮转后缀仍按底层 writer 的 UTC 边界生成。

## 目前存在的缺陷与限制

- **已确认的性能取舍**：日志通道非丢弃模式，sink 长时间阻塞会向调用者施加背压。
- **已确认的退出限制**：退出只给后台 writer 有限排空时间，慢 sink 下仍可能丢尾部日志；不能把日志当成唯一业务提交凭证。
- **已确认的保留限制**：三天日志不是长期审计库；需要长期审计的业务应有独立持久事实。
- **已确认的时间差异**：本地事件日期可能与按 UTC 轮转的文件后缀不同，定位问题应看记录 timestamp。
