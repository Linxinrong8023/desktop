## 日志写着“成功”，数据库没有记录，该信谁？

用户切 Agent 后发生异常。日志有“准备完成”，界面有成功提示，历史文件却缺 handoffDelivered。要定位故障，首先明确每个日志事件证明哪个步骤，不能拿一句普通日志当业务提交凭证。

整体设计：结构化日志提供时间、关联身份与错误来源链；业务记录提供可恢复的状态与操作责任。日志级别是可动态调整的运行设置，改变它也有应用与持久化的失败窗口。

## 为什么稳定错误码与内部来源链要分开？

### 当前实现与演算

直接将 SQLite/Git 错误文字返回 UI，可能包含路径、敏感内容，且不同版本字符串变化破坏前端判断。**当前实现**：公开错误用 `{code, params, requestId}`；外层请求生命周期记录一次关联完成，内部保留 source chain 便于诊断。

```text
用户界面：稳定错误码 + 安全参数 + requestId=REQ1
诊断日志：REQ1 / trace / Session S / 失败阶段 / 内部错误链
业务查询：sessions 绑定、JSONL 交接债务、Effect Operation 或 Git job
```

requestId 帮助串联请求，不是持久业务幂等键，也不是所有流取消的 call ID。重复传播同一错误不应每一层各打印一条“最终失败”，否则误导故障次数。

连续追问“有来源链就一定可安全导出吗”：不一定，调用方仍需控制字符串内容，日志框架不是自动脱敏保险。**可能方案**是安全字段白名单与导出审查，保存脱敏规则版本/导出范围；成本是可能丢诊断信息，未知第三方文本截断或过滤，不能原样转发凭据和 prompt。

## 为什么普通日志不能替代业务操作表？

### 当前行为与完整反例

日志可能按级别被过滤、轮转删除、排队未落盘，退出只有有限排空时间。Host 日志和插件日志策略还不同：Host 非丢弃通道可背压；插件日志按行数/字节有界，满时计数丢弃，不能让第三方大量 stderr 堵住协议 reader。

| 信息 | 介质 | 恢复时能否依赖 |
| --- | --- | --- |
| “准备提交 OP1” | 普通日志文件 | 只证明执行到记录点，且可能缺失 |
| OP1 phase=prepared | effect_operations | 已登记外部操作责任 |
| handoffDelivered | Session JSONL | 按其具体语义证明一次发送接受 |
| J1 pending | git_cleanup_jobs | 仍负有清理责任 |
| desired/applied/ready | effect_target_status | 对应版本进度 |

没有普通 logs/request_logs 表。Effect audit 是业务审计体系，不等于普通轮转日志。当前 Host 日志保留三天，不能承担长期审计。事件 timestamp 用本地时间偏移，文件轮转按 UTC 日界，所以文件后缀和本地日期可能不同。

### 连续追问：把日志改为同步落盘就可以了吗？

同步增加耐久成本，也仍没有让“写业务表”和“写日志”原子。先日志后事务可能记录未发生成功，先事务后日志可能缺日志。**可能方案**：在业务事务内写审计/outbox，再异步导出；新增审计序号、对象和安全负载，成本是写放大/保留政策。导出失败保留责任并重试，普通日志继续用于诊断，不能回填猜测的成功事件。

## 改日志级别为什么也要补偿？

### 当前实现与演算

Desktop 本次进程可用 ORA_LOG_LEVEL 覆盖；否则读保存偏好，默认 info。环境覆盖不修改数据库。运行时设置 manager 串行化改变：先切过滤器，再保存 `user_config(key=log_level,value=...)`，保存失败回滚过滤器；调用方取消等待不能中断已开始的提交/补偿。

| 时刻 | 有效 filter | 数据库偏好 | 说明 |
| --- | --- | --- | --- |
| t0 | info | info | 一致 |
| t1 应用新值 | debug | info | 短暂中间窗口 |
| t2 保存成功 | debug | debug | 提交完成 |
| t2 保存失败 | 回到 info | info | 补偿后返回失败 |

这不是 SQLite 对内存做事务，而是所有者串行协调。保存失败而回滚也失败时应报告真实不一致，不伪造已恢复。用户只查数据库也不能知道本次环境覆盖后的实际级别。

**可能方案**：展示有效值、持久值和覆盖来源三列，必要时记录变更 operation 结果。无需把每条日志入库；代价是 UI/合同复杂，状态不一致时明确标记，不能以持久偏好冒充当前生效。

## 进程内 scheduler 能不能承担所有恢复重试？

**当前实现**：调度器有显式时区，注册前解析 cron，同一个 cron 不重叠，错过 tick 不补跑；关闭拒绝新任务并等管理任务清空。它是进程内调度，句柄表达取消/detach，不是持久队列。

例：更新检查定时器在退出期间错过一个 tick，下次启动重新检查即可；Git cleanup 责任却不能丢，必须先存在 job 表。**可能方案**若需要持久周期任务，要保存 schedule、下次时点、claim、执行结果和 missed-tick 策略；代价是时钟与重复执行，仍需任务幂等。不能仅换一个定时器库就获得分布式调度。

## 完整业务推演：排查一次交接失败

从 requestId 找到 S 的请求阶段，再查 `sessions` 当前 Agent/provider 绑定，读取 JSONL 中 agentSwitched、用户输入和 handoffDelivered，判断失败窗口。若绑定已变但记录缺失，日志只能帮助定位原因，不能自动补造交付回执；若写历史降级，检查持久 reason。导出日志由 Host 保存动作进行，前端不拿任意私有日志路径。涉及 MCP 时只记录 ID/版本/稳定错误码，不把配置值、headers 或命令环境贴进诊断包。
