## 下载到了 100%，为什么重启后还不能直接安装？

用户下载更新后退出，第二天网络不可用。缓存目录有一个完整包，但宿主还需要判断它是否属于当前平台、哪个发布身份、签名信任根是否仍匹配。下载完成和可信可安装不是同一事实。

整体设计：更新服务串行管理状态，下载产物先在 staging 完整验证再提交，Ready 必须携带真实可安装产物。重启后重新用发布信息核对缓存，安装前再次验证；坏新包不覆盖已经可用的旧 Ready。

## 为什么校验摘要还要验签？

### 当前实现与反例

摘要验证包内容和期望哈希相同；如果攻击者同时替换包和旁边的哈希文件，两者仍一致。签名把内容与受信任发布者关联。**当前实现**：缓存恢复和安装前检查 manifest 发布身份、target、bundle、信任根、摘要及签名；旁边的缓存记录不能自我授予信任。

| 输入 | 能证明 | 不能证明 |
| --- | --- | --- |
| 文件长度/下载完成 | 传输获得这些字节 | 是正确包 |
| SHA-256 一致 | 与预期内容一致 | 预期来自可信发布者 |
| 验签通过 | 对应信任根签名 | 当前平台可安装/当前应采用 |
| 版本、target、bundle 匹配 | 与本次升级合同相符 | 操作系统安装必成功 |

**可能方案**：若要求离线重启可安装，持久化可独立验证的签名发布元数据、有效期和撤销政策。新增信任元数据与时钟处理，成本是过期/回滚攻击管理；缺可信时钟或元数据过期时不宣称完全可信，必要时转手动。当前不能仅因包在磁盘就保证离线恢复 Ready。

## 为什么新包要整个目录提交？

### 当前实现与完整演算

直接写 Ready 路径，下载中断就可能破坏原可用产物。**当前实现**：版本化缓存布局为 `~/.ora/cache/desktop-updates/v2/staging` 和 `entries/<artifact-id>`，安全身份名称不直接拼接原始 manifest 字段。payload 和记录完整后将目录 rename 提交，新 artifact 成功后才替换旧 ready。

```text
初始：entries/A1 完整可信；内存 Ready(A1)
下载：staging/T2 部分内容，A1 保留
验证：T2 完整、身份/签名通过
提交：T2 -> entries/A2
采用：内存 Ready(A2)，随后处理旧缓存
```

断在下载阶段只留下未提交 staging；断在目录提交后、内存采用前，重启可以发现 A2，但仍需按当前 manifest 核对。当前没有 app_updates 表，运行 Checking/Ready/安装句柄在内存，缓存文件承载产物。

连续追问“rename 原子就能抗所有断电吗”：目录可见性与物理耐久要分开；数据库也不参与这次事务。**可能方案**是明确同步文件/目录并做断电故障验证，记录完整产物身份与清理责任；成本是 I/O，失败保留旧 A1，不宣传未经测试的硬件保证。

## 检查失败和安装失败为什么不能都清空 Ready？

### 当前实现与演算

新一次联网检查失败，不代表已有 A1 损坏。普通 installer 失败也不一定使下载包无效。**当前实现**：检查失败保留已有 Ready，普通安装失败恢复 Ready 供重试；验证失败才使坏产物失效。单一操作锁避免多个检查/下载/安装同时改相同状态。

| 故障 | 合理状态 | 依据 |
| --- | --- | --- |
| 网络检查失败 | 原 Ready 可以保留 | 已有有效产物不因网络错误改变 |
| 安装器普通失败 | 回 Ready | 包仍可用，系统安装未成功 |
| 安装前摘要/签名失败 | 失效坏缓存 | 不再具备可信证据 |
| Linux 非 AppImage 安装形态 | ManualUpdate | 该路径不能安全原地更新 |

每次后续检查重读网络代理，不能复用永远不变的旧设置。当前更新下载/安装与应用重启由平台能力完成，不存在一个跨平台全部原子的“升级事务”。

**可能方案**：增加安装尝试记录、目标版本、重启确认和健康回执，为自动回滚提供依据。成本是双版本空间、数据库兼容与平台机制；新版本启动失败时旧二进制未必能读新数据库，必须预先设计可回退 schema/备份，不能只保留旧安装包就承诺自动回滚。

## Sidecar 为什么也要有独立的供应链检查？

**当前实现**：下载型 Deno/ripgrep 固定 release/target 与归档和可执行文件的摘要；缺 pin 或校验失败拒绝安装。先验证归档，再验证普通 executable，原生目标检查版本，全部成功才替换；外平台二进制不在本机执行。`--force` 不是绕过校验。ora-reaper 从仓库源码构建，不属于同一下载链。

若只校验压缩包，包内目标文件选择错误仍可能安装错程序；若只校验文件名，路径穿越/链接/异常解压量仍可伤害宿主。通用归档组件负责条目、路径、大小、倍率等边界，不能由每个安装脚本随意解包。

**可能方案**：为构建产物加入可验证来源声明并统一追溯版本。需保存构建身份、源码摘要和验证结果，成本是发布基础设施；证据缺失不偷偷降级“接受任何下载”。

## 完整业务推演：A2 下载好后被外部修改

A2 原本进入 Ready，外部进程改了 payload。用户点击安装，服务重新读取校验，失败使 A2 失效，不能因为内存还叫 Ready 就直接执行。若只是联网失败而 A1 在本进程已有效，保留 A1；跨进程重新认可缓存则依赖新 manifest。数据来源和核对时机决定结论，不是看目录名字。
