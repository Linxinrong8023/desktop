# 应用更新与安装包恢复

> 核对日期：2026-09-10；依据本地 `project_learn` 分支源码。本文是当前实现学习说明。

[返回学习导航](../README.md)

## 模块职责

学习桌面应用如何检查更新、持久化安装包、重启恢复及再次验签。

## 设计逻辑与执行流程

Desktop UpdateService 用 scheduler 进行启动后延迟检查和周期检查，所有更新操作共用锁。manifest 解析、版本比较和下载由 Tauri updater 负责。

新包先下载／验证，在 staging 准备 payload 与记录，再将整个目录重命名到 entries 下。新 artifact 完全提交后才替换旧 ready 包。

重启后磁盘有缓存不代表立即可安装：需要新 manifest 的发布身份、目标平台、bundle、签名和信任根匹配，并重新检查文件内容与签名。SHA-256 只能检测损坏，不能替代签名信任。

安装前再次读取／验签；安装失败保留可重试 Ready，验证失败移除坏包。代理每次检查前从 Backend 读取，用户修改后无需复用旧代理对象。

## 数据库表与持久化

| 数据 | 存储 | 何时写入 |
| --- | --- | --- |
| 下载包、身份／校验记录 | `~/.ora/cache/desktop-updates/v2/staging` 与 `entries/<artifact-id>` | 下载校验后原子目录提交 |
| 运行时 Ready／Checking／安装句柄 | 内存 RuntimeUpdateState | 当前进程服务推进 |
| 网络代理 | `user_config` 的 `network_proxy_settings` | Settings 保存，检查时读取 |

没有 app_updates 表。artifact-id 是内容寻址安全名称，不能把原始 manifest 字段当路径。启动清理未提交 staging 和已被当前版本取代的缓存；可疑缓存不能只凭旁边的记录文件恢复信任。

## 目前存在的缺陷与限制

- **已确认的平台限制**：Linux deb／rpm／裸可执行安装转入 ManualUpdate，不按 AppImage 通道强行覆盖。
- **已确认的离线限制**：上一进程下载的包需要新 manifest 重新确认；磁盘文件存在不等于离线就能自动进入 Ready。
- **已确认的事务边界**：本地缓存提交是文件系统协议，不是数据库事务；安装与应用重启还由平台 updater 决定。
