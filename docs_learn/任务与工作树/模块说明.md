## 数据库没有任务，但磁盘出现了一份代码，谁来负责？

创建隔离任务需要真实 Git 操作。Git 成功后应用可能崩溃，还没写 tasks；删除 tasks 后也可能崩溃，工作树尚未移除。两种情况都不能靠重新加载列表解决。

整体设计：创建前预留资源和固定基线，Git 完成后事务公布业务记录；删除时把隐藏业务对象与清理责任一起提交，后台依据持久身份幂等清理。业务完成与物理清理完成分开。

同一任务换 Agent 时继续使用同一个 Workspace/工作树，省去寻找目录、搬运改动和重新确认基线；不同任务并行才使用不同工作树隔离文件修改。Git 工作树不绑定某一种 Agent，Ora 的价值在统一所有权与交接流程，不能声称其他工具技术上无法进入同一目录。隔离工作目录也不保证最终合并无冲突。

## 为什么先把分支解析成 commit？

### 当前实现与演算

用户选择本地 main，此刻指向 C100；创建期间另一个工具把 main 移到 C101。若直到执行 Git 命令才重新取 main，会让用户看到的基线与实际基线不同。

**当前实现**：校验本地 Git 仓库和显式 base ref，先解析固定 commit，再创建 linked worktree。分支与目录检测冲突，包括目录没有但分支残留的情况，身份重试有界。

| 保存内容 | 示例 | 用途 |
| --- | --- | --- |
| worktrees.workspace_id | W1 | 与 Workspace 同一身份 |
| worktrees.branch_name | ora/某个唯一前缀 | 核对实际 checkout 分支 |
| worktrees.base_commit_id | C100 的完整 commit ID | 固定比较基线 |
| tasks | T1, workspace_id=W1, title=修复重试 | 用户标签 |

main 后来移动不改 C100。浏览本地分支不会隐式 fetch/prune，离线与网络副作用有明确边界。

连续追问“用户本来想要最新 main 呢”：需定义选择时还是创建时的最新。**可能方案**是显式 fetch 后显示解析 commit 并确认此次基线，保存远端/ref/解析时间；代价是网络和凭据，fetch 失败不偷偷用旧本地 ref 冒充最新。当前默认本地规则更确定。

## 创建前的 lease 保存了什么？

### 当前实现与完整失败演算

`worktree_provisioning_leases` 在 Git 变更前记录 project_id、workspace_id、repository_root、checkout_root、branch_name、lease_expires_at。执行期间续租，成功提交任务、工作区、工作树时删除 lease。

| 中断点 | 数据库 | Git/文件 | 下一步依据 |
| --- | --- | --- | --- |
| 登记 lease 后 | 有 L1，无 T1 | 尚未创建 | 租约/原资源事实 |
| Git 已成功 | 有 L1，无 T1 | W1 已存在 | 不能当无主垃圾立即删除，先识别创建者/租约 |
| 最终事务成功 | T1/W1/worktree 齐全，L1 删除 | W1 已存在 | 正式位置与基线 |
| 项目并发删除 | 提交时 P 已不可见 | W1 可能已创建 | 不能暴露 T1，移交清理责任 |

最终事务重新检查项目可见性。慢 Git 不在 SQLite 写锁中运行；这是缩短锁持有的选择，代价是必须保留中间责任与补偿，而不是假装没有窗口。

**边界与缺口**：lease 过期说明创建者没有按期续租，不证明目录没被用户接管或 Git 已停止。**可能方案**是更强的进程尝试关联和目录 native identity，保存启动/收尾回执，代价是宿主集成；证据不足标待人工，不能拿过期时间授权递归删除。受管 Node 链路提供另一套更强责任模型，但不能直接声称 Desktop 已全部采用。

## 为什么清理任务必须和软删除一起存？

### 当前实现与数据变化

先删业务行再发内存队列，崩溃会丢清理；先清磁盘再删行，会让仍可见任务失去目录。**当前实现**：在同一删除事务写软删除和 `git_cleanup_jobs`。

```text
删除前：tasks(T1).is_deleted=0，W1 可见，Git checkout 存在
同一事务：T1/W1 等关联软删；写 J1
J1 = {project_id:P, workspace_id:W1, repository_root:/repo/app,
      checkout_root:/worktrees/w1, branch_name:ora/..., state:pending,
      attempts:0, next_attempt_at:t0}
提交后：列表不可见；worker 尚可能未执行
完成后：J1.state=completed；Git 资源清理完毕
```

清理失败保存 attempts、last_error、next_attempt_at，退避或进入 manual_attention。jobs 与 leases 无业务外键，允许业务记录不可见后继续持有清理证据。已不存在的自有资源可以安全结算，未知非空目录应保留。

Git 审查、暂存、提交、推送等已接入共享使用租约，物理清理取独占租约；普通文件读取并不全在这个租约内，不能说所有访问都被锁保护。

### 连续追问：只看路径和 branch 还安全吗？

用户可能删除 W1 后在同一路径建立新目录，或修改分支。当前清理核对保存的仓库/分支/checkout 归属，拒绝不确定资源；它只清 Ora 负责的本地资源，不删除远程分支和 provider 历史。

**可能方案**：持久资源 tombstone 与更强目录身份，防路径复用；每次清理重新校验。成本是平台身份差异，缺少证明就 manual_attention，而不是“为了完成删除”扩大清理范围。

## 完整业务推演：清理成功但记账失败

J1 已移除 worktree，写 completed 时数据库失败。下次仍看到 pending，worker 再次核对；如果自有资源已不存在，可以完成 J1，不需要重新创建再删除。若目录被新用户文件占据，应保留并报告，不因“上次应该是我的”继续删。这个例子说明至少一次重试必须配合幂等与所有权检查；重试次数不是安全证明。
