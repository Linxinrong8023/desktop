## 添加一个“代码审查专家”，到底添加了什么？

用户创建角色“严格审查者”，再导入一个包含 SKILL.md、脚本和参考资料的技能包。角色让提示内容可复用，技能包提供可读取的能力说明和资源；两者都不会凭空安装一个 Agent CLI。把这三种东西都叫 Agent，会在解释“为什么不能执行”时失去边界。

整体设计：角色正文存在数据库；Skill 的元数据在目录表、正文和资源在文件包。包与表通过操作 journal 协调，导入先预览后逐项提交，工作区实际交付另由 Effect 负责。

## 为什么角色存在表里，Skill 却不能只存一段 Markdown？

### 当前实现与演算

**当前实现**：`agents` 是角色定义表，包含 `content`；`skills` 包含 namespace/name/description，但没有正文列。本地 Skill 在 `atoms/skills/<name>/`，可能含 SKILL.md、scripts、references。插件来源技能通过其不可变安装包解析。

| 介质 | 示例投影 | 意义 |
| --- | --- | --- |
| agents | id=ROLE1, namespace=local, name=reviewer, content=“先检查边界再给结论” | 角色材料 |
| skills | id=K1, namespace=local, name=retry-review, description=“检查重试幂等性” | 目录身份 |
| 文件 | retry-review/SKILL.md、references/checklist.md | 技能实际内容 |
| sessions | S, agent_cli=demo/agent-a | 执行者身份；不外键指向 ROLE1 |

聊天会展开已知角色引用；未知引用不伪造角色内容。Skill 列表实时检查 package availability，缺目录或无法解析根 SKILL.md 会标 unavailable，不因此删除目录行或使整个列表失败。

连续追问：为什么不删 unavailable 行？因为删除会丢失身份和引用恢复能力。同名缺包技能可恢复原 ID。反过来，文件存在也不代表系统可随便认领为已管理包。

**可能方案**：若要远程分发技能，可把包放内容寻址对象存储，表记录不可变摘要、来源和可用副本。它解决文件包跨设备分发，成本是下载缓存与垃圾回收；下载未完整校验前仍 unavailable，不用元数据存在冒充包可用。

## 文件改好了但数据库写失败，怎样不把包弄丢？

### 问题与直观方案

先写表再写文件会留下“目录显示新名字，文件仍在旧路径”；先改文件再写表也会留下反方向不一致。把文件复制放进数据库事务里并不能回滚文件，反而长时间占着写锁。

### 当前实现与逐步演算

**当前实现**：在同一技能根下使用 `.ora-staging`、`.ora-backup`、`.ora-journal`。操作顺序为暂存完整包、Prepared journal、切换正式目录、Swapped journal、提交行、清理补偿资料。journal 包含不可变 skill ID，已有包的替换还记录之前行版本。

以 K1 从 retry-review 改为 retry-audit 为例：

| 阶段 | skills 行 | 正式文件 | journal/备份 | 失败后依据 |
| --- | --- | --- | --- | --- |
| 原始 | K1/name=retry-review | 旧包 | 无 | 一致 |
| Prepared | 仍旧名 | 仍旧包 | 新包暂存、操作意图 | 未切换则放弃暂存 |
| Swapped | 仍旧名 | 新路径新包 | 旧包备份保留 | 行未提交则补偿目录 |
| 行提交 | K1/name=retry-audit | 新路径新包 | journal 尚可能存在 | 根据 ID/旧行版本判断已提交 |
| 收尾 | 新名 | 新包 | 清理 journal/备份 | 正常一致 |

编辑元数据先复制旧包，只改必要 manifest 字段，保留未知 front matter、正文与附属文件。名称拒绝点开头，避免技能名撞上内部事务目录。启动先恢复在途事务，再对外服务。

### 连续追问：同名技能删掉又建了一个，旧 journal 怎么办？

名称会被复用，所以要核对 K1，而不是只找 retry-review。同名新记录 K2 不应被旧恢复动作覆盖。旧行版本还能区分同名更新未提交、已提交或已被更晚更新取代。

**边界与缺口**：这是 journal 补偿模型，不是数据库跨文件天然原子性。Windows 目录刷新是尽力，macOS 普通 fsync 不等于 F_FULLFSYNC；不能宣传全部平台物理断电零损失。外部直接改目录也会绕过协议。

**可能方案**：增加目录内容摘要与恢复诊断报告，遇到 journal 与实际包不一致时隔离而非猜测性覆盖。新增证据和人工决策，成本是存储/哈希；无法确认旧包归属时保留冲突资料，避免把恢复变成误删。

## 批量导入为什么不是“全成功或者全失败”？

### 当前实现与完整演算

导入 prepare 把一个来源快照到临时目录，按最近祖先的精确 SKILL.md 边界分包；校验路径、大小与 manifest，给每个候选 ready/conflict/invalid。准备阶段不改正式资料。同来源存在大小写不敏感重名候选会使准备失败，避免不确定覆盖顺序。

```text
预览候选：A=ready，B=conflict(K2)，C=invalid
用户决定：B=overwrite
提交：冻结决定，按稳定顺序处理
A 提交成功；B 在真正提升前发现并发占位 -> staleConflict；C 保持无效
结果：A 保留，不因 B 失败回滚
```

每个候选用上一节的包事务协议。提交接纳后后台工作不因调用者关闭页面而取消；同一内存导入会话用相同决定重试复用结果，用不同决定重试拒绝。导入会话本身在内存并会过期，不能把这个幂等性扩大成跨重启永久请求去重。预留进度发布端口的默认实现不发送总线进度，不能凭接口存在宣称已接通。

### 连续追问：预览 ready，提交怎么又冲突？

预览不是持久锁。另一窗口可能先创建同名技能或占据目标目录。此时是 staleConflict，不应当作临时 I/O 错误无限重试。

**可能方案**：持久批次 ID、来源摘要、候选身份、用户决定和逐项结果，允许重启继续查询；代价是临时来源保留与过期清理。每项依然单独提交，恢复时先确认已经成功项，不能整批再导入。若产品必须整批原子，需要全局暂存与提交协议以及更昂贵的补偿，不应仅在 UI 改成一个进度条。

## 完整业务推演：导入以后工作流仍用不到

1. K1 的文件与 `skills` 行通过 journal 一致提交，目录列表显示 available。
2. 这只证明全局目录包可用；工作流部署还需解析所需技能，并通过 Effect 交付到目标工作区资源。
3. 交付回执冻结实际调用名和绝对包路径，后续节点使用回执，不按可变名称重新猜目录。
4. 若用户随后更新 K1，全局源产生新版本；已有运行的冻结依据与消费者就绪要分别处理，不能把“编辑已保存”当成所有进行中会话已读取新正文。

## 脱离案例自测

**问题链：为何 Skill 用文件包 → 两个介质如何一致 → 崩溃时怎么区分提交前后 → 名称复用怎么办 → 批量幂等为什么不跨重启 → 导入成功为何不等于可执行？**

<details><summary>分析提示与参考思路</summary>

沿身份、journal、行版本和交付回执回答。比较数据库提交前后、清理前后四个窗口，不只说“失败回滚”。测试应保留附属文件和未知 manifest 字段，注入目录提升失败/行写失败，覆盖 K1 删除后 K2 同名与预览后的并发占位。跨重启幂等需要持久批次，工作区生效需要 Effect 的资源和消费者证据。角色引用只是输入展开，不为 Agent 安装运行能力。
