# Ora 核心工程措施

本文面向熟悉软件开发、但未参与所有模块的开发者。保留 **12 项重点措施**，按功能解释使用场景、实现机制和保证范围；细项仍放在[完整清单附录](工程措施完整清单.md)。文中的 Host 指 Ora 宿主程序，Agent 指通过插件接入、实际执行模型请求和工具操作的程序。

本文按源码核对工程行为。规格中的 `approved` 表示方案获批，不等于已经实现；不将未交付方案计入已完成功能。

## 工作流：让执行版本、执行进度和失败恢复都有依据

### 1. 草稿与运行版本隔离

**为什么需要。** 工作流定义包含节点、连线和节点配置，例如 Agent 的提示词、条件分支和变量引用。用户修改这些内容时，已有任务可能还在运行。如果执行引擎每走一步都读取编辑器的最新内容，同一次运行就可能前半段使用旧规则、后半段使用新规则，排查失败时也难以还原当时的配置。

**如何实现。** 系统区分三个对象：草稿是可持续编辑的工作副本；发布快照是发布时复制、校验并保存的固定版本；Run 是一次执行记录，绑定所用快照。保存草稿不会不断创建发布版本；发布时才在事务中生成快照并切换当前发布版本。运行读取绑定的快照，后续编辑不会自动改变它。

```text
编辑草稿 → 发布快照 V1 → 运行 A 绑定 V1
继续编辑 → 发布快照 V2 → 后续运行可使用 V2
                         运行 A 仍使用 V1
```

**具体效果与边界。** 例如运行 A 正在生成代码，此时把后续测试节点从“单元测试”改成“集成测试”，A 不会被这次编辑悄悄改变。失败运行接管新快照属于显式操作，需要单独做兼容性处理。快照固定的是工作流定义，不会冻结模型、远程服务或所有外部数据，因此不能据此承诺输出完全可复现。

实现入口：[定义与发布](../crates/application/src/workflow/README.md)、[运行引擎](../crates/application/src/workflow_run/engine/README.md)。

### 2. 从持久状态计算进度，把节点完成与结果一起提交

**为什么需要。** 工作流可能同时运行多个独立节点。如果进度只保存在内存里，重启后就难以判断做到了哪里；如果先记录“节点成功”，再单独保存输出，中间发生崩溃，后续节点就会看到成功状态，却拿不到所需变量。

**如何实现。** 引擎根据已经保存的节点状态、条件分支决定和变量重新计算哪些节点可以执行。节点执行可以并行，但同一次 Run 的状态推进通过串行执行器协调；节点完成及其输出变量通过数据库事务一起提交。这里的事务保证这组数据库变更一起成功或一起失败。Loop 的每一轮还有独立作用域，用来区分不同轮次的执行记录和变量。

**具体效果与边界。** 例如“生成代码”和“生成说明”可以并行执行，“汇总结果”要等所需前置结果提交后才运行。持久记录为故障判断和恢复提供依据，但重启不代表能从模型生成到一半的位置继续：被中断的执行仍需按节点及容器恢复规则处理。数据库事务也不会连带撤销节点已经产生的文件或远程服务变更。

实现入口：[调度与作用域](../crates/application/src/workflow_run/engine/README.md)、[数据库执行仓储](../crates/db/src/repository/workflow_run_engine.rs)。

### 3. 按依赖关系续跑，并用 Git 检查点辅助恢复文件

**为什么需要。** 假设“分析需求 → 修改代码 → 运行测试”在修改代码时失败，全部重跑会浪费已经完成的分析；只把失败状态改回待执行也不够，因为失败节点可能留下半成品文件，后续节点的旧结果也可能失效。

**如何实现。** 续跑保留可复用的成功记录，重置失败或取消节点及受影响的后继。Agent 和复合节点执行前会尽力创建 Git 检查点，为续跑时的工作树回滚提供依据。两者分别处理执行状态和文件状态：前者决定哪些步骤重做，后者处理失败尝试留下的改动。

**具体效果与边界。** 在上例中，可以保留分析结果，重新执行代码修改，再继续测试。循环容器作为恢复单元，从第 1 轮重新开始，不承诺在内部任意节点精确接续。检查点创建属于尽力操作，失败会记录但不阻断节点；没有有效检查点时不能假定文件可恢复。Git 回滚也不能撤销已经发出的邮件或远程服务操作，不能把续跑理解成所有副作用都只发生一次。

实现入口：[失败与续跑模型](../crates/application/src/workflow_run/engine/failure.rs)、[检查点、回滚及恢复适配](../crates/backend/src/workflow/run/README.md)。

## Agent：管理会话并发、异常连接与历史交接

### 4. 统一通信协议，同时分开管理连接和会话

**为什么需要。** 不同 Agent 的启动方式和能力不同，同一个 Agent 又可能服务多个会话。如果每个业务模块各自管理连接和状态，就容易出现取消错会话、重连后旧消息污染新状态等问题。

**如何实现。** Ora 通过 ACP（Agent Client Protocol，用于宿主与 Agent 通信）对接 Agent。每个 Agent 有独立的连接监督器，负责连接生命周期；每个会话有一个 actor，可理解为持有该会话状态、按顺序处理命令的管理单元。发送消息、取消、停止等操作由它协调。路由还绑定连接代次，也就是这条连接属于第几次建立，用来丢弃旧连接的迟到消息。

**具体效果与边界。** 用户在会话 A 生成内容时打开会话 B，两个会话可以各自推进；A 的取消由 A 的 actor 处理。不同会话不等于不同操作系统进程：同一 Agent 的会话共享其进程和连接，该连接故障会影响它承载的会话。这里提供的是状态与故障范围的管理，不能据此声称每个会话都有独立安全沙箱。

实现入口：[Agent 运行时与故障范围](../crates/backend/src/agent_runtime/README.md)。

### 5. 限制积压、识别停滞，并阻止反复重启

**为什么需要。** Agent 可能持续输出导致消费者来不及处理，也可能连接仍在但长时间没有有效进展，或者启动后反复崩溃。没有限制时，这些故障会变成内存积压、永久等待或不断重启。

**如何实现。** 会话事件队列设容量上限，发送给 Agent 的 prompt 也有大小限制；运行时根据有效活动判断是否停滞。停滞重试前，先请求取消并等待旧请求明确以取消状态结束，避免上一轮输出混入下一轮。连接失败按有上限的退避时间重试；短时间连续失败会触发熔断，即停止该 Agent 的自动重启。

**具体效果与边界。** 一个会话队列溢出会结束受影响会话；连接级故障则影响该 Agent 的会话，其他 Agent 可继续工作。这里限制的是特定队列、请求和重试路径，不是整个进程的内存配额。重新发送 prompt 也不保证外部工具操作不会重复，取消确认是重试的必要条件，不是副作用已回滚的证明。

实现入口：[限制参数](../crates/backend/src/agent_runtime/limits.rs)、[停滞取消与重试](../crates/backend/src/agent_runtime/prompt_retry.rs)、[连接监督](../crates/backend/src/agent_runtime/README.md)。

### 6. 宿主持有会话历史，并记录是否完成交接

**为什么需要。** 如果历史只存在 Agent 自己的会话里，卸载插件、Agent 不可用或切换提供方后，用户可能无法查看旧对话，新 Agent 也不知道之前讨论了什么。

**如何实现。** Ora 将流式事件整理成完整记录，追加到每个会话的 JSONL 文件中；JSONL 是一行一条 JSON 记录，便于追加和逐条读取。查看历史使用 Ora 自己的记录。切换 Agent 时保留 Ora 的会话身份，把历史整理后附加到后续 prompt，并分别记录“已切换”和“已交付”。只有接收方接受了携带历史的请求，才确认交接完成，发送中断不会直接被当成成功。

**具体效果与边界。** 即使原 Agent 插件已不可用，用户仍可查看已保存的对话并选择替代 Agent。交接传递的是历史文本，不是迁移模型内部状态；当前渲染保留用户与助手正文、简化工具记录，也没有上下文窗口预算，长对话仍可能超限。历史写入失败会进入降级处理，文件刷新也不等于每条记录都完成断电持久化。这项能力不能写成已实现上下文压缩。

实现入口：[历史格式与限制](../crates/history/README.md)、[交接待办状态](../crates/backend/src/agent_runtime/handoff.rs)。

## 插件与 Skill：控制生命周期、接口能力和文件归属

### 7. 用同一生命周期入口管理安装、启动、停止和卸载

**为什么需要。** 插件既有磁盘文件，也可能有运行进程和打开的界面。若卸载只删文件，进程可能仍在访问资源；如果安装、启动、卸载同时发生，设置页显示的状态也可能与实际状态不一致。

**如何实现。** 安装路径校验包摘要、目标平台和包内路径，使用暂存目录准备内容。生命周期模块统一管理插件进程，同一插件的变更串行处理，不同插件可独立推进。卸载先关闭插件界面、停止进程，再把待删除文件移入暂存位置并提交移除；中途失败时尝试逆序补偿，提交后的残留清理另行处理。

**具体效果与边界。** 正在运行的插件被卸载时，进程退出和文件移除有明确顺序，调用方无需自行拼接这些步骤。并非所有插件都有常驻进程，静态 Skill 等类型主要交付文件或配置。多次文件操作不能获得数据库式的整体事务保证，补偿也可能失败，因此系统需要报告残留，不能把“尝试回滚”描述成一定恢复原状。

实现入口：[生命周期与卸载补偿](../crates/plugin-lifecycle/README.md)、[包管理](../crates/plugin-manager/README.md)。

### 8. 分别约束会话获得的 MCP 工具和插件界面的调用入口

**为什么需要。** 全局安装一个工具插件，不应意外改变既有工作流节点可用的工具；插件提供的界面也不能只凭方法名就调用任意后端能力。这是两类不同的授权问题。

**如何实现。** MCP（Model Context Protocol）用于接入工具服务。工作流节点创建会话时，将显式选择的 MCP 集合保存到会话上；恢复、切换 Agent 和重建连接继续读取该集合。Workbench 是可执行后端逻辑的插件类型，其方法调用同时检查插件清单允许列表与运行时实际注册的方法，两项都满足才放行。

**具体效果与边界。** 某节点只选了搜索服务，后来安装数据库 MCP，不会因此自动把数据库服务交给它。该规则针对工作流的显式选择，普通会话还存在自动发现模式。方法允许列表约束的是经 Host 接口发生的调用；当前 Agent 插件仍有较宽的执行权限，因此这些措施不能替代操作系统层面的文件、网络和进程隔离。

实现入口：[会话 MCP 选择](../crates/backend/src/session_setup/mcp/README.md)、[界面方法声明](../crates/surface/src/definition.rs)、[插件权限边界](../crates/plugin-lifecycle/README.md)。

### 9. 按期望状态交付 Skill，修改文件前核实所有权

**为什么需要。** Skill 是供 Agent 发现和使用的指令及配套文件，需要放到相应目录。目标目录可能已有用户内容，也可能被多个使用方共享；中途崩溃时，仅凭“文件存在”无法判断是之前安装成功、只写了一半，还是用户自己创建的。

**如何实现。** Effect 是项目中负责协调这类外部变更的机制：记录“应该安装什么”的期望状态，检查当前资源，再决定需要执行的操作。使用方是否准备就绪，与共享文件资源是否已经落地分开记录。覆盖或删除前核对所有权账本、标记和文件身份等证据；实际变更前先持久记录操作意图，以便中断后追查。

**具体效果与边界。** 如果交付目标与用户已有目录冲突，不能仅因名字相同就覆盖它。操作中断且失去有效执行权后，无法判断结果的操作进入隔离恢复状态，等待核实，而不是盲目再执行一次。这里的“隔离”指恢复状态，不是操作系统沙箱；期望状态也不等于已安装成功，调用方仍需检查实际交付及使用方就绪状态。

实现入口：[Effect 状态与所有权](../crates/effect/README.md)、[Skill 文件交付](../crates/effect-skill/README.md)。

## 项目与工作区：隔离并行修改，并在删除后继续承担清理责任

### 10. 用 Git worktree 分开任务目录，用持久任务追踪清理

**为什么需要。** 两个 Agent 在同一目录修改文件，容易互相覆盖或把对方的改动带入提交。另一方面，任务删除涉及数据库记录、工作目录和 Git 分支；只删除列表里的记录，可能留下无人管理的文件和分支。

**如何实现。** 创建任务时，将选定分支或引用解析为固定 commit，再创建独立的 Git worktree。worktree 是同一仓库关联的另一份检出目录，任务有各自工作目录和分支。删除业务记录时，在同一数据库事务中登记 Git 清理任务；后台再处理实际目录和分支，并保存重试或人工处理状态。清理按幂等方式设计，即重复执行时要能识别已完成的步骤。

**具体效果与边界。** 任务 A 和 B 可以从同一 commit 出发，各自在自己的目录修改代码。删除时即使程序重启，未完成清理仍可从数据库找回；无法证明属于目标任务的资源会保留供人工处理。worktree 隔离的是检出文件和分支，不会自动隔离网络端口、用户级配置、凭证或外部服务，也不等于进程安全沙箱。

实现入口：[任务与工作树创建](../crates/application/src/task/README.md)、[清理任务与重试](../crates/backend/src/git_cleanup/README.md)。

## 工程保障：减少接口分歧，验证故障下的真实行为

### 11. 从权威声明生成跨层接口，检查生成结果是否过期

**为什么需要。** Rust 后端和 TypeScript 前端需要对请求字段、返回值、操作名称和路由达成一致。多处手写同一接口时，后端改了字段，前端类型或调用入口可能还停留在旧版本，直到实际请求才暴露问题。

**如何实现。** 数据传输对象（DTO）定义跨边界传递的数据形状；逻辑操作声明业务调用；Desktop 绑定声明桌面端如何接入。它们分别由所属层维护权威定义，再生成前端类型、客户端、路由等连接代码。生成产物漂移检查用来发现“源声明已经改变，但仓库里的生成文件没有同步”的情况。

**具体效果与边界。** 增加一个工作流请求字段时，应修改它所属的声明并更新生成产物，减少逐处复制签名导致的遗漏。这能减少接口形状和连接关系的不一致，但不能证明业务规则正确，也不能取代真实调用和跨层集成测试。

实现入口：[数据契约](../crates/contracts/src/lib.rs)、[Desktop 绑定](../apps/desktop/src-tauri/bindings)、[生成客户端](../packages/contracts/src/client.generated.ts)、[生成与漂移检查任务](../Taskfile.yml)。

### 12. 用故障和取消场景验证“是否真的完成”

**为什么需要。** 正常返回成功只能覆盖最顺利的路径。更难的问题发生在提交失败、取消与完成同时发生、回复丢失或进程被强杀时；尤其是界面停止刷新，并不代表后台已完成清理。

**如何实现。** 相关测试使用真实 SQLite/Git、可注入的故障点和独立子进程，检查中断后的持久状态及恢复结果。流生命周期区分“发送取消请求”和“资源所有者确认清理完成”；需要确定完成的调用方使用 `cancel_and_wait` 等待确认，不能把丢弃流或发送信号直接当成清理成功。

**具体效果与边界。** 例如启动尚未完成时就取消、清理确认丢失、两次取消同时到达，都需要明确结果，避免留下无人管理的订阅或错误报告成功。关闭历史查看流只取消该查看者，不应误停它跟随的生成任务。不同资源的确认只证明各自协议范围内的清理，不代表所有外部服务操作都已撤回；列出测试机制也不等于所有平台和故障路径已经验证。

实现入口：[会话流及测试](../crates/backend/src/agent_runtime/stream.rs)、[Desktop 取消确认及测试](../apps/desktop/src-tauri/src/stream_registry.rs)、[持久化测试](../apps/ora-controller/tests/persistence.rs)。
