## 一个按钮后面，谁负责保证结果是真的？

点击“创建任务”会改数据库、创建 Git 工作树、刷新 UI；点击“停止回答”会发取消、等待运行者清理并结束流。若每一层都各自做一点相同业务判断，失败时很难知道谁承担补偿。

整体设计：传输层负责把请求送达并管理调用生命周期；业务所有者决定规则；存储与进程适配器完成具体动作；Backend 显式组合这些责任。启动不仅创建窗口，还要在暴露业务入口前恢复持久状态和在途责任。

## 为什么不能把业务判断直接写在按钮处理里？

### 当前设计与推演

最直观是前端检查“没有运行中会话”，然后发删除请求。但检查后另一个窗口可能开始会话，而且没有 UI 的调用者会绕过检查。正确的删除资格必须在持有业务权威的一层再检查。

**当前实现**：界面经平台接口/桌面 handler 到 Backend 的领域 API，再进入 application 用例及 repository。domain 管业务身份与实体，contracts 管公开数据/操作合同，db 管 SQL。Git、文件和 provider 是不同外部边界，传输适配器不能靠重新拼规则成为第二个所有者。

| 操作阶段 | 所有者 | 证据 |
| --- | --- | --- |
| 创建任务意图 | Task 用例 | 合法项目、固定 base commit |
| Git 工作树副作用 | Git 适配与 provisioning | 租约、目录/分支事实 |
| 用户可见任务提交 | repository 事务 | tasks/workspaces/worktrees 行 |
| 刷新列表 | 前端数据所有者 | 后端返回对象或重查结果 |

这些不是独立“微服务”，多数在同一应用内；分层价值是责任可定位和依赖可替换，不是增加网络。

连续追问“拆这么多层会不会过度设计”：用是否重复规则、是否能替换故障边界、是否增加真实消费者需要的接口衡量。**可能方案**是对过薄的无意义转发层合并，但保留业务与外部 I/O 的边界；无需新表，成本是接口调整，失败处理仍归原所有者，不能为了少一层把补偿推回 UI。

## 生成契约为什么还不能保证功能可用？

### 当前实现与反例

DTO、逻辑 operation、Desktop handler/权限分别有唯一声明，派生客户端、注册和映射，减少手写漂移。生成先到临时目录校验冲突，仅替换自己拥有的产物。公开错误形如 `{code, params, requestId}`，前端依赖稳定语义，不解析 SQLite 报错文字。

但一个类型、命令名或生成客户端存在，只证明合同存在。若 handler 没有实际执行链、节点类型只可识别但无 runtime，就不能说已落地。工作流 Prompt/Tool 与已支持节点的区别就是反例。

演算：请求合法 → handler 接受 → 用例返回语义错误 → 外层映射稳定 code → UI 翻译；内部 source chain 留给诊断。不同传输可以共用同一用例，但必须各自完成请求结束与资源清理。

**可能方案**：为每个对外操作登记行为验收入口，验证正常/失败/取消/隔离，而不只检查生成文件一致。新增测试映射资料，无需业务表；维护有成本，缺验证时标未覆盖，不能拿构建通过代替真实外部集成。

## 取消请求为什么不是停止已经完成？

### 当前实现与完整演算

流先注册，再创建底层资源；创建中取消也需要处理迟到资源。取消信号、清理触发、所有者回执是不同阶段。重复等待共享回执，等待超时不终止后台清理。诊断 requestId 与用于取消的 call ID 也不是同一个身份。

```text
t0 注册流 C1，资源尚未创建
 t1 前端离开，请求取消 C1
 t2 底层 watcher/会话创建返回
 t3 所有者释放该资源，等待原生句柄/具体操作终止
 t4 返回对应 C1 的清理回执
```

如果 t1 只删 UI 对象，t2 就泄漏；如果 t3 只发 stop 就声称完成，下一次操作可能撞到旧句柄。不能用后来另一个回合结束替旧 C1 作证明。原业务错误也不应被随后的清理错误覆盖。

**边界与缺口**：有界等待可能返回未确认，不能把 timeout 解释成旧资源一定死亡。**可能方案**是对必须跨重启负责的清理登记持久 operation/资源身份；成本是重启协调，失联保留 Unknown，不能按 PID 相同就授权杀进程。

## 启动时先恢复什么？为什么不能失败就新建空库？

**当前实现**：注入 app_data_directory、home_directory、相对路径基准、时区等路径合同。先打开/迁移数据库、读取设置，恢复技能 journal/临时导入资料，组合插件并同步目录，校正会话和工作流中断等。具体恢复仍属于各模块，数据库迁移不修复 JSONL 或 Git。

| 持久位置 | 内容 | 恢复依据 |
| --- | --- | --- |
| app_data/ora.sqlite3 | 当前 54 张表（含 migrations） | 版本历史、仓储约束 |
| app_data/sessions | JSONL、工作流专用基线资料 | 自有历史与相应业务协议 |
| app_data/atoms/skills | 正式包、journal、staging、backup | 包事务恢复 |
| home/plugins、配置的 worktree root | 包/数据与 Git 目录 | 各自身份、安装和清理责任 |

坏数据库如果被静默重建，路径上旧工作树与 provider 仍存在，却失去所有权记录。因此初始化失败必须可见；“启动可用”不能靠丢失责任实现。

## 最新的 Node/Controller/Host 链路和 Desktop 是什么关系？

这是现有代码的另一条本机执行链，不是 Desktop 已经全部迁移的证明。当前 minicloud 的过渡 clone API 由 **ora-controller 本身**提供，没有独立 minicloud server；浏览器通过本机 Vite proxy 调用，Node 独立运行，Host/Guardian 管受控 Git 进程。

| 责任 | 独立持久介质/记录 | 证明范围 |
| --- | --- | --- |
| Controller | 自己的操作和接管记录 | 已接受意图、接收 Node 结果 |
| Node | ora-node.sqlite3：execution/resource/outbox 等 | 执行去重、资源和结果责任 |
| Host | host.sqlite：Scope/Run 意图 | 原 guardian 启动和控制责任 |
| Guardian | 自己的 journal/控制端点 | 原 Run 的进程事实 |

Node 终态、资源事实、outbox 一起提交；Controller 保存结果与精确事件 receipt 后才 Ack。Ack 删除投递责任，结果与去重记录仍保留。拿到数据库锁不证明旧 Git 已停止；失联保留 Unknown，查询原身份，不用新 execution ID 绕过不确定结果。

Linux rootless 当前是 BestEffort，不是强制纳管全部逃逸后代；Host/Guardian 较强的日志配置也没有完成物理断电保证。PTY 基础组件存在不等于 Desktop 已接通完整终端产品；minicloud 是非生产本机应用，不宣称认证、多租户或云集群。这些边界在面试中要主动说准。

## 完整业务推演：结果提交后响应丢失

Desktop 创建任务的事务提交，UI 没收到响应：应查业务事实和清理责任，而不是相信“请求超时所以没创建”。Node clone 链路进一步用稳定操作身份及 outbox 解决结果投递责任，但不能把另一条链路已有的保证自动套在所有 Desktop 操作上。比较时先列相同问题，再指出各自已有证据与缺口。
