> 核对日期：2026-09-10；依据本地 `project_learn` 分支源码。本文是当前实现学习说明。

[返回学习导航](../README.md)

## 模块职责

区分项目、实际执行目录、任务标签和会话归属，建立所有运行记录共用的所有权模型。

## 设计逻辑与执行流程

`Project` 表示仓库／项目身份；`Workspace` 表示一次可定位的执行环境。一个项目可有主工作区和多个隔离工作区。`WorkspaceLocation` 保存位置合同，`WorkspaceProvisioning` 保存准备过程。

1. 项目创建由业务层校验项目属性并持久化项目及主工作区相关记录。
2. 普通项目聊天使用主工作区；任务创建额外的隔离工作区，任务仅是这个工作区的用户可见名称。
3. Agent 的 cwd 根据 `workspace_id → location` 解析，不能从 Task ID 猜路径，也不能依赖进程此刻的 cwd。
4. 项目删除通过 aggregate cascade 处理后代，事务内再次检查仍在运行的会话／工作流，避免检查后资源又被启动。

“地址已记录”与“目录已准备好”分开建模，可以表达 provisioning 失败，而不制造一个看似可用的工作区。

## 数据库表与持久化

| 表 | 关键字段／关系 | 何时写入 |
| --- | --- | --- |
| `projects` | `id,name,repository_kind,repository_url,default_branch,is_deleted` | 项目创建、编辑、软删除 |
| `workspace_locations` | `id,location_kind,plugin_id,locator_version,locator_json` | 保存执行位置；工作区通过 `location_id` 引用 |
| `workspaces` | `id,project_id,workspace_kind,location_id,lifecycle,is_deleted` | 创建主／隔离工作区、推进生命周期、软删除 |
| `workspace_provisioning` | `workspace_id` 主键；请求与实际 revision／branch／locator、`state,last_error_code` | 记录准备意图与执行结果 |
| `effect_scopes` | `workspace_id` 唯一外键 | 业务显式建立工作区 Effect 作用域 |

`workspaces_active_project_main_unique` 只允许每个项目一个未删除主工作区。远程位置／准备类型要求 `plugin_id`；非远程类型禁止该值。`sessions.workspace_id` 和 `workflow_runs.workspace_id` 指向真正的执行归属。

`0010` 已删除自动插入 Effect Scope 的旧 trigger；不要照着 `0006` 认为任意插入 workspace 都会自动产生 scope。

## 目前存在的缺陷与限制

- **已确认的限制**：Schema 能表示远程位置，不能据此断言所有远程创建和文件操作均已实现；具体能力需沿 provisioner／resolver 核对。
- **已确认的限制**：软删除不物理清空历史行；SQL 外键也不会因 `is_deleted=1` 自动删除子项，必须走级联业务。
- **设计风险**：位置 JSON 使用版本合同；外部手工移动目录会使保存的位置与磁盘不一致，解析失败需要显式处理。
