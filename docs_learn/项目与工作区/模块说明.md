## 对话究竟属于任务，还是属于一份执行环境？

同一个项目既有直接聊天，也有隔离任务和工作流运行。若所有会话都挂 Task，普通项目聊天被迫制造一个假任务；若会话只挂 Project，两个隔离工作树就无法判断应该读取哪份文件。

整体设计：Project 表示项目身份，Workspace 表示可定位的执行环境；Task 是隔离工作区的用户标签。Session、WorkflowRun、Effect Scope 直接归属 Workspace。位置合同与准备状态分开，路径由后端从身份解析。

## 为什么一个 project_id 不够？

### 当前实现与完整演算

项目 P 的主目录为 `/repo/app`，隔离任务目录为 `/worktrees/w1`，两者都属于 P，但文件内容、分支和技能投影不同。

| 表 | 主工作区投影 | 隔离工作区投影 |
| --- | --- | --- |
| projects | P, repository_kind=git | 同一 P |
| workspace_locations | L0, 本地位置合同 | L1, 隔离位置合同 |
| workspaces | W0, project_id=P, workspace_kind=main, location_id=L0 | W1, project_id=P, workspace_kind=isolated, location_id=L1 |
| tasks | 无需任务行 | T1, workspace_id=W1, title=修复重试 |
| sessions | S0, workspace_id=W0 | S1, workspace_id=W1 |

`workspaces` 的部分唯一索引保证一个项目只有一个未删除主工作区。`tasks.workspace_id` 唯一，但 S0 不必经过 tasks。实际 cwd 不能用标题拼，也不能用后端进程当前 cwd 猜；相对位置有显式 relative_path_base。

连续追问“复制 Task 标题是否复制环境”：不会，标题是展示字段。改工作树根配置也不重写已有位置。**可能方案**若支持移动环境，应保存旧/新 locator、迁移阶段和校验结果，代价是暂停使用与回滚；移动失败沿旧证据恢复，不能更新路径字符串就宣称搬迁完成。

## 为什么位置存在，还需要 provisioning 状态？

### 直观方案、当前实现与反例

只要目录路径写进表就允许发送，会把 clone/worktree 尚未完成的目录当可用。**当前实现**：`workspace_locations` 描述去哪里，`workspace_provisioning` 描述准备请求与结果，Workspace lifecycle 描述业务可用阶段。

| 时刻 | provisioning 投影 | 文件事实 | 可解释状态 |
| --- | --- | --- | --- |
| 接受准备 | requested_revision=main，actual_revision=NULL | 目录未就绪 | 有意图，未完成 |
| 解析基线 | 固定实际 commit 的准备依据 | Git 尚在创建 | 不能假定可执行 |
| 完成 | actual_revision=固定提交，actual_locator_json=实际位置，state=完成语义 | 目录验证通过 | 可以公布执行环境 |
| 失败 | last_error_code=稳定错误码 | 可能有残留 | 进入补偿/清理，不能只清错误字符串 |

这里状态文字为语义说明；具体序列化由对应 provisioner 合同决定。远程 location/provisioner 要求 plugin_id，非远程禁止填，数据库能表达远程不证明所有远程操作已接通。

**可能方案**：引入远程健康租约与定位能力版本，保存远端稳定资源 ID、最近确认和授权合同。成本是网络不确定性；暂时不可达标 Unknown，不能将“查询失败”当资源不存在后重建。Node 本机链路已有自己的执行记录，不能与 Desktop `workspace_provisioning` 混用。

## 删除项目时，为什么必须在事务内再次检查使用者？

### 当前实现与演算

前端 t0 查询没有 Running，t1 另一个窗口开始会话，t2 删除项目。如果只相信 t0，后台仍在目录里执行。**当前实现**：聚合级联在数据库写事务中检查活跃记录并软删除后代，相关外部 Git 清理责任同事务登记。SQL 外键只约束行存在，不理解 `is_deleted=1` 的业务可见性。

```text
提交前：P 可见；W1 可见；S1 正在使用 -> 删除被阻止
使用者停止后：在事务内再次核验 -> P/W1/关联记录软删除
同时保存 Git 清理意图 -> 事务提交
后台：核验资源归属 -> 物理清理或明确待人工处理
```

Effect Scope 由业务显式建立，0010 已去掉“插入 Workspace 自动建 Scope”的旧触发器。手工插表不能假设其他领域关系也自动齐全。

### 连续追问与可能方案

“事务内检查是否消除所有并发？”只能覆盖同一存储协议内正确参与的业务状态；外部编辑器、恶意同用户进程不由它控制。**可能方案**是统一环境退役协议：先拒绝新工作，等待受管使用者回执，再提交删除与清理责任。新增 retiring epoch/使用租约，成本是漏释放处理；超时保留待退役，不能强删未知占用目录。

## 完整业务推演：重命名任务后访问历史

T1 从“修复重试”改名“幂等性整改”，W1/L1 未变。S1 回放根据 S1.workspace_id 找同一环境，Git 基线仍来自 W1 的 worktrees 行，不由新标题推导。用户移动目录则属于位置漂移，resolver 明确失败；不能猜相邻同名目录继续。删除 P 时检查所有 W 的使用者，而非只检查当前选中的 T1。
