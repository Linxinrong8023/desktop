## 设置保存了，为什么正在工作的 Agent 还没采用？

用户换了工具服务凭据，保存成功；S 正在执行旧请求，T 空闲。S/T 不可能在同一瞬间神奇地切到新配置。这个模块要讲清配置内容、保存版本、实际运行版本之间的关系。

整体设计：不同作用域的设置由不同所有者管理。插件声明在不可变包里，显式值在跨版本配置文件里；保存用声明指纹和 revision 检测冲突，消费模块负责安全生效。持久成功不等于所有执行者已确认采用。

## 为什么不是所有设置都放进一个 key/value 表？

### 当前实现与反例

后端 `user_config(key,value)` 管受支持的用户偏好；插件配置服务管理 `store.json`；前端原型 UI 偏好放 localStorage。将所有东西塞进 SQLite 看似统一，却混合凭据、窗口显示状态、可执行策略和插件版本兼容规则。

| 例子 | 当前介质 | 谁解释/执行 |
| --- | --- | --- |
| log_level、network_proxy_settings、worktree_root、developer_mode | user_config | 对应后端设置所有者 |
| 插件显式 override、revision | plugins/data/namespace/name/store.json | plugin-config 校验，消费者采用 |
| theme、approvalPolicy、historyRetention 等 UI 偏好 | localStorage 的 settings store | 仅实际接线的前端行为 |
| S 的 Active MCP revision | 内存 | Session setup/刷新协调 |

**边界与缺口**：前端出现 approvalPolicy、网络开关或保留天数，不证明后台已有对应审批、隔离、清理实现。没有 `plugin_settings` 表，MCP 实值也不应复制入业务 SQLite。

连续追问“统一备份只导出数据库够吗”：不够，插件文件、前端偏好和业务文件各有作用域。**可能方案**是显式设置导出包，列出版本、来源、敏感字段处理及可移植性；成本是迁移校验，导入失败逐项报告，不能把工作区绝对路径和凭据无条件搬到另一台机器。

## 为什么保存时要同时带 revision 和声明指纹？

### 场景与完整演算

编辑器 E1、E2 同时读到 revision=7，声明 fingerprint=f1，值为 endpoint=X。E1 改 endpoint=Y 并保存；E2 改 timeout=20，若只合并它看见的旧对象，会把 endpoint 又写回 X。另一方面插件升级后声明从 f1 变 f2，旧字段即使 revision 没变化也可能非法。

**当前实现**：配置服务编译声明、合成默认与显式值、检查完整性；保存替换完整 override 集，用 revision 和 declaration fingerprint 做乐观检查。

| 步骤 | 持久事实（逻辑投影，非文件原文） | 结果 |
| --- | --- | --- |
| 两编辑器读取 | revision=7, declaration=f1, overrides={endpoint:X} | 两者持有相同基线 |
| E1 保存 | revision 推进，overrides={endpoint:Y} | E1 成功 |
| E2 用旧 revision 保存 | 当前已不是 7 | 冲突；先重读再决定合并 |
| 包升级声明 f2 | 旧表单仍带 f1 | 即便值版本巧合一致，也不能照旧表单覆盖 |

原子替换配置文件避免正常写入中读到半个 JSON；坏文件恢复会保留无冲突、本地时间命名的备份。替换或恢复失败要明确报错，不能返回一个假的“已恢复”快照。

### 连续追问：为什么不自动合并两个编辑器？

互不相关字段可以合并，但“删掉 override 使用默认值”和“显式设置为旧默认值”语义不同；声明变化还有类型/必填条件变化。**可能方案**是保存基线值与字段级意图，进行三方合并并展示冲突。新增暂存基线/编辑元数据，成本是复杂交互；冲突不自动选最后写入，用户取消时保留本地编辑，不能伪装持久成功。

## 怎样判断配置已经被所有相关执行者采用？

### 当前实现与推演

配置服务拥有保存，不拥有所有消费进程。以 MCP revision 从 7 变 8 为例：保存发不含实值的唤醒；空闲 T 安全刷新，忙碌 S 等本轮结束。刷新期间禁止新 prompt 使用过期配置，成功才推进 Active；失败只阻塞该 Session，下次再尝试。

```text
保存后：文件 revision=8
S（忙）：Desired=8, Active=7，当前轮按已有输入继续
T（空闲刷新成功）：Desired=8, Active=8
S 本轮结束、刷新失败：Desired=8, Active=7，后续 prompt 受阻
```

这些 Desired/Active 在内存，重启重新构建。日志级别采用另一种生效顺序：先串行切换运行过滤器，再保存偏好，保存失败补偿回旧级别；请求方取消等待不应截断提交/补偿责任。不能把不同消费者都套成同一种热更新流程。

**边界与缺口**：当前没有全局“所有消费者已采用第 8 版”的持久确认表。MCP Active 还只是列表投递成功，不证明模型已经用上工具。配置变更若涉及撤销权限，要明确旧请求继续执行是否可接受。

**可能方案**：保存 rollout ID、目标消费者集合、desired revision、各消费者采用回执和截止策略。解决跨重启的进度查询，成本是死实例清理和集合变化定义；超时可阻止新工作，强制中断旧工作必须另行定义，不能把保存接口成功改名 rollout 完成。

## 配置隐藏在 UI 后面是否就安全？

**当前实现**：MCP 当前设置类型限 string/number/boolean，secret/file/directory 被拒绝；HTTP header 通过 Setting 引用，URL 与文本有约束。列表 DTO 隐藏实值，Host 保留未改字段，值进入配置存储和短时解析产物，而非日志/业务表。

示例：UI 显示 credential“已配置”，保存另一个字段时没有回传原凭据，并不表示要清空它；服务按明确修改语义保留。凭据仍需交给受信任 Agent/MCP 使用，不能声称端到端不可见。磁盘权限保护也不是系统钥匙串或加密保险库。

**可能方案**：把敏感值变成凭据句柄，存储到系统安全存储，配置只保存引用。成本是平台差异、迁移与解锁；运行时拿不到凭据时阻止对应显式服务 setup，不降级到空值继续。还要限制错误来源链、第三方 stderr 对实值的暴露，不能只改 UI。

## 完整业务推演：一次保存同时遇到升级和取消

1. 用户读 f1/revision7；插件升级生成 f2。保存旧表单先失败于声明冲突，文件保持旧合法值。
2. 重读 f2 后形成完整 override 集，保存到新 revision。文件替换成功是持久提交边界。
3. 界面此时关闭，不代表通知消费者的责任消失；消费者按自己的安全点采用。
4. 若某会话刷新失败，配置本身仍已保存，不能回退全局凭据来“照顾”一个失败消费者；应暴露该会话阻塞并重试。
5. 重启后从文件重建配置状态，不能靠旧内存 Active 数字宣称已采用。
