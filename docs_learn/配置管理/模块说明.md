[返回学习导航](../README.md)

## 模块职责

区分后端用户偏好、前端界面偏好与插件配置文件，理解并发保存和失效恢复。

## 设计逻辑与执行流程

后端 `ora-user-config` 统一 ConfigKey 与值编解码；`Settings` 封装业务设置。前端原型偏好由 Zustand/localStorage 保存，不会自动同步到后端。

插件配置由包中不可变的 `assets/config.json` 声明，值在插件版本外的 `store.json` 保存。编译器校验声明和类型，服务将默认值与显式 override 合成有效配置并检查完整性。

保存插件值使用 revision 与声明 fingerprint 进行乐观并发检查，避免老编辑器覆盖新版本声明／别人刚保存的值。保存替换完整 override 集，不是任意合并若干字段。坏文件恢复会保留无冲突、本地时间命名的备份。

设置变更由相应消费模块决定如何生效，例如日志过滤器先切换并在持久化失败时补偿，MCP 则唤醒会话刷新。

## 数据库表与持久化

| 存储 | 精确用途 | 写入时机 |
| --- | --- | --- |
| `user_config(key,value)` | 后端 `developer_mode`、`log_level`、`network_proxy_settings`、`worktree_root` | Backend Settings 保存；按 key upsert |
| 插件 `<data-dir>/plugins/data/<namespace>/<name>/store.json` | 跨安装版本的显式配置值、revision | 配置服务校验并原子替换 |
| localStorage `ora.settings.v1` | 主题、默认 Agent、approvalPolicy、historyRetention 等 UI 偏好 | 前端 settings store 更新 |
| 内存 | 有效运行日志级别、打开的配置编辑器、MCP 快照 | 消费模块应用配置时更新 |

数据库没有 `plugin_settings` 表。MCP 配置值不应被复制进 SQLite；`user_config` 也不是任意业务对象的通用垃圾箱。ConfigKey 当前仅四种，不能把前端设置字段全部当成已有后端设置。

## 目前存在的缺陷与限制

- **已确认的缺口**：前端 store 明确是 prototype preferences；approvalPolicy、网络访问开关、historyRetention 的存在不能证明后端执行限制／清理服务已实现。
- **已确认的限制**：当前 MCP 设置类型限 string／number／boolean，secret／file／directory 会被拒绝；配置文件不可被描述成已经接入系统凭据保险库。
- **设计风险**：SQLite、localStorage、插件 store 有不同作用域，用户迁移机器若只备份一种介质，设置不完整。
