Lesson 0004 · Agent 执行链

NodeRun 已创建，
Session 在哪里？

Agent 节点被调度后，NodeRun 会先以 Running、session_id 为空的状态落库。执行器随后完成 warm、attach、模型选择、Prompt 组装与提交；只有首个 owning prompt 被接受后，Session 才绑定到 NodeRun 并对界面可见。

本课胜利条件：仅凭 NodeRun 状态与 session_id，就能划定故障阶段

事故现场：Running，却没有 Session

Incident

Agent A 已经出现一条 workflow_node_runs 记录，状态是 Running，但 session_id = NULL。这证明调度器已经把 A 选入 ready wave 并持久化，却不能证明 Agent Session 从未创建。

为什么？因为 Session 会先在执行器内部 warm/attach，等 owning prompt 被接受以后才公开绑定。

一条 Agent 节点的真实时间线

01 · PersistNodeRun 先落库

状态 Running，session_id 暂时为空；随后才派发执行器。

02 · Warm准备 Agent Session

按 Workspace 和 agentCli 取得 provider Session 与可用模型配置。

03 · PrepareAttach 与组装请求

选择模型、读取 Role、解析 Skill 回执、构造 Prompt、抓取文件基线。

04 · Admit提交 owning prompt

Agent actor 接受 Prompt 后，执行所有权才稳定。

05 · Publish绑定并公开 Session

写入 NodeRun.session_id，随后 UI 才能发现并跟随这条 Session。

为什么不在 Warm 后立刻绑定？

Warm / Attach 已完成 │ │ Session 尚未公开 ▼ 设置模型、组装 Prompt、提交 owning prompt │ ├─ 失败：停止并丢弃未公开 Session，NodeRun 失败 │ └─ Prompt 被接受 ▼ 绑定 session_id + 发布给 UI

如果 Session 过早对 UI 可见，界面加载会话可能与节点的首个 Prompt 争抢同一个 actor，造成 session_busy 或错误卸载。当前实现让工作流自己的 Prompt 先获得所有权，之后 UI 只能作为 follower 加入。

Prompt 提交前到底准备什么

步骤 读取来源 典型故障
解析 Agent Snapshot.agentCli 空引用、插件/provider 不可用
选择模型 Snapshot.modelId + warm 返回的模型列表 模型没有被该 Agent 公布
读取 Role Agent Definition 数据库 Repository 读取失败；Role 内容未冻结
解析 Skill Run payload 的物化回执 + Workspace 回执无绑定、路径不合法
组装 Prompt 节点配置、Run 输入、Graph、上游 NodeRun 输出 冻结 payload 或上下文无效
提交 Prompt Agent Runtime Session Busy、Provider 错误、Prompt 未被接受

看到什么，能证明什么

Running · session_id NULL

尚未越过绑定点

NodeRun 已调度；执行器可能尚未 warm，也可能已创建内部 Session 但准备或 Prompt 提交失败。

Running · session_id 有值

Prompt 已被接受

Session 已与同一 Workspace 校验并公开；可以查 Session 事件与历史。

Pending · session_id 有值

HITL 正在等待

交互节点第一轮自然结束，Session 保持开放，等待用户下一轮输入或手动完成。

Failed

先看 NodeRun.error

无 session_id 偏向绑定前失败；有 session_id 则说明曾越过绑定点，再结合 Session 与日志定位。

绑定本身也有事务门禁

  • NodeRun 必须仍为 Running；Cancel 已经获胜时，绑定返回 NotRunning。
  • Run 必须仍为 Running，不能把 Session 发布到终态 Run。
  • Session 必须存在、未删除，并且属于与 Run 相同的 Workspace。
  • 检查通过后才把 session_id 写入 NodeRun；随后执行器再发布给观察者。

绑定之后如何结束

Session 事件流 │ ├─ 自动节点 EndTurn / MaxTokens │ └─ Stop Session → 计算文件差异 → complete_node │ ├─ Refusal / 未知 StopReason / 执行错误 │ └─ fail_node │ └─ 交互节点第一轮自然结束 └─ NodeRun Running → Pending Session 保持开放，等待 HITL
Interview pressure

面试官会怎么追问

NodeRun 没有 session_id，能断言 Agent Session 从未创建吗？

不能。Warm 和 Attach 发生在绑定之前；只能断言 owning prompt 尚未成功越过公开绑定点。

为什么绑定时还要重新检查 Run 和 NodeRun 状态？

准备 Session 是异步过程，期间 Cancel 可能先完成。重新检查能让迟到绑定成为 no-op，并清理未公开 Session。

一个 Agent 节点是否总有一个 Session？

只有真正启动的 Agent NodeRun 才尝试创建专属 Session；Start、Output 等控制节点不创建 Session，绑定前失败的 Agent NodeRun 也可能始终没有公开 session_id。
