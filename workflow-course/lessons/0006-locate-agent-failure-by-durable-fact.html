Lesson 0006 · 故障定位

不要先猜日志，
先找最后一个落库事实

Agent 节点从进入 ready wave 到 ACP 回调结束，会留下几个不可逆的数据库检查点。 NodeRun.status 与 session_id 的组合，可以先把故障范围砍掉一半，再去读 Session 与日志。

本课胜利条件：看到一条异常 NodeRun，就能说出执行链已经走过什么、还没证明什么

事故现场：Running，但没有 session_id

Incident

Start → Agent A → Output 已启动两分钟，界面一直显示 A 正在运行。 

workflow_runs
status = Running
current_nodes = ["A"]

workflow_node_runs
node_id = A
status = Running
session_id = NULL
error = NULL

这不表示“调度器还没调度 A”。A 的 Running NodeRun 已经证明调度事务完成；缺少 session_id 只说明 owning prompt 尚未成功越过绑定检查点，或者后续失败回调没有完成落库。

一条 Agent 节点的八个检查点

01 · Ready内存计算

冻结 DAG 与已成功前驱算出 A Ready；这一步本身还没有 A 的 NodeRun。

02 · Persist先写 NodeRun

start_ready_nodes() 创建 Running NodeRun，并把 A 写入 current_nodes。

03 · Dispatch后台派发

WorkflowRunNodeExecutor::dispatch() 启动异步执行任务。

04 · Preparewarm 与 attach

准备 provider Session、选择模型、解析 Role/Skill，并组装 owning prompt。

05 · Admit提交 Prompt

prompt_session() 接受 owning prompt，返回事件流。

06 · Bind发布 session_id

数据库仍确认 Run/NodeRun Running 后，才绑定并公开 Session。

07 · Stream消费 ACP 事件

累计 Agent 回复，等待 stop reason；交互节点可能转为 Pending。

08 · Callback完成或失败

回调写入 output/error，移除 current_nodes，并继续调度或终止 Run。

数据库证据阶梯

持久化现象 已经能够证明 优先排查范围
没有 A NodeRun A 尚未进入成功落库的 ready wave 前驱状态、DAG ready、启动校验、调度事务
Running + session_id NULL A 已调度并落库，但 Session 尚未成功绑定 Agent 配置、warm/attach、模型、Role/Skill、Prompt admission、失败回调
Running + session_id 有值 owning prompt 已被接受，绑定检查点已越过 ACP 事件流、Agent CLI、stop reason、Session 停止与完成回调
Pending + session_id 有值 若冻结配置 interactive=true，这是合法 HITL 等待 用户后续 Prompt 或“完成当前节点”动作
Failed + error 有值 失败回调已经完成持久化，Run 同时进入 Failed 先读 NodeRun.error，再根据 session_id 判断绑定前后
Succeeded，但后继无 NodeRun 本节点完成事实已落库，后续调度可能在提交后中断 ready 重算、回调后的 run_schedule、启动恢复 reconcile

为什么 session_id 要晚绑定？

warm/attach 期间可能已经存在内部 Session，但 Ora 故意不立即把它绑定到 NodeRun。只有 prompt_session() 接受该节点的 owning prompt 后， bind_node_run_session() 才在数据库确认 Run 与 NodeRun 仍是 Running。

  • 取消操作如果先赢，迟到的绑定会被拒绝，Session 不会重新把节点“复活”。
  • 界面一旦通过 NodeRun 找到 Session，就能假设 owning prompt 已经处于活动链路。
  • session_id = NULL 不等于从未 warm，也不等于从未 attach。
  • 绑定前的准备失败会尽力停止并丢弃未公开 Session，然后通过 fail callback 落库。

一条实用的排障顺序

  1. 先用 run_id 查 WorkflowRun：状态、error、current_nodes。
  2. 再查全部 NodeRuns：找最后一个已落库节点，以及它的 status/session_id/error。
  3. 没有 session_id 时，优先检查绑定前准备链；不要先翻 Session 历史。
  4. 有 session_id 时，沿 Session 历史、Agent CLI 与 ACP stop reason 继续查。
  5. NodeRun 已 Succeeded 时，不再怀疑该节点没有执行；转查回调后的 DAG 推进。
一句话方法：先确定最后一个持久化检查点，再检查它与下一个检查点之间的代码和日志。
Interview pressure

常见追问

Running + session_id NULL，能否断言 session/new 没发生？

不能。warm 可能已经创建 provider Session，attach 也可能已经完成；Ora 只在 owning prompt 被接受后才把 Session 绑定到 NodeRun。

NodeRun 为什么必须先于外部执行落库？

它先建立执行尝试和 current_nodes 锚点。若先调用外部 Agent 再写库，数据库失败会留下已经执行却无法归属和恢复的外部副作用。

Succeeded 但 output 为空，是否代表 Agent 没回答？

不代表。协议执行可能成功，但 outputPolicy = none 会有意不把最终回复暴露到 NodeRun.output；完整对话仍属于 Session。

一手源码

  • run_schedule、complete_node 与 fail_node
  • warm → attach → prompt → bind → callback
  • 回调串行化与启动恢复
  • NodeRun、session_id 与完成状态的事务写入

遇到真实故障时，把 Run 与 NodeRun 的五个关键字段贴给老师：status、current_nodes、session_id、error、output。
